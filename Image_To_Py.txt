================================================================================
PART 220 — IMAGE-TO-PYTHON OUTPUT CONTRACT
================================================================================

The image-to-Python workflow is identical to the prompt-to-Python
workflow (Prompt_To_Py.txt PART 200) except the FACTORY the AI writes
is informed by a reference IMAGE rather than a prompt. The renderer's
contract is the same:

  1. AI receives the user's reference image (provided as an attachment
     to the chat, or as a URL the AI can fetch).
  2. AI analyses the image (silhouette, color palette, proportions,
     mechanical details, surface texture) — see PART 221.
  3. AI writes a .py file following the prompt-to-Python contract
     (PART 200-219) but with the image analysis as the design source
     rather than the user's text prompt.
  4. User drops the .py file on the page. The renderer loads it via
     the same Python pipeline as a prompt-driven .py file.

The output file format is identical — a .py file with a factory that
returns either a blueprint dict (Style A) or a THREE.Group (Style B).
What differs is the AI's INPUT BAKING — the analysis pass that goes
from "pixels" to "Python code".

The factory name convention, return type, options interface, file
layout, and pre-output checklist are ALL inherited from Prompt_To_Py.txt
PART 200 — do NOT duplicate them here.

================================================================================
PART 221 — READING A REFERENCE IMAGE
================================================================================

The first pass over a reference image extracts four things the Python
factory needs:

221.1 — SILHOUETTE
  What is the overall shape? What's the bounding box aspect ratio?
  Where are the major volumes (legs, body, head, base, top)?
  Look for:
    • Aspect ratio (W:H) — drives the scale of primitives
    • Primary axis orientation (portrait / landscape / square)
    • Visual weight distribution (top-heavy / bottom-heavy / balanced)
    • Symmetry axis (bilateral, 4-fold, 6-fold, or none)
    • Major sub-volumes (count them; name them; estimate their bbox)

221.2 — COLOR PALETTE
  What 3-12 colors dominate the image? Sample the image at the
  centroid of each major sub-volume and write down what you see.
  Look for:
    • Primary color (the largest visible area)
    • Secondary colors (accents, surface details, decals)
    • Material differentiation (matte vs. glossy vs. metallic)
    • Edge cases (highlights, shadows, gradient regions)
  Then define those colours in `lbl.define_palette({...})` (Style A)
  or as Python variables (Style B). Use semantic names:
    - "shell" for the main body color
    - "accent" for the brightest highlight
    - "frame" / "darkMetal" for darker structural elements
    - "glass" / "screen" for transparent or emissive parts

221.3 — PROPORTIONS
  Estimate the proportions of the major volumes relative to each
  other. The PART 225 contract (PART 49.1 from Prompt_To_Ts.txt)
  formalises this as a `meta.proportions` field — see PART 225 below.

221.4 — SURFACE DETAIL
  What's the silhouette beyond the major volumes? Are there:
    • Decorative details (rivets, panel lines, decals) — usually skip
      them in low-poly unless they're identity features
    • Mechanical details (joints, hinges, springs) — these become
      Mesh primitives if they're prominent
    • Surface texture (smooth / rough / metallic / matte) — drives the
      material's roughness / metalness values

PART 221 is the AI's job to perform; the renderer does NOT do image
analysis. The AI's analysis is what makes the difference between a
recognisable low-poly model and a generic box.

PART 222 — TRANSLATING IMAGE FEATURES TO lbl.* PRIMITIVES (Style A)
================================================================================

For Style A (Blueprint-Return, simple path), the translation is
direct: each major sub-volume becomes one or more `lbl.attach_box()`,
`lbl.attach_cylinder()`, `lbl.attach_chain()`, or `lbl.create_anchor()`
call.

Recipe (use this order, repeat per sub-volume):

  1. Estimate the sub-volume's bbox (width, depth, height) in
     proportion to the overall model.
  2. Decide the sub-volume's primitive type:
       • Box-like → lbl.attach_box(id, footprint_size=(W, D), length=H)
       • Cylinder-like (rotationally symmetric) → lbl.attach_cylinder(...)
       • Long thin element → lbl.attach_chain(...) with keypoints
       • Reference point only → lbl.create_anchor(id, position=...)
  3. Decide the position relative to the world origin (the centre of
     the bbox base is the easiest anchor).
  4. Decide the rotation (default Y-up; rotate the aim for sideways
     parts).
  5. Pick a material from the palette (PART 224).
  6. Repeat for the next sub-volume. Adjust positions so parts touch
     cleanly (no gaps, no overlaps).

Example (a coffee mug):
  Image analysis:
    • Silhouette: cylinder with handle. Height ≈ 1.4 × diameter.
    • Palette: matte ceramic white, dark brown ring around top.
    • Proportions: diameter 1.0 × height 1.4. Handle protrudes 0.25.
  Style A factory:
    lbl.name("Coffee Mug")
    lbl.define_palette({
        "ceramic": {"color": "#f4f0e6", "roughness": 0.65, "metalness": 0.0},
        "rim":     {"color": "#5a3a00", "roughness": 0.4,  "metalness": 0.0},
    })
    # Body — cylinder
    lbl.attach_cylinder("body", radius=0.5, length=1.4,
                        position=(0, 0.7, 0), material="ceramic")
    # Rim accent
    lbl.attach_cylinder("rim", radius=0.52, length=0.06,
                        position=(0, 1.37, 0), material="rim")
    # Handle — chain (3 cylinders along a half-loop)
    lbl.attach_chain("handle",
                     segments=[(0.5, 1.0, 0), (0.75, 0.7, 0), (0.5, 0.4, 0)],
                     base_radius=0.06,
                     position=(0, 0, 0),
                     material="ceramic")
    return lbl.blueprint()

That's 3 attach calls → coffee mug. The rim accent is a stylistic
choice; the handle is the only complex part (a chain). Most low-poly
mugs are 4-6 attach calls total.

================================================================================
PART 223 — TRANSLATING IMAGE FEATURES TO THREE.* PRIMITIVES (Style B)
================================================================================

For Style B (Three.js Direct, advanced path), the translation is the
same shape as Style A but you reach for Three.js primitives directly.
Reach for Style B when the image shows:
  - Anything non-primitive (a character with a non-cylindrical head shape)
  - Anything with holes / cutouts (the engine block of a motorcycle)
  - Anything with detailed mechanical articulation (a folding knife)
  - Anything with custom surface materials (clearcoat, transmission, etc.)

Recipe (Style B):
  1. Estimate the bbox and primitive type (same as Style A).
  2. Reach for the right Three.js geometry constructor:
       • Box-like → THREE.BoxGeometry.new(w, h, d) OR
                    THREE.RoundedBoxGeometry.new(w, h, d, segments, radius) (from three/addons)
       • Cylinder-like → THREE.CylinderGeometry.new(rT, rB, h, segs)
       • Sphere-like → THREE.SphereGeometry.new(r, w, h)
       • Lathe-symmetric → THREE.LatheGeometry.new(points, segs)
       • Extrude-from-2D-shape → THREE.ExtrudeGeometry.new(shape, opts)
       • Tube-along-curve → THREE.TubeGeometry.new(curve, segs, radius, ...)
  3. Compose the geometry + a MeshStandardMaterial into a Mesh.
  4. Set castShadow / receiveShadow / name (PART 207 sculptRuntime).
  5. Position, rotate, add to the Group.
  6. Repeat per sub-volume.
  7. (Optional) Add a tick for per-frame animation (PART 208).

Example (a chunky motor scooter):
  Image analysis:
    • Silhouette: low-poly retro scooter with a front shield, a step-
      through frame, 2 wheels, a headlight, and a saddle.
    • Palette: matte red body, chrome accents, black wheels, glass headlight.
    • Proportions: width 1.4 × length 2.2 × height 1.4. Wheels at corners.
  Style B factory:
    (See the full example in Prompt_To_Py.txt PART 212 — the same code
     applies to image-driven factories; the only difference is the
     analysis input that drove the choice of primitives.)

PART 224 — COLOR SAMPLING (THE 6-BAND PALETTE DISCIPLINE)
================================================================================

The image-driven path requires the AI to extract a coherent palette
from the reference image. The discipline (same as Prompt_To_Ts.txt
PART 153-166 §2):

  1. Sample the dominant color in 6 representative regions:
       ├── top-of-body
       ├── mid-body
       ├── bottom-of-body
       ├── accent / feature
       ├── structural (frame, edges)
       └── wheel / base
  2. Each region contributes ONE palette entry (sometimes two, if the
     region has a sharp color boundary).
  3. Name the entries semantically:
       shell, accent, frame, darkMetal, glass, wheel, saddle, ...
  4. Optional: declare a "primary" palette entry (the most visible
     color) and 5 "accent" entries.

The 6-band discipline is a guideline, not a hard rule. If the image
shows a 3-color palette (a banana is yellow with brown tips and green
stem), use 3 palette entries. If it shows 12 colors (a peacock), use
as many as the scene needs — but group semantically.

Define the palette in `lbl.define_palette()` (Style A) or as Python
variables (Style B). Reference each palette entry from the relevant
attach* call.

PART 224.1 — COLOR FORMAT
  Python accepts the same color formats as the JSON pipeline:
    - Hex strings: "#ff6b35"
    - Hex integers: 0xff6b35
    - Named CSS colors: "orange", "tomato", "cornflowerblue"
  Pick whichever is cleanest for the value. Hex strings read best in
  palette declarations; hex integers read best in tight code.

PART 225 — PROPORTION DECLARATION (the PART 49.1 contract)
================================================================================

For image-driven factories, declare the model's proportions in TWO
places — they serve different purposes:

  1. AS A `#` COMMENT BLOCK AT THE TOP OF THE FILE (the text-level
     declaration). This is the canonical PART 49.1 contract — a
     10-line `# FIELD: value` block placed BEFORE any code, so the
     renderer's parseProportionDeclaration() can extract it. Without
     this, the validator warns "PART 49.1 proportion declaration
     not found at all".

  2. IN THE RETURNED DICT'S `meta.proportions` FIELD (the data-level
     declaration). This is the structured form the validator's
     schema check uses to grade the build.

Both are required. The comment block survives a copy-paste through
chat (a paper trail for the audit); the meta.proportions field is
what the fidelity grader actually reads.

────────────────────────────────────────────────────────────────────
225.0 — THE TEXT-LEVEL `#` COMMENT DECLARATION
────────────────────────────────────────────────────────────────────

The validator (v1.36 / v8.28+) accepts both `//` (JSON/JS/TS) and
`#` (Python) comment styles. For a .py factory, place this block
BEFORE any code/imports:

    # STYLE: smooth-low-poly
    # CAMERA: isometric-front-right
    # SUBJECT_CATEGORY: character
    # HEAD_TO_BODY: 0.45
    # PRIMARY_ASPECT: 0.8 width / 1.2 height / 0.6 depth
    # LIMB_TO_TORSO: 0.6
    # SUBJECT_HEIGHT: 1.7
    # DOMINANT_COLORS: #6c7280, #ff9aa2, #2c2f36
    # BACKGROUND: #e8edf2
    # DISTINCTIVE_DETAIL: rounded-box chassis with glowing antenna orb

The 10 fields are the same 10 from PART 49.1's enumerated set. The
PROPORTION_DECL_FIELDS list in index.html is the authoritative source
for the canonical field names — don't rename them or the regex won't
match.

────────────────────────────────────────────────────────────────────
225.1 — THE DATA-LEVEL meta.proportions DICT
────────────────────────────────────────────────────────────────────

Shape (Style A):
  return {
      "meta": {
          "name": "My Model",
          "proportions": {
              "W_over_H": 1.0,   # width / height ratio
              "fill": 0.85,      # overall silhouette fullness 0..1
              "leg_fraction": 0.4,  # leg height / total height (if any)
              "head_share_of_length": 0.25,
              "belly_y_over_H": 0.45,
              # ... other fields as relevant
          },
      },
      "materials": {...},
      "objects": [...],
  }

For Style B, the proportions live in `g.userData.meta.proportions`
(Style B doesn't have a meta dict, but userData.meta is the
cross-path equivalent — see PART 202.2.1 in Prompt_To_Py.txt):

  g.userData.meta = {
      "style": "smooth-low-poly",
      "category": "character",
      "proportions": {
          "W_over_H": 0.55,
          "fill": 0.78,
          "head_share_of_length": 0.21,
      },
  }

The validator (validateBlueprintSchema) checks the proportions are
plausible (W_over_H between 0.1 and 10, etc.). Plausible proportions
+ image-aligned primitives → low render failure rate.

If you omit `meta.proportions` entirely, `lbl.blueprint()` auto-
injects the canonical defaults `{"W_over_H": 1.0, "fill": 0.85}` —
same shape as the Style A case. Style B factories that omit
`userData.meta` get the same defaults auto-injected by the renderer
in v1.36 / v8.28+ (see PART 202.2.1).

PART 225.1 — WHAT TO DECLARE
  Always include W_over_H (the bbox aspect ratio). Include other
  fields only if the model has the corresponding feature:
    • leg_fraction — only if the model has legs (mascot / creature)
    • head_share_of_length — only if the model has a head
    • wheel_radius_over_H — only if the model has wheels
    • fin_count / wing_count — only if the model has fins / wings

PART 225.2 — HOW TO MEASURE
  Estimate from the reference image:
    • Trace the bounding box of the silhouette.
    • W_over_H = bbox.width / bbox.height (in image-space)
    • leg_fraction ≈ 0.4 means the legs take up 40% of the total height
    • Don't agonise over precision — a ±20% estimate is fine.

PART 226 — IMAGE-DRIVEN WORKED EXAMPLE
================================================================================

To exercise the full pipeline end-to-end, follow this recipe with the
AI:

  1. Provide a single reference image (a chunky low-poly motor scooter,
     or any subject — the example assumes a chunky retro scooter).
  2. Ask the AI to analyse the image (PART 221).
  3. Ask the AI to declare a 6-band palette (PART 224).
  4. Ask the AI to write a .py file using the Blueprint-Return style
     (Prompt_To_Py.txt PART 200 + PART 222 style A recipe).
  5. Drop the .py file on the page.

Example output the AI would produce for a chunky motor scooter image:

  """
  scooter.py — image-driven Style A factory.
  Analysis: silhouette is low-poly retro scooter; primary color is
  coral red body with chrome accents, black wheels, glass headlight.
  """
  import lbl

  def create_model():
      lbl.name("Chunky Retro Scooter")
      lbl.define_palette({
          "shell":      {"color": "#e8553d", "roughness": 0.55, "metalness": 0.05},
          "accent":     {"color": "#f7d959", "roughness": 0.4,  "metalness": 0.1,
                          "emissive": "#5a3a00", "emissiveIntensity": 0.2},
          "frame":      {"color": "#2a2a2e", "roughness": 0.8,  "metalness": 0.2},
          "glass":      {"color": "#aef5ff", "roughness": 0.05, "metalness": 0.0,
                          "transparent": True, "opacity": 0.7},
          "wheel":      {"color": "#1a1a1e", "roughness": 0.95, "metalness": 0.0},
          "saddle":     {"color": "#3a2a1a", "roughness": 0.85, "metalness": 0.0},
      })

      # Body — main shell (boxes front-shield + step-through + rear)
      lbl.attach_box("body_front",  footprint_size=(1.0, 0.4), length=1.0,
                     position=( 0.55, 0.7, 0), material="shell")
      lbl.attach_box("body_step",   footprint_size=(0.8, 0.4), length=0.6,
                     position=( 0.0, 0.5, 0), material="shell")
      lbl.attach_box("body_rear",   footprint_size=(1.0, 0.4), length=0.7,
                     position=(-0.55, 0.55, 0), material="shell")

      # Headlight (glass + accent)
      lbl.attach_cylinder("headlight_glass", radius=0.18, length=0.05,
                          position=(1.04, 1.05, 0), material="glass")
      lbl.attach_cylinder("headlight_glow", radius=0.12, length=0.04,
                          position=(1.02, 1.05, 0), material="accent")

      # Frame underneath the step-through
      lbl.attach_box("frame",       footprint_size=(0.7, 0.3), length=0.18,
                     position=( 0.0, 0.25, 0), material="frame")

      # Wheels
      for i, x in enumerate(( 0.65, -0.65)):
          lbl.attach_cylinder(f"wheel_{i}", radius=0.3, length=0.18,
                              position=(x, 0.3, 0), material="wheel")

      # Saddle on top
      lbl.attach_box("saddle",      footprint_size=(0.6, 0.25), length=0.15,
                     position=(-0.35, 1.0, 0), material="saddle")

      return lbl.blueprint()

That's ~30 lines → 11-object low-poly scooter. Most image-driven
factories are in this size range (15-50 attach calls).

PART 227 — WHEN TO REACH FOR STYLE A vs. STYLE B FOR IMAGE-DRIVEN WORK
================================================================================

The choice is the same as the prompt-driven path (Prompt_To_Py.txt
PART 217) — Style A for procedural primitives, Style B for Three.js
features. But for image-driven work, Style A covers more ground, because:

  1. Most reference images map cleanly to the primitive vocabulary
     (box, cylinder, sphere, lathe). Style A is the right choice for
     ~80% of images.
  2. Style B is needed when the image shows:
       • Character mascots with non-primitive shapes (use lathe / extrude)
       • Skeletal / rigged subjects (need AnimationMixer)
       • Vehicles with detailed mechanical articulation (need
         rotation joints, hinge groups)
       • Anything with custom shaders (clearcoat, transmission, etc.)

The bias toward Style A for image-driven work is a feature, not a
limitation — Style A is faster to iterate (the validator catches
schema errors with helpful messages), easier to debug (no Three.js
roundtrip), and produces smaller files.

PART 228 — IMAGE NOISE / SCALE / LIGHTING PITFALLS
================================================================================

228.1 — IMAGE NOISE
  Reference images often have photographic noise, JPEG artefacts, or
  surface texture that doesn't translate to primitives. Ignore it —
  the renderer is a low-poly tool, not a photorealistic one. Focus on
  the major volumes.

228.2 — SCALE
  The reference image has its own scale (in pixels). The factory's
  primitives are unitless. Pick a convention: the model's bounding
  box should fit within roughly [-1, +1] in each axis. If your
  primitives overflow, the renderer auto-frames the camera but the
  model will look small relative to the viewport. If your primitives
  are too small (sub-0.1), they'll be hard to see.

228.3 — LIGHTING
  Reference images are lit. The renderer's scene has its own lighting.
  Don't try to bake the image's lighting into the model — instead, let
  the renderer's PBR materials + scene lights handle it. The factory
  just sets material colours; the renderer does the rest.

228.4 — BACKGROUND
  Most reference images have a background (sky, table, gradient).
  Ignore it — the factory only models the subject. If the AI tries
  to model the background too, the model will have lots of irrelevant
  geometry that clutters the scene.

228.5 — TRANSPARENCY / GLASS
  Some reference images show glass / transparent materials (a glass
  jar, a clear phone screen). The renderer supports transparency via
  `transparent: True` in the material definition. Don't try to fake
  transparency with a low-saturation color — set the flag.

228.6 — MULTIPLE OBJECTS
  If the reference image shows multiple objects (a coffee cup on a
  saucer next to a spoon), the factory models ALL of them in one
  blueprint — not just the most prominent. The renderer mounts the
  whole blueprint, and the inspector lets the user pick any part.

────────────────────────────────────────────────────────────────────
230. STYLE FIELD (text → palette + style hints)
────────────────────────────────────────────────────────────────────
The problem: an AI / user says "rusty iron with a glowing seam" or
"matte ceramic with brass fittings" and the factory has to translate
that into a 6-band palette. Real systems (text2mesh, CLIP-Mesh) use
CLIP embeddings. We use a curated text→mood-color lookup table —
deterministic, no ML, no GPU, instant, runs in Pyodide.

Python:
    sf = lbl.style_field("rusty iron with brass fittings")
    # sf = {
    #   palette: [
    #     { name: "shell",  color: "#3a3d42", roughness: 0.55, metalness: 0.85 },
    #     { name: "metal",  color: "#b5965a", roughness: 0.40, metalness: 0.80 },
    #     { name: "accent", color: "#8b3a1a", roughness: 0.85, metalness: 0.30 },
    #     ...
    #   ],
    #   style: { mtlMood: "rusty", glossLevel: 0.45, emissiveLevel: 0,
    #            matchedKeywords: ["iron", "brass"] }
    # }
    for entry in sf["palette"]:
        lbl.define_palette({ entry["name"]: entry })

Style B:
    from js import MT_textures
    sf = MT_textures.makeStyleField("ceramic vase with neon glow")

Reference repos: text2mesh (Michel et al., CVPR 2022),
                  CLIP-Mesh (Khalid et al., SIGGRAPH ASIA 2022).
Mood table lives in `mt-texture-extensions.js` (window.MT_textures
.moodTable). ~50 keywords across metals / plastics / organics /
stones / naturals / glow / specials. Extend via opts.moodOverrides
when authoring a new domain.

────────────────────────────────────────────────────────────────────
231. MULTI-SCALE PATTERN (multi-octave procedural)
────────────────────────────────────────────────────────────────────
Stack the same procedural pattern at 2-4 scales with weighted
blending. From geometric-textures (Hertz et al., SIGGRAPH 2020):
"Multi-scale generator approach — learns texture statistics at
multiple scales and progressively applies finer details."

Python:
    r = lbl.multi_scale_pattern(
        {"type": "noise", "seed": 1, "octaves": 4},
        size=512,
    )
    # r = { canvas, texture }
    # Apply the texture to a material:
    #   material.map = r["texture"]
    #   material.needsUpdate = True

Default levels: [{1, 0.5}, {4, 0.3}, {16, 0.15}, {64, 0.05}] — base
pattern at 1×, fine detail at 4×, micro-detail at 16×, sparkle at
64×. Override via opts.levels = [{scale, weight}, ...] for
domain-specific patterns (e.g. a single 1× level with weight 1.0
for a clean wood-grain, or 6 levels for a fractal dirt).

────────────────────────────────────────────────────────────────────
232. CAVITY-AWARE PATTERN (curvature-modulated)
────────────────────────────────────────────────────────────────────
Wraps a procedural pattern with curvature-driven intensity
modulation: cavities boost contrast (dirt-in-crevices, the PART 74
cavity-dirt trick); ridges pull toward the base color (polished
rim). From mesh-texture-synthesis (Kovacs et al., CGF 2024):
"tracks oriented patches surrounding each texel on mesh surfaces,
enabling seamless texture synthesis that accounts for geometric
content."

Python:
    from js import THREE  # or via your lbl.attach_box chain
    geom = THREE.SphereGeometry.new(1, 24, 16)
    r = lbl.cavity_aware_pattern(
        {"type": "noise", "seed": 7},
        geom,
        size=256,
        curvatureMode="both",     # "cavity" | "ridge" | "both"
        curvatureStrength=0.6,    # 0..1
    )
    # r.texture, r.curvature (per-vertex Float32Array)

────────────────────────────────────────────────────────────────────
233. GEODESIC FIELD (geodesic distance on a mesh)
────────────────────────────────────────────────────────────────────
For each vertex, compute the approximate geodesic distance to the
nearest anchor. Useful for procedural placement of patches /
detail / UV islands along the surface. The same idea as UV3-TeD
(Foti et al., 3DV 2023) and Point-UV Diffusion (Yu et al.,
ICCV 2023), which use geodesic heat diffusion for UV-free texture
synthesis, but reduced to a vertex-distance field that composes
with the renderer's UV pipeline.

Python:
    distances = lbl.geodesic_field(
        geom,
        [[0, 1, 0]],   # anchor at top of sphere
    )
    # distances is a Float32Array, length = vertex count
    # Use it to mask an existing material:
    #   for i, v in enumerate(vertices):
    #       v.material.opacity = 1.0 - min(1.0, distances[i] / 0.5)

────────────────────────────────────────────────────────────────────
234. PROGRESSIVE UV (visibility-priority UV unwrap)
────────────────────────────────────────────────────────────────────
Like uvUnwrap, but processes the mesh in a visibility-priority
order so the most-seen faces get assigned UV space first with
the highest texel density. From Text2Tex (Richardson et al.,
ICCV 2023): "Tracks each texel's generation status, dynamically
segments rendered views into a generation mask tracking each
texel's generation status." We adapt that to UV space: the
texture-space atlas is filled in visibility order, so the
"first painted" faces always have the best texel density.

Python:
    result = lbl.progressive_uv(
        geom,
        cameraDir=[0, 0, 1],   # view direction
        method="planar",        # "planar" | "box"
        axis="y",               # for planar
        atlasSize=1024,
    )
    # result.faceOrder   — visibility-priority face indices
    # result.tilesPerRow — atlas grid (sqrt(triCount))
    # UVs written to geom.attributes.uv in place

PART 235-242 — HIGH-POLY / STYLE-AGNOSTIC SURFACE (v1.36 / v8.30)

The "low_poly_3d" project name is a brand, not a constraint.
PART 38.22 of the spec already declares the system style-agnostic —
13 canonical styles including `pbr-realistic` and `photogrammetry`,
which are inherently high-poly. PART 235-242 backstops that
declaration with concrete high-poly capability:

  235. importExternalMesh(url, format)  — OBJ / GLTF / FBX / STL / DAE

  237. makeFastCurvature(geom, opts)    — BVH-accelerated curvature
  238. highPolyPBR(opts)                — pbr-realistic material recipe
  239. photogrammetryPBR(opts)          — photogrammetry material recipe
  240. subdivideForHighPoly(geom, opts)  — boost low-poly → high-poly
  241. decimateForLowPoly(geom, opts)    — reduce high-poly → low-poly
  242. makeImageTexture(url, opts)      — image → UV texture

JS surface (window.MT_highpoly): the 8 helpers + a selfTest.
Python surface (lbl.*): 8 pass-through methods

────────────────────────────────────────────────────────────────────
Style-agnosticism contract
────────────────────────────────────────────────────────────────────
The renderer's auto-injected default meta.style is still
"smooth-low-poly" (matches the project name; the chunky 3D look
the demo models ship). To use this module's high-poly surface,
override the default explicitly:
    bp = lbl.blueprint()
    bp["meta"]["style"] = "pbr-realistic"     # for high-poly meshes
    # or
    bp["meta"]["style"] = "photogrammetry"   # for scanned meshes

The renderer reads meta.style to pick the matching look-dev
lighting rig (PART 187 / 199.3) and to apply the triangle-budget
guidance (PART 50.4). The default is low-poly because that's
what the demo models use; it's NOT because the renderer can't
do high-poly — see the catalog table below.

235. IMPORT EXTERNAL MESH (load any 3D model file)
────────────────────────────────────────────────────────────────────
Python:
    import asyncio
    g = await asyncio.ensure_future(
        lbl.import_external_mesh(
            "https://example.com/scan.glb", format="glb",
        )
    )

Style B:
    from js import MT_highpoly
    g = await MT_highpoly.importExternalMesh(url, "glb")

Supports: OBJ, GLTF (.gltf + .glb), FBX, STL, Collada (.dae).
Auto-normalises: computes vertex normals if missing, generates
planar UVs if missing (STL files often have no UVs), assigns a
neutral MeshStandardMaterial if missing. Stashes loader metadata
on g.userData.__gltf so animation clips can be picked up by
the renderer's animation player.

────────────────────────────────────────────────────────────────────
236. ATLAS UV (MaxRects BSSF packing for high-poly)
────────────────────────────────────────────────────────────────────
Python:
    r = lbl.make_atlas_uv(geom, atlasSize=2048, padding=4)
    # r = { uv, atlasSize, faceCount, packed }
    # UVs written into geom.attributes.uv in place

For meshes with 1K+ faces, this is the right way to assign UVs.
makeProgressiveUV (PART 234) is the visibility-priority shortcut
for low-poly (≤100 faces). For meshes where every face is equally
visible and texel density matters, use makeAtlasUV.

────────────────────────────────────────────────────────────────────
237. FAST CURVATURE (BVH-accelerated for 100K+ verts)
────────────────────────────────────────────────────────────────────
Python:
    curv = lbl.fast_curvature(geom, scale=0.02)
    # curv is a Float32Array, length = vertex count

For meshes with 100K+ verts (photogrammetry scans, etc.), use
this instead of lbl.cavity_aware_pattern (PART 232) which uses
a 3×3×3 hash (O(N×27)). The BVH path is O(N log N). Falls back
to the spatial-hash version if MeshBVH isn't loaded.

238-239. HIGH-POLY MATERIAL RECIPES

240-241. RESOLUTION TRANSITIONS
────────────────────────────────────────────────────────────────────

    high_geom = lbl.subdivide_for_highpoly(low_geom, { rates: 2 })

model and you want to render it in a high-poly style, or when a
photogrammetry scan is too heavy and you want to simplify it for
real-time rendering.

PART 275-280 — v1.36 / v8.27 IMAGE-DRIVEN PYTHON ADAPTATION
================================================================================

The original v1.36 / v8.27 release shipped PART 220-229 for image-
to-Python, but those PARTs were the BASIC image-to-Python contract
only — they cross-referenced the image-driven methodology
(PART 153-166) without embedding it. AI factories were expected
to read Image_To_Ts.txt's PART 153-166 and translate the TS
examples to Python on their own, which left most image-driven
Python factories using a single primitive per major volume and
skipping the validation gates (IoU check, 3-variant ranking,
detail inventory).

PART 275-280 fixes this by shipping the image-driven methodology
as Python-native recipes. Each PART is the image-driven analogue
of a PART 153-199 / 250-254 layer, with concrete `def` examples
for the Python idioms (lbl.* helpers + `from js import THREE` +
the renderer's validation gates).

These PARTs are layered on top of PART 220-229 (basic image-to-
Python contract) AND PART 243-274 (Python adaptations of the
methodology layers from Prompt_To_Py.txt). They do NOT replace
the TS spec — the canonical image-driven methodology lives in
Image_To_Ts.txt. This file ships the Python form.

────────────────────────────────────────────────────────────────────────
PART 275 — IMAGE-DRIVEN FACTORY DEFAULTS (PYTHON FORM)
(amends Image_To_Ts.txt PART 153-166)
──────────────────────────────────────────────

Image-driven Python factories get the 14 image-driven factory
defaults (PART 153-166) in their Python forms. Each default has
a concrete recipe:

  153. MT HELPER DEFAULTS
       Use `from js import MT_core, MT_meshes, MT_advanced` instead
       of hand-authored BufferGeometry. See PART 244 above for the
       8 shape-creation techniques in Python form.

  154. ACES AUTO-TRIGGER
       The renderer's lblValidateAgainstSpec() function auto-runs
       `ACES.run({scene: root})` on every image-driven factory. No
       Python code needed — the renderer wires it.

  155. MAT_DB SEMANTIC LOOKUP
       Use `lbl.style_field("...")` (PART 230) for prompt-based
       material lookup, or `lbl.color_sampling(image, region)`
       (PART 275.5 below) for image-based color sampling.

  156. STYLE-LOCK flatShading + outline + toneMapping
       The renderer's lookDevLights() factory auto-applies the
       style-lock rules based on `meta.style`. For `chunky-mascot`:
           - every material gets `flatShading: True` (PART 252)
           - OutlinePass is enabled
           - renderer.toneMapping = NoToneMapping
       The Python factory doesn't need to set any of this manually.

  157. imageToWorld() HELPER
       Python:
           from js import lblSpec
           world_pos = lblSpec.helpers.imageToWorld(
               [pixel_x, pixel_y],   # pixel coordinates
               ref_img,              # the reference image (HTMLImageElement)
               [0, 0, 0],            # camera position
               [0, 0, 1],            # camera forward
           )
       Converts a pixel coordinate in the reference image to a
       world-space position. Use this to translate image features
       to factory primitives (PART 222.1).

  158. IoU CHECK HELPER
       The renderer's `lblSpec.helpers.compareToReference(root, img)`
       computes the IoU between the rendered silhouette and the
       reference image. See PART 254 above for the full Python
       form, including the graceful-skip for prompt-only mode.

  159. SDF + MARCHING CUBES TRIGGER
       If the model has >2 contiguous body parts, the renderer
       auto-triggers `MT_core.sdfUnion` + `MT_core.sdfMarch`. See
       PART 250 above for the Python form.

  160. CSG RECIPES
       The renderer's `MT_meshes.csg_union(a, b)` (Python form)
       handles the standard CSG cases. For architectural CSG, use
       `MT_architectural.createWallWithApertures` (PART 271.1).

  161. MT.core.loft STANDARD
       The renderer's `MT_core.loft(profile, opts)` is the standard
       for limb construction. See PART 253 above for the Python
       form.

  162. INSTANCED RIVETS
       `MT_advanced.makeInstanced(rivet_geo, count, {"transforms": ...})`
       is the standard for repeated small details. Python form.

  163. PMREM/HDRI AUTO-ENABLE
       The renderer auto-enables PMREM/HDRI for metallic materials
       (any material with metalness >= 0.5). No Python code needed.

  164. DETAIL INVENTORY
       The renderer's detail-inventory discipline (PART 207) is
       the standard. Python:
           g.userData.sculptRuntime = {
               ...,
               "detailInventory": [
                   {"id": "body", "region": "chassis",
                    "kind": "feature", "priority": "high",
                    "reviewThreshold": 0.7},
                   ...
               ],
           }
       The validator checks that every high-priority entry has at
       least one matching Mesh in the userData tree.

  165. 11-STEP CANONICAL RECIPE
       The 11-step recipe (with ACES + IoU) is documented in PART
       243.1 + PART 248.2. The renderer's drop-validator runs
       steps 7-11 automatically.

  166. 3-VARIANT RANKING
       For image-driven factories, generate 3 variants (seeds 1,
       2, 3), run ACES + IoU on each, pick the highest-IoU +
       fewest-warnings. Python:
           best = None
           best_iou = 0
           for seed in (1, 2, 3):
               g = build_variant(seed)
               iou = lblSpec.helpers.compareToReference(g, ref_img)
               if iou > best_iou:
                   best_iou = iou
                   best = g
           return best
       Most Python factories skip this for simplicity; it ships
       in the canonical MT_* helper if you opt in.

  275.5 — COLOR SAMPLING HELPER (NEW in this release)
    Image-driven Python factories can use a Python-native color
    sampler that wraps the renderer's imageToWorld() + style_field()
    pattern:
           from js import lblSpec
           palette = lblSpec.helpers.sampleImagePalette(ref_img, n=6)
           # palette = [
           #   {"name": "shell",  "color": "#e8553d",
           #    "roughness": 0.55, "metalness": 0.05, "share": 0.42},
           #   {"name": "frame",  "color": "#2a2a2e",
           #    "roughness": 0.8,  "metalness": 0.2,  "share": 0.18},
           #   ...
           # ]
           lbl.define_palette({p["name"]: p for p in palette})
    The 6-band palette discipline (PART 224) is auto-applied —
    the helper picks the top-6 dominant colors by area and
    names them based on luminance + position.

  276.1 — IMAGE-DRIVEN SCOOTER WORKED EXAMPLE (Style B)
    The original v1.36 / v8.27 release only shipped a Style A
    scooter example (PART 226). PART 276.1 adds the Style B form
    for cases where the image shows non-primitive shapes (a
    curved fairing, a sculpted tank):

      """
      scooter_style_b.py — image-driven Style B factory.
      Analysis: chunky retro scooter with a curved front fairing,
      rounded tank shell, sculpted saddle, chrome accents.
      Style A (Blueprint-Return) can't express the curved fairing,
      so this is Style B (Three.js Direct).
      """

      from js import THREE, MT_hardsurface, lblSpec
      import math

      def create_model():
          g = THREE.Group.new()
          g.name = "Chunky Retro Scooter (Style B)"

          # Body shell — extruded 2D shape with curved top
          body_shape = THREE.Shape.new()
          body_shape.moveTo(-0.7, 0)
          body_shape.lineTo(0.7, 0)
          body_shape.bezierCurveTo(0.85, 0.1, 0.85, 0.5, 0.7, 0.6)
          body_shape.lineTo(-0.5, 0.6)
          body_shape.bezierCurveTo(-0.7, 0.6, -0.85, 0.4, -0.7, 0)
          body_shape.closePath()
          body_geo = THREE.ExtrudeGeometry.new(body_shape, {
              "depth": 0.4,
              "bevelEnabled": True,
              "bevelSize": 0.04,
              "bevelThickness": 0.04,
              "bevelSegments": 4,
          })
          body_mat = THREE.MeshStandardMaterial.new({
              "color": 0xe8553d, "roughness": 0.55, "metalness": 0.05,
              "flatShading": True,
          })
          body = THREE.Mesh.new(body_geo, body_mat)
          body.position.set(0, 0.4, 0)
          body.castShadow = True
          body.receiveShadow = True
          body.name = "body"
          g.add(body)

          # Tank shell — lathed half-ellipse
          tank_pts = []
          for i in range(11):
              t = i / 10.0
              # Half-ellipse: rx=0.28, ry=0.18
              x = 0.28 * math.cos(t * math.pi)
              y = 0.18 * math.sin(t * math.pi)
              tank_pts.append([x, y])
          tank_geo = THREE.LatheGeometry.new(tank_pts, 24)
          tank = THREE.Mesh.new(
              tank_geo,
              THREE.MeshStandardMaterial.new({
                  "color": 0xdc6b0a, "roughness": 0.4,
                  "flatShading": True,
              }),
          )
          tank.position.set(0.1, 0.85, 0)
          tank.castShadow = True
          tank.name = "tank"
          g.add(tank)

          # Headlight — sphere with emissive glow
          headlight = THREE.Mesh.new(
              THREE.SphereGeometry.new(0.12, 16, 12),
              THREE.MeshStandardMaterial.new({
                  "color": 0xffd66b, "roughness": 0.25,
                  "emissive": 0xffae3a, "emissiveIntensity": 2.4,
                  "flatShading": True,
              }),
          )
          headlight.position.set(0.78, 0.85, 0)
          headlight.castShadow = True
          headlight.name = "headlight"
          g.add(headlight)

          # Wheels — lathed tires (PART 256.3)
          for i, x in enumerate((0.55, -0.55)):
              wheel_geo = MT_hardsurface.createLathedTireGeometry({
                  "outerR": 0.25, "innerR": 0.16, "width": 0.16,
                  "treadDepth": 0.008, "sidewallStyle": "chunky",
              })
              wheel = THREE.Mesh.new(
                  wheel_geo,
                  THREE.MeshStandardMaterial.new({
                      "color": 0x1a1a1e, "roughness": 0.95,
                      "flatShading": True,
                  }),
              )
              wheel.position.set(x, 0.25, 0)
              wheel.rotation.x = math.pi / 2  # axis along Z
              wheel.castShadow = True
              wheel.receiveShadow = True
              wheel.name = f"wheel_{i}"
              g.add(wheel)

          # Frame bar — tapered tube
          frame_pts = [[-0.4, 0.3, 0], [0, 0.35, 0], [0.4, 0.3, 0]]
          frame_geo = MT_hardsurface.createSweptTube(
              frame_pts, {"radius": 0.025, "segments": 32, "twist": False},
          )
          frame = THREE.Mesh.new(
              frame_geo,
              THREE.MeshStandardMaterial.new({
                  "color": 0xc0c0c0, "roughness": 0.3, "metalness": 0.85,
                  "flatShading": True,
              }),
          )
          frame.castShadow = True
          frame.name = "frame"
          g.add(frame)

          # Saddle — extruded 2D shape with rounded top
          saddle_shape = THREE.Shape.new()

PART 277 — IMAGE-DRIVEN ARTIST-FIRST GEOMETRY (PYTHON FORM)
(amends Image_To_Ts.txt PART 179)
──────────────────────────────────────────────

For image-driven factories, the "Hierarchy of Fidelity" rule
(PART 260) applies with one image-specific addition: the
reference image is the GROUND TRUTH. If the image shows a curved
fairing, the Python factory must produce a curved fairing — a
box that approximates the silhouette is a Hierarchy of Fidelity
violation even if the box "looks fine" from most angles.

Image-driven factories should follow this discipline:

  1. Read the silhouette first (PART 221.1). The 4-angle silhouette
     test (PART 248.1) is the gate — if the model doesn't match
     the reference image's silhouette, the IoU (PART 254) is
     below 0.80 and the retry loop kicks in (PART 254.1).

  2. Preserve compound contours (PART 260 rule 2). A body+head
     that the image shows as a single mass should be a single
     SDF-merged mesh (PART 250), not two separate primitives.

  3. Match the material's tactile quality. The image's PBR cues
     (specular highlights, roughness gradient) drive the
     material's `roughness` / `metalness` / `emissive` values.
     PART 275.5 (color sampling helper) reads the image's
     top-6 dominant colors; the AI's job is to set the PBR
     fields to match.

  4. Match the mechanical skeleton. The image's mechanical
     details (joints, hinges, springs) become Mesh primitives.
     Don't skip them in the name of "low-poly simplification".

  5. Minify last. After steps 1-4 pass, the AI can simplify
     or minify. Code minification is the LAST step.

  Rule 167.1.1 Form Preservation Mandate: when porting an
  image-driven TS factory to Python, the form must be preserved
  exactly. Don't replace ExtrudeGeometry fairings with
  BoxGeometry (it'll look like a flat slab) just because
  BoxGeometry is shorter. The reference image is the source
  of truth; the form is the language.

PART 278 — IMAGE-DRIVEN ARCHITECTURAL PIPELINE (PYTHON FORM)
(amends Image_To_Ts.txt PART 190-199)
──────────────────────────────────────────────

Image-driven architectural factories (buildings, interiors,
landscapes) follow the same 6-pitfall + 7-constructor pattern
as the prompt-driven path (PART 270-274), but the design source
is the reference image instead of the user's text prompt.

Key image-driven architectural idioms:

  - Wall decomposition: `MT_architectural.createWallWithApertures`
    takes a list of apertures (door / window / arch) that you
    derive from the image's facade. Python:
        wall_geo = MT_architectural.createWallWithApertures({
            "width": 4.0, "height": 2.8, "thickness": 0.15,
            "apertures": [
                {"type": "door", "x": 0.5, "width": 0.9, "height": 2.1},
                {"type": "window", "x": 1.8, "width": 0.8, "height": 0.8},
                {"type": "window", "x": 2.9, "width": 0.8, "height": 0.8},
            ],
        })

  - Roof pitch: derived from the image's roof angle. Python:
        roof_geo = MT_architectural.createPitchedGableRoof({
            "width": 4.3, "length": 4.3, "pitch": 30,
            "tileRows": 8,
        })

  - Window placement: from the image, declare each window's
    (x, y) position on the wall, its width, and its height. The
    aperture system handles the cutout via Shape.holes (no CSG
    needed).

  - Color sampling: use `lblSpec.helpers.sampleImagePalette(
    ref_img, n=6)` (PART 275.5) to extract the top-6 colors
    from the image, then map them to the 9-key architectural
    palette (PART 274).

  - IoU check: for architectural image-driven factories, the
    silhouette IoU is the validation gate (PART 254). Aim for
    IoU >= 0.80; below that, the renderer's auto-scaler
    enlarges the model by 10% and retries.

PART 279 — IMAGE-DRIVEN FLOATING-PARTS FIX (PYTHON FORM)
(amends Image_To_Ts.txt PART 250-254)
──────────────────────────────────────────────

For image-driven Python factories, the 5 floating-parts rules
(PART 250-254) apply identically. PART 279 is the Python form
with image-driven examples.

  PART 250 (SDF + MarchingCubes) — Use MT_core.sdfUnion when
  the image shows a single mass that the AI would otherwise
  build from 3+ separate primitives. Common in image-driven
  work: a body+head+neck that the image shows as one mass.

  PART 251 (Pivot offsets) — Derive from bbox (PART 251.1
  above). Image-driven factories are especially prone to
  eyeballed magic numbers because the AI "sees" the proportions
  in the image but doesn't always translate them to factory
  coordinates correctly.

  PART 252 (Style lock) — Set `meta.style` based on the
  image's aesthetic. Most image-driven factories target
  `chunky-mascot` or `flat-low-poly`. The renderer's
  lookDevLights() factory (PART 187) auto-applies the
  flatShading + outline + NoToneMapping rules.

  PART 253 (Loft limbs) — Use `MT_core.loft` for any tapered
  limb. Image-driven factories sometimes stack cylinders
  because the limb is "small in the image and the AI doesn't
  notice the segmented look". The IoU check (PART 254)
  catches this — segmented limbs produce visible Z-fight
  patterns in the silhouette that drop the IoU below 0.80.

  PART 254 (IoU check) — Run on every image-driven factory.
  The `lblSpec.helpers.compareToReference(g, ref_img)` call
  is mandatory for image-driven mode. See PART 254.1 above
  for the full Python form including the retry-on-low-IoU
  loop.

  279.1 — IMAGE-DRIVEN RETRY LOOP (PYTHON)
    For image-driven factories, the retry loop is the most
    important part of PART 254. When the IoU is below 0.80,
    the factory has 3 retry options:
      (a) Scale up by 10% (PART 254 Python form)
      (b) Adjust proportions of the major volumes
      (c) Re-sample the silhouette and rebuild

    The renderer's lblSpec.helpers.compareToReference() returns
    not just the IoU but a diff map that highlights the
    misaligned regions. Use it to decide which retry to apply:
        iou, diff_map = lblSpec.helpers.compareToReference(g, ref_img)
        if iou < 0.80:
            # Find the largest misaligned region
            if "head" in diff_map["misaligned_regions"]:
                # Re-scale the head
                head_pivot.scale.set(1.1, 1.1, 1.1)
            elif "limbs" in diff_map["misaligned_regions"]:
                # Re-loft the limbs with a thicker profile
                ...

    The retry loop runs up to 3 times; if all 3 retries fail
    to reach 0.80, the factory returns the best variant with
    a warning to the validator log.

PART 280 — IMAGE-DRIVEN STYLE-AGNOSTICISM (PYTHON FORM)
(amends Image_To_Ts.txt PART 38.22)
──────────────────────────────────────────────

Image-driven Python factories can target any of the 13 canonical
styles. The choice is driven by the image's aesthetic:

  Image aesthetic                  Recommended style
  ───────────────────────────────  ──────────────────────
  Chunky / blocky / low-poly       chunky-mascot
  Faceted / sharp edges            flat-low-poly
  Voxel / minecraft-like           voxel
  Smooth / rounded                 smooth-low-poly
  Realistic / scanned              pbr-realistic
  Photographed / photo-scanned     photogrammetry
  Anime / cartoon                  chibi / anime-cel
  ...                              ...

  For each style, the renderer's lookDevLights() factory
  (PART 187 / 199.3 / 273) switches the lighting rig, the
  tone mapping, the post-processing pass, and the triangle
  budget guidance. The Python factory just sets meta.style
  and the renderer does the rest.

  280.1 — STYLE-DOWNGRADE FOR LOW-POLY SIMPLIFICATION
    A common image-driven use case: the user provides a
    high-poly reference image (a 4K photograph or a 50K-tri
    photogrammetry scan) but wants a chunky-mascot output.

    The Python factory can do this by:
      1. Sampling the high-poly image's color palette
         (PART 275.5) for material derivation.
      2. Using lbl.subdivide_for_highpoly (PART 240) on a
         low-poly base shape to get the high-poly surface.
      3. Using lbl.decimate_for_lowpoly (PART 241) to bring
         the tri count back down to the chunky target.
      4. Setting meta.style = "chunky-mascot" so the renderer
         applies the flatShading + outline + NoToneMapping rules.

    The result is a chunky 3D model that captures the high-poly
    image's proportions and colors but renders in the
    chunky-mascot aesthetic.

(extends Prompt_To_Py.txt PART 281 + 286)
──────────────────────────────────────────────

  Style A (Blueprint-Return) reaches for a SUBSET of the MT bundle
  — only the primitives that have a `lbl.*` wrapper. Use this when:

    - The model is small (≤ 500 lines of Python)

  via `from js import MT_*`. Use this when:

      organic, articulated joints)
    - The model is large (> 500 lines of Python)

    - All 12 MT.core helpers (PART 281)
    - All 9 MT.mesh helpers (PART 282)
    - All 13 MT.organic helpers (PART 283)
    - All 6 MT.materials helpers (PART 284)

    - The 7 cross-primitive shape generators (PART 287)
    - The 12 standalone primitives (PART 288)
    - The CS2 PBR profile (PART 289)
    - The advanced shaders (PART 290)
    - The declarative constraints (PART 291)
    - The rigging + sculpt enrichment (PART 292 + 293)

  Style B is the recommended path for image-driven Python
  factories whenever the reference image shows anything more
  complex than a primitive vocabulary can express — which is
  most real-world images.

  Style A vs. Style B decision rule (image-driven):
      Image shows only primitives (box, cylinder, sphere)
        → Style A (Blueprint-Return)
      Image shows ANY of:
        - curved fairings
        - sculpted organic shapes
        - articulated joints
        - non-primitive characters
        - skeletal subjects
        - skinned meshes
        - custom shaders
        - transmission / clearcoat / iridescence
        → Style B (Three.js Direct)

  The original v1.36 / v8.27 release only documented Style A for

  scooter example. PART 295 here makes the Style A / Style B
  boundary explicit for the MT bundle specifically.

       from js import lblSpec

PART 299 — DETERMINISM (IMAGE-DRIVEN FORM)
──────────────────────────────────────────────

  Image-driven factories that use procedural textures should
  derive the texture's seed from the image, not from a hard-coded
  constant. Use the image's hash as the seed:

       import hashlib
       def derive_seed_from_image(ref_img):
           # Use the image's hash as the mulberry32 seed
           img_data = ref_img.toDataURL().encode("utf-8")
           return int(hashlib.md5(img_data).hexdigest()[:8], 16)

       seed = derive_seed_from_image(ref_img)
       rng = mulberry32(seed)
       # procedural pattern is deterministic given this image

  This guarantees that the same reference image produces the
  same procedural pattern across runs.

       def create_model(ref_img=None, options=None):

           ref_img: the reference image (HTMLImageElement) when
                    image-driven mode is active; None for prompt-only.
           options: future per-load options (currently always None).

           if ref_img is not None:

  chunky-mascot output:

       async def image_to_chunky(ref_img, target_tris=3000):
           """Convert a high-poly reference image to a chunky model."""
           source_mesh = await import_source_mesh(ref_img)
           if source_mesh is None:
               return None
           # Subdivide if too low-poly
           if source_mesh.attributes["polygons"] < target_tris:
               source_mesh = lbl.subdivide_for_highpoly(
                   source_mesh, {"levels": 2},
               )
           # Decimate to the target tri count
           chunky = lbl.decimate_for_lowpoly(
               source_mesh, {"ratio": target_tris / source_mesh.attributes["polygons"]},
           )
           return chunky

PART 382-388 — 7 IMAGE-DRIVEN READING HELPERS (FULL FORM)
──────────────────────────────────────────────

  Each image-reading helper has its own PART here:

  PART 382 — sampleImagePalette(ref_img, n_colors)
      Returns: [{"name": "c0", "color": "#rrggbb",
                 "rgb": [r, g, b], "lab": [l, a, b],
                 "weight": 0..1, ...}, ...]
      Top-1 = dominant color (largest weight)
      The palette is sorted by weight, descending.
      n_colors default = 5.

  PART 383 — detectFeatures(ref_img)
      Returns: [{"name": "eye", "x": 0..1, "y": 0..1,
                 "strength": 0..1, "size": 0..1, ...}, ...]
      "name" is one of: eye, mouth, door, window, handle,
      wheel, head, body, leg, arm, antenna, fin, etc.
      "x"/"y" are normalized (0..1) within the image.
      "strength" is the detection confidence.
      "size" is the bounding box size (normalized).

  PART 384 — measureDimensions(ref_img)
      Returns: {"width": world_units, "height": world_units,
                "depth": world_units, "scale_factor": 1.0,
                "subject_bbox": [x0, y0, x1, y1]}
      The dimensions are in world units (default: meters).
      The subject_bbox is the bounding box of the detected

            g = build_model(ref_img)
            if ref_img:
                for attempt in range(3):
                    iou = lblSpec.helpers.compareToReference(g, ref_img)
                    if iou >= 0.80:
                        break
                    # Adjust and retry
                    if attempt == 0:
                        g.scale.set(1.1, 1.1, 1.1)
                    elif attempt == 1:
                        g.scale.set(0.9, 0.9, 0.9)
                    # attempt == 2: just return (last attempt)
                print(f"Final IoU: {iou}")
            return g

  PART 399 — MT.core.sdfUnion (IMAGE-DRIVEN FORM)
        # Image-driven blob merging:
        def create_image_blob(ref_img):
            features = lblSpec.helpers.detectFeatures(ref_img)
            # Each feature becomes an SDF sphere
            sdfs = []
            for f in features:
                world_pos = lblSpec.helpers.imageToWorld(
                    [f["x"], f["y"]], ref_img, [0, 0, 0], [0, 0, 1],
                )
                radius = f["size"] * 0.3
                sdfs.append(MT_core.sdfSphere(world_pos[:3], radius))
            # Merge all SDFs
            sdf = sdfs[0]
            for s in sdfs[1:]:
                sdf = MT_core.sdfUnion(sdf, s)
            return MT_core.sdfMarch(sdf, {"resolution": 64})

PART 431-440 — IMAGE-DRIVEN PYTHON ERROR REFERENCE
──────────────────────────────────────────────

  PART 431 — PYODIDE LOAD ERROR
        CAUSE: Pyodide failed to load (network issue, MIME type, etc.)
        FIX: Check that Pyodide CDN is reachable. Fall back to
             TS-only mode.

  PART 432 — FACTORY IMPORT ERROR
        CAUSE: Python syntax error in the factory file
        FIX: Validate the factory with `python -m py_compile`.

  PART 433 — FACTORY CALL ERROR
        CAUSE: Runtime error during create_model()
        FIX: Check the traceback. Most common: missing import,
             Pyodide idiom (Three.Group.new()), missing argument.

  PART 434 — IoU LOW ERROR
        CAUSE: Model doesn't match the reference image (IoU < 0.80)
        FIX: PART 254 retry loop (PART 392). Otherwise, regenerate
             the factory with a different seed.

  PART 435 — VALIDATION WARNING
        CAUSE: Missing detailInventory entries, low triShare, etc.
        FIX: Add detailInventory entries. Reduce triShare on lower-
             priority meshes.

  PART 436 — SHADER COMPILE ERROR
        CAUSE: Shader fails to compile (vertex/fragment mismatch)
        FIX: Use only standard materials (MeshStandardMaterial,
             MeshPhysicalMaterial). Avoid custom shaders.

  PART 437 — GEOMETRY INVALID ERROR
        CAUSE: NaN or Inf in geometry vertices (degenerate CSG)
        FIX: Reduce the CSG operands' complexity. Use lower
             marching cubes resolution.

  PART 438 — MATERIAL MISSING ERROR
        CAUSE: Material is undefined when assigned to a mesh
        FIX: Always define materials before assignment.

  PART 439 — TEXTURE LOAD ERROR
        CAUSE: External texture URL is unreachable
        FIX: Fall back to procedural textures. Or use base64-encoded
             texture data.

  PART 440 — ANIMATION LOOP ERROR
        CAUSE: tick() throws an exception (IndexError, ZeroDivision)
        FIX: Wrap tick() in try/except. Log errors to console.

        node_id = "ao"

        output: scalar

  PART 506 — emissive node
        node_id = "emissive"
        input: color
        output: color

  PART 507 — texture sample node
        node_id = "tex2D"
        input: sampler2D + uv + vec2
        output: color

  PART 508 — multiply node
        node_id = "multiply"
        input: color * color / scalar * scalar
        output: color / scalar

  PART 509 — mix node
        node_id = "mix"
        input: float (factor) + a + b
        output: same as a, b

  PART 510 — power node
        node_id = "power"
        input: float (base), float (exponent)

PART 581 — EXAMPLE 1: IMAGE-DRIVEN LOW-POLY CHARACTER (FULL)

  """
  chunky_character.py — image-driven Style B factory.
  Builds a chunky-mascot character from a reference image.

  Usage:
    - Save as public/models/chunky_character.py
    - Renderer auto-discovers and registers it
    - Drop a reference image on the page to use it
    - Or use without an image for default character
  """
  from js import MT_core, MT_materials, MT_advanced, MT_lookdev, THREE, lblSpec, lbl
  import math

  def create_model(ref_img=None, options=None):
      g = THREE.Group.new()
      g.name = "Chunky Character"

      # ── Palette derivation ──
      palette = (
          sample_image_palette(ref_img, n_colors=4) if ref_img
          else DEFAULT_PALETTE
      )
      lbl.define_palette({p["name"]: p for p in palette})

      # ── Materials ──
      shell = THREE.MeshStandardMaterial.new({
          "color": 0xcc4444, "roughness": 0.7, "metalness": 0.05,
          "flatShading": True,
      })
      accent = THREE.MeshStandardMaterial.new({
          "color": 0x4a6fa5, "roughness": 0.5, "metalness": 0.1,
          "flatShading": True,
      })

      # ── Body (SDF merged) ──
      sdf = MT_core.sdfUnion(
          MT_core.sdfSphere([0, 0.4, 0], 0.3),
          MT_core.sdfCapsule([0, 0.0, 0], [0, 0.3, 0], 0.2),
      )
      body_geo = MT_core.sdfMarch(sdf, {"resolution": 64})
      body = THREE.Mesh.new(body_geo, shell)
      body.castShadow = True
      body.name = "body"
      g.add(body)

      # ── Head, eyes, antenna ──
      head = THREE.Mesh.new(
          THREE.BoxGeometry.new(0.4, 0.35, 0.4), accent,
      )
      head.position.y = 0.75
      head.castShadow = True
      head.name = "head"
      g.add(head)
      for i, x in enumerate((-0.08, 0.08)):
          eye = THREE.Mesh.new(
              THREE.SphereGeometry.new(0.05, 8, 6),
              THREE.MeshStandardMaterial.new({
                  "color": 0xffffff,
                  "emissive": 0xaef5ff, "emissiveIntensity": 1.5,
              }),
          )
          eye.position.set(x, 0.78, 0.21)
          eye.name = f"eye_{i}"
          g.add(eye)

      # ── Arms (lofted) ──
      arm_profile = [{"t": 0.0, "radius": 0.07},
                     {"t": 0.5, "radius": 0.05},
                     {"t": 1.0, "radius": 0.04}]
      arm_geo = MT_core.loft(arm_profile, {"radial": 8})
      for side in (-1, 1):
          arm = THREE.Mesh.new(arm_geo, shell)
          arm.position.set(side * 0.25, 0.35, 0)
          arm.castShadow = True
          arm.name = f"arm_{side}"
          g.add(arm)

      # ── Legs (lofted) ──
      leg_profile = [{"t": 0.0, "radius": 0.08},
                     {"t": 0.5, "radius": 0.06},
                     {"t": 1.0, "radius": 0.05}]
      leg_geo = MT_core.loft(leg_profile, {"radial": 8})
      for side in (-1, 1):
          leg = THREE.Mesh.new(leg_geo, shell)
          leg.position.set(side * 0.12, -0.4, 0)
          leg.castShadow = True
          leg.name = f"leg_{side}"
          g.add(leg)

      # ── sculptRuntime ──
      g.userData.sculptRuntime = {
          "nodes": {n.name: n for n in g.children if n.name},
          "meshes": {n.name: n for n in g.children
                     if n.name and hasattr(n, "geometry")},
          "detailInventory": [
              {"id": "body", "region": "torso", "kind": "feature",
               "priority": "high", "reviewThreshold": 0.7},
              {"id": "head", "region": "head", "kind": "feature",
               "priority": "high", "reviewThreshold": 0.7},
              {"id": "eye_0", "region": "face", "kind": "feature",
               "priority": "high", "reviewThreshold": 0.5},
              {"id": "eye_1", "region": "face", "kind": "feature",
               "priority": "high", "reviewThreshold": 0.5},
              {"id": "arm_-1", "region": "limb", "kind": "feature",
               "priority": "high", "reviewThreshold": 0.6},
              {"id": "arm_1", "region": "limb", "kind": "feature",
               "priority": "high", "reviewThreshold": 0.6},
              {"id": "leg_-1", "region": "limb", "kind": "feature",
               "priority": "high", "reviewThreshold": 0.6},
              {"id": "leg_1", "region": "limb", "kind": "feature",
               "priority": "high", "reviewThreshold": 0.6},
          ],
      }
      g.userData.meta = {
          "style": "chunky-mascot",
          "category": "character",
          "proportions": {"W_over_H": 0.8, "fill": 0.78},
      }

      # ── IoU check (image-driven only) ──
      if ref_img:
          iou = lblSpec.helpers.compareToReference(g, ref_img)
          if iou < 0.80:
              g.scale.set(1.1, 1.1, 1.1)
      return g

  DEFAULT_PALETTE = [
      {"name": "shell", "color": "#cc4444",
       "roughness": 0.7, "metalness": 0.05},
      {"name": "accent", "color": "#4a6fa5",
       "roughness": 0.5, "metalness": 0.1},
      {"name": "glow", "color": "#ffaa00",
       "emissive": "#ff7700", "emissiveIntensity": 2.0,
       "roughness": 0.3},
  ]

  def sample_image_palette(ref_img, n_colors=5):
      """Sample dominant colors from the reference image."""
      return lblSpec.helpers.sampleImagePalette(ref_img, n_colors=n_colors)

  """

  """
  from js import MT_core, MT_materials, MT_hardsurface, MT_lookdev, THREE, lblSpec, lbl
  import math

      g = THREE.Group.new()

          "color": 0xcc4444, "roughness": 0.4, "metalness": 0.3,

          "color": 0x1a1a1e, "roughness": 0.95, "metalness": 0.0,

      body.position.set(0, 0.3, 0)
      body.castShadow = True
      body.receiveShadow = True

      # Cabin
      cabin_shape = THREE.Shape.new()
      cabin_shape.moveTo(-0.6, 0)
      cabin_shape.lineTo(0.5, 0)
      cabin_shape.lineTo(0.4, 0.3)
      cabin_shape.lineTo(-0.5, 0.3)

      glass_mesh = THREE.Mesh.new(glass_geo, glass)
      glass_mesh.position.set(-0.05, 0.85, 0)
      glass_mesh.name = "windows"
      g.add(glass_mesh)

      # Wheels (4 lathed)

          [THREE.Vector2.new(0.15, 0),
           THREE.Vector2.new(0.18, 0),
           THREE.Vector2.new(0.18, 0.13),
           THREE.Vector2.new(0.15, 0.13),
           THREE.Vector2.new(0.15, 0)],
          16,
      )
      wheel_positions = [
          (-0.7, 0.18, 0.4),
          (-0.7, 0.18, -0.4),
          (0.7, 0.18, 0.4),
          (0.7, 0.18, -0.4),
      ]
      for i, (x, y, z) in enumerate(wheel_positions):
          wheel = THREE.Mesh.new(wheel_geo, tire)
          wheel.position.set(x, y, z)
          wheel.castShadow = True
          wheel.name = f"wheel_{i}"
          g.add(wheel)

      for i, x in enumerate((0.95, 0.95)):

              THREE.MeshStandardMaterial.new({
                  "color": 0xffffaa,
                  "emissive": 0xffffaa,
                  "emissiveIntensity": 2.0,
              }),
          )

          head.name = f"headlight_{i}"
          g.add(head)

      g.userData.sculptRuntime = {
          "nodes": {n.name: n for n in g.children if n.name},
          "meshes": {n.name: n for n in g.children
                     if n.name and hasattr(n, "geometry")},
          "detailInventory": [
              {"id": "body", "region": "chassis", "kind": "feature",
               "priority": "high", "reviewThreshold": 0.8},
              {"id": "cabin", "region": "chassis", "kind": "feature",
               "priority": "high", "reviewThreshold": 0.7},
              {"id": "windows", "region": "chassis", "kind": "feature",
               "priority": "high", "reviewThreshold": 0.6},
              {"id": "wheel_0", "region": "running_gear", "kind": "feature",
               "priority": "high", "reviewThreshold": 0.8},
              {"id": "wheel_1", "region": "running_gear", "kind": "feature",
               "priority": "high", "reviewThreshold": 0.8},
              {"id": "wheel_2", "region": "running_gear", "kind": "feature",
               "priority": "high", "reviewThreshold": 0.8},
              {"id": "wheel_3", "region": "running_gear", "kind": "feature",
               "priority": "high", "reviewThreshold": 0.8},
          ],
      }

PART 621-700 — v1.36 / v8.27 IMAGE-DRIVEN PYTHON FULL SPEC BODY
================================================================================

This section contains the full Image_To_Py.txt spec body, in the
same format as PART 223-290 in Prompt_To_Py.txt. Each PART covers

────────────────────────────────────────────────────────────────────────
PART 621 — IMAGE READING PATTERN (FULL FORM)
──────────────────────────────────────────────

  The 5-step image reading pattern:

  1. LOOK — survey the image as a whole. Note the dominant
     subjects, the silhouette, the lighting, the overall mood.
  2. SHAPE — identify the major shapes. Are they simple
     primitives? Curved fairings? Sculpted organic?
  3. COLOR — sample the dominant colors. Note the saturation,
     the value range, the metallic cues.
  4. MEASURE — estimate the proportions. How tall is it? How
     wide? How deep? Where are the joints?
  5. STYLE — assess the style hint. Is it matte? Glossy?
     Iridescent? Wireframe? Photogrammetry?

  Output: a structured plan (in g.userData.meta and the
  sculptRuntime contract) that drives the build.

────────────────────────────────────────────────────────────────────────
PART 622 — IMAGE-DRIVEN 6-PRIMITIVE VOCABULARY (FULL FORM)
──────────────────────────────────────────────

  Image-driven factories reach for these 6 primitives most often:

  1. BOX — for image-aligned structural parts (walls, body, head)
  2. SPHERE — for image-aligned round shapes (eyes, lights, fruit)
  3. CYLINDER — for image-aligned cylindrical parts (limbs, towers)
  4. CONE — for image-aligned tapering parts (antennas, spires)
  5. CAPSULE — for image-aligned organic parts (body, torso)
  6. ICOSAHEDRON — for image-aligned faceted parts (rocks, gems)

────────────────────────────────────────────────────────────────────────
PART 623 — IMAGE-DRIVEN SDF + MARCH (FULL FORM)
──────────────────────────────────────────────

  Use SDF + Marching Cubes for:
    - Image-aligned organic merging (torso + head as one mesh)
    - Image-aligned boolean shapes (subtract eye sockets from head)
    - Image-aligned continuous surfaces (no visible seams)

  Trade-offs:
    - PRO: watertight, no gaps, perfect for chunky-mascot
    - CON: slower than MT-mesh primitives, higher tri count

  Pattern:
    sdf = MT_core.sdfUnion(sdf_a, sdf_b)
    geo = MT_core.sdfMarch(sdf, {"resolution": 64})

────────────────────────────────────────────────────────────────────────
PART 624 — IMAGE-DRIVEN LOFT (FULL FORM)
──────────────────────────────────────────────

  Use Loft for:
    - Image-aligned tapered limbs (arms, legs, antennae)
    - Image-aligned organic tapering (snake, vine, tentacle)
    - Image-aligned curved surfaces (water flow, hair)

  Pattern:
    profile = [
        {"t": 0.0, "radius": 0.07},  # shoulder
        {"t": 0.5, "radius": 0.05},  # elbow
        {"t": 1.0, "radius": 0.04},  # wrist
    ]
    geo = MT_core.loft(profile, {"radial": 8})

────────────────────────────────────────────────────────────────────────
PART 625 — IMAGE-DRIVEN EXTRUDE (FULL FORM)
──────────────────────────────────────────────

  Use ExtrudeGeometry for:
    - Image-aligned panels (vehicle body, wall, sword blade)
    - Image-aligned shapes with depth (2D silhouette → 3D)

  Pattern:
    shape = THREE.Shape.new()
    shape.moveTo(-1.0, 0)
    shape.lineTo(1.0, 0)
    shape.bezierCurveTo(1.05, 0.2, 1.0, 0.45, 0.7, 0.5)
    shape.lineTo(-0.7, 0.5)
    shape.closePath()
    geo = THREE.ExtrudeGeometry.new(shape, {
        "depth": 0.8, "bevelEnabled": True,
        "bevelSize": 0.04, "bevelThickness": 0.04,
    })

────────────────────────────────────────────────────────────────────────
PART 626 — IMAGE-DRIVEN LATHE (FULL FORM)
──────────────────────────────────────────────

  Use LatheGeometry for:
    - Image-aligned rotational shapes (wheel, vase, column)
    - Image-aligned bottles, urns, hourglasses

  Pattern:
    pts = [
        THREE.Vector2.new(0.15, 0),
        THREE.Vector2.new(0.18, 0),
        THREE.Vector2.new(0.18, 0.13),
        THREE.Vector2.new(0.15, 0.13),
        THREE.Vector2.new(0.15, 0),
    ]
    geo = THREE.LatheGeometry.new(pts, 16)

────────────────────────────────────────────────────────────────────────
PART 627 — IMAGE-DRIVEN CASTSHADOW + RECEIVESHADOW
──────────────────────────────────────────────

  Image-driven factories should always set:

    mesh.castShadow = True
    mesh.receiveShadow = True  # for floor parts

  Default: all meshes cast shadows except light sources, particle
  systems, and transparent meshes (which are configured to
  castShadow = False for performance).

────────────────────────────────────────────────────────────────────────
PART 628 — IMAGE-DRIVEN MATERIAL DICTIONARY
──────────────────────────────────────────────

  Image-driven factories should use these materials in order of
  preference:

    1. MeshStandardMaterial (most cases)
    2. MeshPhysicalMaterial (transmission, iridescence, clearcoat)
    3. MeshLambertMaterial (no PBR needed)
    4. MeshBasicMaterial (no lighting, debug)
    5. ShaderMaterial (custom VFX, rare)

  Avoid: MeshPhongMaterial, MeshToonMaterial (deprecated)

────────────────────────────────────────────────────────────────────────
PART 629 — IMAGE-DRIVEN 8 COMMON SHAPES
──────────────────────────────────────────────

  The 8 shapes that appear in most image-driven factories:

    1. Body (capsule + sdfUnion)
    2. Head (box)
    3. Eyes (2 spheres)
    4. Limbs (4 lofted limbs)
    5. Antenna (cylinder + sphere tip)
    6. Wheels (lathe geometry, 4 instances)
    7. Windows (transmission glass)
    8. Lights (emissive spheres)

────────────────────────────────────────────────────────────────────────
PART 630 — IMAGE-DRIVEN 5 CATEGORIES OF DETAIL
──────────────────────────────────────────────

  Image-driven factories should distribute detail across these
  5 categories:

    1. PRIMITIVE features (eyes, mouth, doors) — high priority
    2. STRUCTURAL features (walls, beams) — medium priority
    3. SECONDARY features (rivets, decals) — medium priority
    4. AMBIENT features (smoke, particles) — low priority
    5. ENVIRONMENTAL features (ground, sky) — low priority

  Apply 60/25/15 to PRIORITY/MEDIUM/LOW.

PART 643 — IMAGE-DRIVEN PYTHON PERFORMANCE TARGETS
──────────────────────────────────────────────

  Image-driven factories should hit these targets:

    - Pyodide load: 2-5s first time, <100ms cached
    - Factory load: <50ms (after Pyodide loaded)
    - Factory execution: <500ms (for typical 5000-tri model)
    - IoU check: <200ms
    - Total pipeline: <2s typical, <5s worst case

  If a factory exceeds these targets:
    - Reduce tri count (use Decimate)
    - Reduce shader complexity (use simpler materials)
    - Reduce draw calls (use Instancing)
    - Cache expensive operations (lbl.define_palette, etc.)

PART 901 — IMAGE-DRIVEN PYTHON WORKFLOW DIAGRAM
──────────────────────────────────────────────

  The complete image-driven Python workflow:

       [User drops image]
            ↓
       [Renderer loads image] → lblSpec.helpers.measureDimensions
            ↓
       [AI analyzes image] → detectSubject, sampleImagePalette
            ↓
       [AI emits factory .py]
            ↓
       [Pyodide loads factory]
            ↓
       [create_model(ref_img) called]
            ↓
       [Factory builds THREE.Group]
            ↓
       [IoU check] → if low, retry
            ↓
       [sculptRuntime + meta set]
            ↓
       [scene.add(group)]
            ↓
       [MT_lookdev.applyLookDev]
            ↓
       [userData.tick registered]
            ↓
       [Main render loop]
