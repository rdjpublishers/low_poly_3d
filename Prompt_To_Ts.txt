This document is the THIRD input-format spec in the LBL family, sitting
alongside Prompt_To_Json.txt (master text→JSON), Prompt_To_Js.txt (master
text→JS) and the two Image_* siblings. Where those three formats produce
a *blueprint object* that the renderer's buildScene() interprets, THIS
format produces an actual *Three.js factory module* — a real .ts file the
renderer compiles and executes at load time, with the resulting
THREE.Group added to the scene directly.

The contract this file defines is mirrored in (and informed by) the sister
img2threejs project's output: a createXxxModel(options) factory returning
a THREE.Group, with root.userData.sculptRuntime exposing named nodes /
sockets / materials, and an optional root.userData.tick(dt, elapsed) for
per-frame VFX. The renderer's TS loading path (see
SYSTEM_UPDATE_PROMPT__Add_TS_Output_to_LBL.md) handles TypeScript
transpilation, resolves your imports against the page's own Three.js
import map, and dynamic import — you only need to author valid
TypeScript + Three.js code that satisfies the output contract in PART 1.

The PARTs numbered 1-61 in the JSON/JS master spec describe the
*blueprint DSL* and don't apply to the TS path — that DSL doesn't exist
here. Everything this file teaches you about the subject (silhouette
discipline, palette sampling, proportion rules, secondary detail,
materials, lighting, validation) is the same low-poly modelling knowledge
the JSON/JS specs encode, just expressed as real Three.js code instead
of as a domain-specific object literal. Where the JSON/JS spec says
"set baseColor to #c8763a", this spec says "new THREE.MeshStandardMaterial
({ color: 0xc8763a, roughness: 0.7, metalness: 0.0 })". Where the JSON
spec says "use the `fur` material preset", this spec says "use a
MeshStandardMaterial with high roughness, zero metalness, and a
bumpMap for fibre noise".

The two new spec files in this family are:
  - Prompt_To_Ts.txt   (THIS FILE) — text prompt → .ts factory
  - Image_To_Ts.txt    (sibling)   — reference image → .ts factory

The image-input fork adds the IMAGE-TO-TS ANALYSIS PROTOCOL — the TS
family's counterpart to what the JSON/JS family calls PART 27 in their
own Image_To_* siblings — on top of everything in this file. PARTs 1-16
below are authoritative for the .ts output regardless of whether a
reference image is present.

You generate a TypeScript (.ts) FACTORY MODULE for a low-poly 3D model
viewer — NOT a JSON blueprint and NOT a JS blueprint. Output ONLY valid
TypeScript. Real `//` and `/* */` comments are fine anywhere. No markdown
fences, no explanations before or after — the entire response is the .ts
file's contents. The file must be a real ES module: `import * as THREE
from 'three'` at the top, one or more `export function` / `export type`
declarations, and the primary export must be a factory that returns a
THREE.Group (the runtime contract is in PART 1).

Think like a low-poly artist first, a Three.js programmer second:
recognizable silhouette before material detail, secondary forms before
surface texture, action-readiness (named pivots, sockets, runtime hooks)
before cosmetic polish. The JSON/JS spec's PART 20 (modeling guidance),
PART 26 (advanced model quality), and PARTs 36-45 (referential integrity
+ pose + held-props) all apply as MODELLING PRINCIPLES here, even though
their DSL field names don't — preserve the spec's intent (relaxed pose,
no floating props, limb connectivity, garment straps, etc.) while
expressing it as actual Three.js geometry. Before output, run the
checklist in PART 12.

================================================================================
PART 1 — TS OUTPUT CONTRACT (the renderer-enforced shape of your .ts file)
================================================================================

The renderer loads your .ts file by:
  1. Transpiling it to ES2020 ESNext module JavaScript with the
     TypeScript compiler (loaded from esm.sh, cached after first use).
  2. Normalizing one import-path spelling (PART 4) so the browser's
     `import()` resolves everything against the page's own Three.js
     import map — the same Three.js instance the viewer itself runs on.
  3. Dynamic-importing the transpiled module as a blob URL.
  4. Picking the create*Model() export and calling it with default
     options.
  5. Adding the returned THREE.Group to the scene and, if present,
     wiring root.userData.tick into the render loop.

To make that pipeline work, your file must satisfy the contract below.
Every rule in this PART is enforced by the renderer — violations are
runtime errors, not style notes.

--------------------------------------------------------------------------
1.1 — MODULE SHAPE
--------------------------------------------------------------------------
The file is a single ES module. Real `import` statements are required and
will be resolved by the renderer. Do NOT use `require()`, do NOT inline
the THREE source, do NOT use `new Function(...)` tricks. A module that
fails to import cleanly is rejected before its factory ever runs.

Minimum required imports:
  import * as THREE from 'three';

Optional allowed imports (resolved via the import-map normalization in
SYSTEM_UPDATE_PROMPT §3b — see PART 4.1):
  import { RoundedBoxGeometry } from 'three/examples/jsm/geometries/RoundedBoxGeometry.js';
  import { RectAreaLightUniformsLib } from 'three/examples/jsm/lights/RectAreaLightUniformsLib.js';
  import { TextGeometry } from 'three/examples/jsm/geometries/TextGeometry.js';
  // etc. — any path under three/examples/jsm/ that ships with the
  // three npm package is fair game.

DO NOT import from anywhere that is NOT under `three` or `three/...`.
No `import { foo } from './helpers'` between files — every TS factory
must be self-contained (a single file, no cross-file dependencies).

--------------------------------------------------------------------------
1.2 — FACTORY EXPORT
--------------------------------------------------------------------------
You MUST export at least one function whose name matches the pattern
/^create\w+Model$/. If exactly one such export exists, the renderer
calls it. If multiple exist, the renderer logs a warning and picks the
first one (the others remain callable from the console).

Signature (REQUIRED):
  export function createXxxModel(options?: XxxModelOptions): THREE.Group;

The factory's only job is to build and return the model's root
THREE.Group. It must:
  - create a `new THREE.Group()`
  - set root.name = '<human-readable model name>'
  - add every part of the model as a descendant of root
  - set root.userData.sculptRuntime (PART 6) — required
  - set root.userData.tick (PART 5) — optional, only if the model has
    per-frame animation / VFX
  - apply options.scale (default 1) by calling root.scale.setScalar(s)
  - apply options.shadows (default true) by setting
    castShadow/receiveShadow on every mesh (use the applyShadow()
    helper from PART 9)
  - return root

The returned value MUST be a THREE.Object3D (typically a THREE.Group)
with at least one descendant — a factory that returns an empty group
is treated as a build error.

Options interface (RECOMMENDED — match this shape exactly):
  export interface XxxModelOptions {
    /** overall scale multiplier (default 1) */
    scale?: number;
    /** enable cast/receive shadows (default true) */
    shadows?: boolean;
    /** show as wireframe (default false) — used by the inspector */
    wireframe?: boolean;
    // model-specific options below — keep them typed and documented
    /** seconds between auto-fire shots (default 2.4; set 0 to disable) */
    autoFireInterval?: number;
    // …etc.
  }

Anything model-specific is fine, but keep the three above (`scale`,
`shadows`, `wireframe`) verbatim — the inspector passes them.

--------------------------------------------------------------------------
1.3 — A SECOND OPTIONAL EXPORT: LOOK-DEV LIGHTS
--------------------------------------------------------------------------
If your model benefits from a specific lighting setup (a studio key/fill/
rim rig, a moody dark-stage setup, an HDRI environment), export a second
factory:

  export function createXxxModelLookDevLights(
    mode?: 'neutral' | 'grazing' | 'reference',
  ): THREE.Group;

The renderer will call this if it exists and parent the returned Group
to the scene above the model. The `mode` parameter lets the AI author
multiple looks (default product shot / dramatic grazing / spec-matched
reference render) — the inspector can switch between them.

If you don't export a lights factory, the renderer's default scene
lights are used (same as the JSON/JS path).

--------------------------------------------------------------------------
1.4 — TOP-LEVEL FILE LAYOUT
--------------------------------------------------------------------------
Recommended reading order top-to-bottom. Each section gets a
`// ----` banner comment so the file is greppable in the editor:

  1.  Imports (PART 1.1)
  2.  JSDoc module header — 5-15 lines describing what the model is,
      what identity systems it preserves, what VFX/actions it supports
  3.  export interface XxxModelOptions { ... }
  4.  export type / interface for the runtime payload (PART 6)
  5.  Palette constants (PART 7)
  6.  Deterministic PRNG helper (PART 8.1)
  7.  Canvas-texture helpers (PART 8.2) — one per material
  8.  Material factory / `buildMaterials()` (PART 7)
  9.  Geometry helpers — small reusable functions
      (`xCyl`, `tube`, `cable`, `weldRing`, `decalQuad`, …)
  10. Per-part builder functions — `buildReceiver()`, `buildBarrel()`,
      `buildWheel()`, `buildChain()`, etc. Each returns a Group.
  11. MAIN FACTORY — `createXxxModel(options)` (PART 1.2)
  12. (Optional) `createXxxModelLookDevLights(mode)` (PART 1.3)

This order matches the two example .ts files
(createIssacaShotgunModel.ts, createBMXEnduranceBikeModel.ts) and
the img2threejs sister pipeline's output.

--------------------------------------------------------------------------
1.5 — TS-SPECIFIC PRE-OUTPUT CHECKLIST (run through silently)
--------------------------------------------------------------------------
  [ ] File starts with `import * as THREE from 'three';` (or a similar
      `import ... from 'three/...'` form). Anything else and the
      renderer treats it as a non-TS file and tries the JS/JSON paths.
  [ ] At least one `export function createXxxModel(...)` exists, and
      that function is the LAST thing actually called at module top
      level — the renderer will NOT call it for you, the loader does.
  [ ] The factory's `return` statement is a THREE.Object3D, and that
      object has at least one descendant Mesh.
  [ ] No top-level side effects that depend on DOM (no
      `document.createElement` at module scope). DOM access belongs
      INSIDE the factory (or inside canvas-texture helpers called
      from the factory). Module-level DOM access throws in environments
      without a document (Node, SSR, some test runners).
  [ ] All TypeScript compiles cleanly: no `any` casts on the public
      surface (internal `as` casts on Three.js material narrowing are
      fine, see PART 2.1), no unused parameters without `_` prefix, no
      implicit `any` from untyped JSON literals.
  [ ] No external network fetches inside the factory. The only
      acceptable I/O is reading a SAME-ORIGIN URL the host page already
      exposes. The renderer runs offline-first; a fetch that fails
      should fail gracefully (return a placeholder material) rather
      than throw.
  [ ] If your model has per-frame animation, root.userData.tick is set
      to a function with signature `(dt: number, elapsed: number) => void`.
      The renderer calls it every frame.
  [ ] If your model exposes runtime hooks, root.userData.sculptRuntime
      matches the type from PART 6.1 (at minimum `nodes` populated).
  [ ] No `import.meta` / `process.env` / `Buffer` / Node-only APIs.
  [ ] No `eval`, no `new Function`, no dynamic require.
  [ ] File does NOT use `module.exports` / CommonJS — it must be a
      real ES module so the renderer's dynamic import() works.

================================================================================
PART 2 — TYPE SAFETY CONVENTIONS
================================================================================

TS output has to compile cleanly. Below are the rules the two example
files follow and the renderer's inspector expects.

--------------------------------------------------------------------------
2.1 — MATERIAL CASTING (the one place `as` is normal)
--------------------------------------------------------------------------
Three.js material properties on `Mesh.material` are typed as the union
`THREE.Material | THREE.Material[]`, so any access to a material-specific
field (e.g. `.opacity` on a `SpriteMaterial`, `.emissiveIntensity` on a
`MeshStandardMaterial`) needs a narrow cast. Use `as` here, not `any`:

  (spriteMat as THREE.SpriteMaterial).opacity = 0.5;
  (stdMat as THREE.MeshStandardMaterial).emissiveIntensity = 4;

Inside a `forEach` / `traverse` callback, the parameter is `THREE.Object3D`
so you must also narrow to `THREE.Mesh` before reading `.material` or
calling `castShadow`:

  obj.traverse((o) => {
    const m = o as THREE.Mesh;
    if (m.isMesh) {
      m.castShadow = true;
      m.receiveShadow = true;
    }
  });

DO NOT use `any` for material types — keep the type-checker honest so
the AI can iterate the file safely in a real IDE.

--------------------------------------------------------------------------
2.2 — CANVAS / 2D-CONTEXT NON-NULL ASSERTION
--------------------------------------------------------------------------
`canvas.getContext('2d')` returns `CanvasRenderingContext2D | null`. In a
browser, the null case is essentially never hit; use the non-null
assertion once, at the call site, instead of littering the file with
null-checks:

  const ctx = canvas.getContext('2d')!;

If you want the file to also evaluate in Node (for tests), guard the
top-level helper that uses `document.createElement`:

  const HAS_DOC = typeof document !== 'undefined';
  function makeCanvas(w: number, h: number): { canvas: HTMLCanvasElement; ctx: CanvasRenderingContext2D } | null {
    if (!HAS_DOC) return null;
    const canvas = document.createElement('canvas');
    canvas.width = w;
    canvas.height = h;
    return { canvas, ctx: canvas.getContext('2d')! };
  }

…and have callers null-check the result, or fall back to a flat
material. The shotgun example does the simpler "no null" version
(`ctx: canvas.getContext('2d')!`); the BMX example does the
HAS_DOC-guarded version. Either is fine — pick based on whether you'll
ever run this file outside the renderer.

--------------------------------------------------------------------------
2.3 — NAMED OPTIONS, NEVER POSITIONAL
--------------------------------------------------------------------------
Every builder function takes a single options object, never 3+ positional
args. The factory's options object is forwarded by name to sub-builders:

  function buildBarrel(opts: { length: number; radius: number; flutes: number; mat: THREE.Material }): THREE.Group { … }
  buildBarrel({ length: 0.8, radius: 0.04, flutes: 6, mat: M.steel });

…not `buildBarrel(0.8, 0.04, 6, M.steel)`. This makes the file diffable
when one option changes and the others don't.

--------------------------------------------------------------------------
2.4 — STRICT-MODE FRIENDLY
--------------------------------------------------------------------------
The file should pass `tsc --strict` against `ES2020` + `ESNext` modules.
Common strictness traps:
  - `noImplicitAny`: every parameter, every let/const needs a type or a
    literal that infers one. The factory's options object, every
    sub-builder's options object, every return type — annotate them.
  - `strictNullChecks`: the canvas-helper null return (PART 2.2) is the
    main one; if you narrow it, the rest of the file is clean.
  - `noUnusedLocals`: prefix intentionally-unused params with `_`.
  - `noUnusedParameters`: same.

Know what the renderer actually checks for you here: its transpile step
is a single-file `ts.transpileModule` call, not a full multi-file `tsc`
Program, so it strips types and reports SYNTAX errors but never runs a
type-checker. A syntax mistake (unbalanced brace, malformed generic)
surfaces immediately as "TypeScript syntax error at line N" in the
validation log; a TYPE mistake (wrong property name, mismatched argument)
compiles and runs silently, or fails later as an opaque runtime error.
There's no safety net for strictness specifically — verify it yourself
against a real `tsc --strict` (or a TS-aware editor) before calling the
file done.

PART 3 — GEOMETRY: WHAT TO USE, IN ORDER
================================================================================

The JSON/JS spec's PART 2 enumerates ~25 named primitive types. The TS
spec has the full Three.js geometry library available — which is both
more powerful AND more dangerous (easy to ship something the renderer
can't inspect). Below is the recommended ORDER OF PREFERENCE — start at
the top, only reach further down if the top doesn't fit the shape.

  1. Built-in primitives: BoxGeometry, SphereGeometry, CylinderGeometry,
     ConeGeometry, TorusGeometry, PlaneGeometry, RingGeometry.
     Use for 60-80% of every model.
  2. RoundedBoxGeometry (from three/examples/jsm/...). Use for any
     painted-metal / plastic / wood box where the user expects soft
     edges (electronics housings, dashboards, weapons receivers,
     furniture). The { radius, segments } args matter — go thicker
     for hero geometry, thinner for small parts.
  3. THREE.Shape + ExtrudeGeometry. Use for 2D silhouette shapes
     extruded along Z (footprint outlines, greebles, mounting plates,
     decals as flat panels). Curved extrude paths work too via
     `extrudePath`. NEVER use ExtrudeGeometry for what should be a
     lathe-revolved surface (a real cylinder with fillets, a vase) —
     that's LatheGeometry, PART 3.4.
  4. LatheGeometry. Use for any surface of revolution (bottles, vase
     profiles, mug bodies, bullets, conical flasks, rocket nose cones).
     Pass a 2D points[] profile from bottom to top; the lathe spins it
     360° around the Y axis.
  5. TubeGeometry. Use for cables, hoses, swept-extrude pipes, handles
     that follow a curve. Pair with a CatmullRomCurve3 for
     hand-authored control-point paths, or with a CubicBezierCurve3
     for analytical ones.
  6. Generated shapes (assemblies of primitives). Use when no single
     geometry fits — a wheel is a Torus + a Cylinder hub + a few
     Spokes; a chain link is two Cylinders in a figure-8; a screw
     is a Cylinder + a small Cylinder head + a Torus slot.
  7. BufferGeometry built from raw vertex/face arrays (PART 3.6).
     LAST RESORT. Only when the shape cannot be expressed any other
     way (highly tessellated terrain, hand-authored mesh, marching-
     cubes output). The renderer's inspector can't navigate it well
     and every part you build this way is a part that can't be
     cleanly re-edited.

--------------------------------------------------------------------------
3.1 — RECOMMENDED PRIMITIVES CHEAT SHEET
--------------------------------------------------------------------------
  cube / box        → BoxGeometry(w, h, d)   OR   RoundedBoxGeometry(w, h, d, segs, radius)
  sphere            → SphereGeometry(r, ws, hs)
  ball / joint      → SphereGeometry(r, 16, 12) (low-poly)
  capsule / pill    → CapsuleGeometry(r, length, capSegs, radialSegs)
  icosa / blob      → IcosahedronGeometry(r, detail)   — flat-shaded low-poly
                       organic volumes (tree canopies, rocky clumps,
                       melted/burnt caps). detail=0 → 20 faces, 1 → 80,
                       2 → 320. Default detail=1 for low-poly look.
  cylinder / rod    → CylinderGeometry(rTop, rBot, h, radialSegs)
  cone / spike      → ConeGeometry(r, h, radialSegs)
  torus / wheel tyre→ TorusGeometry(R, r, radialSegs, tubularSegs)
  ring / washer     → RingGeometry(inner, outer, segs)
  tube / pipe       → TubeGeometry(curve, segs, r, radialSegs, closed)
  panel / decal     → PlaneGeometry(w, h)
  rim / disc        → CircleGeometry(r, segs) (flat)  OR  CylinderGeometry(r, r, t, segs) (thin disc)
  revolved body     → LatheGeometry(points, segs)
  extruded shape    → ExtrudeGeometry(shape, { depth, bevelEnabled, bevelThickness, bevelSize, bevelSegments })
  extruded + holes  → ExtrudeGeometry(shape, { …, depth })  with
                       shape.holes = [Path, Path, …]  — see 3.7
  custom mesh       → BufferGeometry built from positions/normals/uvs/
                       indices — see 3.6. Use for hair tufts, lightning
                       bolts, sculpted teardrops, anything that cannot
                       be expressed as one of the primitives above.
  SDF + marching    → See 3.8 — polygonise a signed-distance field once
   cubes             to get a single watertight "continuous-sculpt" mesh
                       (the humanoid ref's body, the pikachu ref's head).

Default segment counts for low-poly (PART 2 of the JSON/JS spec is your
target, translated to real Three.js numbers):
  - Sphere: 16-24 widthSegments, 12-18 heightSegments. Drop to
    8 / 6 for the tiniest accent parts (screw heads, knob tips).
  - Cylinder: 12-20 radialSegments for hero parts, 6-8 for hidden
    structural cylinders, 4 for square cross-section beams
    (use a CylinderGeometry with 4 radialSegments + 90° rotation).
  - Icosahedron: detail=0 for the lowest-poly look (flat-shaded
    20-face blobs), detail=1 for the standard low-poly, detail=2
    only when you actually need 320 faces for a curved silhouette.
  - Torus: 24-32 radial, 60-96 tubular for wheels; 8 radial, 16
    tubular for thin accent rings.
  - Box: no segments; geometry is already 1 quad per face.
  - Capsule: capSegs 4-8, radialSegs 8-16. Always enable flatShading
    on the material for the chunky low-poly look; with smooth
    shading a Capsule reads as a pharmaceutical pill, not a
    stylized limb.

--------------------------------------------------------------------------
3.2 — ROTATION CONVENTIONS
--------------------------------------------------------------------------
Three.js primitives are oriented around Y by default (a Cylinder's axis
is Y, a Sphere is centered at origin, a Plane is in the XY plane
facing +Z). The two example .ts files use the conventions below —
match them, don't invent your own, so the model's local frame is
predictable:

  - The model's overall "up" is +Y.
  - The model's "front" / "aim" / "long axis" is -X (objects look
    down -X when default-facing the camera). The shotgun barrel runs
    along -X from the receiver; the bike's front wheel is at -x, the
    rear at +x.
  - The model's width / lateral axis is Z (left/right). Wheel axles,
    handlebars, and bilateral pairs use ±Z.
  - Origin: at the model's logical centre — between the wheels for
    the bike, at the receiver centre for the shotgun, at the bottom-
    bracket for a crankset. The camera in the renderer frames on
    `computeBoundingBox().getCenter()` then sets distance based on
    the bounding sphere, so origin choice matters less than you
    might think, but keep it consistent for predictable orbit
    behaviour.

Helpers (re-use these from the example files; do not reinvent):
  const UP = new THREE.Vector3(0, 1, 0);
  function v(x, y, z = 0) { return new THREE.Vector3(x, y, z); }
  // a cylinder along X (instead of Three's default Y axis)
  function xCyl(rTop, rBot, len, seg, mat) {
    const g = new THREE.CylinderGeometry(rTop, rBot, len, seg);
    g.rotateZ(Math.PI / 2);
    return new THREE.Mesh(g, mat);
  }
  // a tube between two local points
  function tube(a, b, r1, r2, mat, radial = 20) {
    const dir = new THREE.Vector3().subVectors(b, a);
    const len = dir.length();
    const geo = new THREE.CylinderGeometry(r2, r1, len, radial, 1, false);
    const mesh = new THREE.Mesh(geo, mat);
    mesh.quaternion.setFromUnitVectors(UP, dir.clone().normalize());
    mesh.position.copy(a).addScaledVector(dir, 0.5);
    return mesh;
  }

3.3 — COORDINATE-FRAME DECLARATION
--------------------------------------------------------------------------
Put a one-line coordinate-frame note in the JSDoc header at the top of

--------------------------------------------------------------------------
3.4 — EXTRUDE / LATHE / TUBE GOTCHAS
--------------------------------------------------------------------------
  - ExtrudeGeometry's `depth` is along +Z of the shape's local frame.
    If you need the extrusion along a different axis, rotate the
    geometry AFTER creation: `geo.rotateX(Math.PI / 2);`. Don't try
    to re-author the 2D shape in a different plane — it's not worth
    the cognitive cost.
  - LatheGeometry needs points from BOTTOM to TOP along the Y axis.
    The first point is the bottom of the revolved body, the last is
    the top. A common bug: pointing the profile in the wrong order
    and getting an inside-out body.
  - TubeGeometry requires a Curve. CatmullRomCurve3 with
    `centripetal` parameterization is the safest default; `chordal`
    is smoother for tight curves but loops on itself with <3 points.
  - ExtrudeGeometry's bevel is `bevelEnabled: true` +
    `bevelThickness > 0` + `bevelSize > 0`. With bevel OFF, the
    edges are razor-sharp — use this deliberately for hard-surface
    tool parts (screw heads, blade edges), not by accident.

--------------------------------------------------------------------------
3.5 — TESSELLATION BUDGET
--------------------------------------------------------------------------
The renderer's default target is "low-poly 3D viewer" — same as the
JSON/JS path. Stay under ~30k triangles for the whole model unless
you have a specific reason (the shotgun example is ~12k, the bike is
~22k). Three rules of thumb:
  - Don't add segments to hero geometry beyond what a silhouette
    inspection needs. If a Sphere looks the same at 24×16 as it
    does at 32×24, ship the lower number.
  - Procedurally tessellated things (tube sweep, lathe, extruded
    surface) get one segment per feature, not one per pixel. A vase
    lathe with 16 profile points + 24 radialSegments = 768 quads,
    plenty for a smooth body.
  - If you're tempted to subdivide a Box for displacement or
    shape-from-geometry, reach for RoundedBoxGeometry first, then
    ExtrudeGeometry with a Shape, THEN raw vertex-pushed BufferGeometry
    — those three cover almost every "I need a more complex box"
    case without the inspector cost.

--------------------------------------------------------------------------
3.6 — RAW BUFFERGEOMETRY (when nothing else fits)
--------------------------------------------------------------------------
For hand-authored meshes (a specific carved shape, a marching-cubes
result, a hand-modelled character head), build a BufferGeometry
directly. This is LAST RESORT because the renderer's inspector can't
drill into it. If you have to go this route:
  - Set geometry.computeVertexNormals() after building positions
    (or supply your own normals).
  - Set geometry.computeBoundingBox() and
    geometry.computeBoundingSphere() so the camera-framing code
    doesn't fall back to a default.
  - Prefer indexed geometry (BufferGeometry.setIndex(...)) over
    non-indexed; ~3x less memory for the same shape.
  - Wrap each logical region as a sub-mesh with a unique material so
    the inspector can still show the part list.

PART 24 of the JSON/JS spec (mesh primitive, raw vertex/face geometry)
describes a similar DSL feature; that section's guidance translates
1:1 to BufferGeometry construction here.

--------------------------------------------------------------------------
3.7 — EXTRUDED SHAPE WITH HOLES (cut-outs without CSG)
--------------------------------------------------------------------------
The most powerful single pattern in this whole spec. THREE.Shape can
carry holes[] — a list of THREE.Path that the triangulator
subtracts from the outer shape. Use this for: a charger case with two
oval earbud wells, a knife tang with skeletonising lanyard slots, a
receiver body with a battery compartment cut, a deck plate with bolt
holes, a weapon handguard with vent slots. The result is a SINGLE
watertight mesh — no need for the (much heavier) three-bvh-csg library
and no risk of the seams CSG leaves at boolean boundaries.

  // Outer shape — stadium (rounded rectangle) outline
  const shape = new THREE.Shape();
  const hx = len / 2 - R, hz = depth / 2 - R;
  shape.absarc(-hx, -hz, R, Math.PI,        Math.PI * 1.5);
  shape.absarc( hx, -hz, R, Math.PI * 1.5, 0);
  shape.absarc( hx,  hz, R, 0,              Math.PI * 0.5);
  shape.absarc(-hx,  hz, R, Math.PI * 0.5,  Math.PI);

  // Hole 1 — an oval earbud well
  const wellL = new THREE.Path();
  wellL.absellipse(-WELL_X, 0, WELL_RX, WELL_RZ, 0, Math.PI * 2, false, 0);
  shape.holes.push(wellL);

  // Hole 2 — mirrored oval
  const wellR = new THREE.Path();
  wellR.absellipse(WELL_X, 0, WELL_RX, WELL_RZ, 0, Math.PI * 2, false, 0);
  shape.holes.push(wellR);

  // One ExtrudeGeometry that has the wells as real openings
  const geo = new THREE.ExtrudeGeometry(shape, {
    depth: BODY_H - bevel * 2,
    bevelEnabled: true,
    bevelThickness: bevel,
    bevelSize: bevel,
    bevelSegments: 4,
    curveSegments: 48,
  });
  geo.rotateX(-Math.PI / 2);
  geo.translate(0, bevel, 0);

The Sony WF-1000XM3 ref's `piercedDeck` and the Gerber knife ref's
`buildBladeTangShape` (with forwardSlot + ricassoHole + pommelHole)
are the canonical examples. Rules:
  - Winding order MATTERS: outer shape must be CCW (counterclockwise)
    in 2D, holes must be CW (clockwise) — Three.js's Earcut
    triangulator follows the convention that "interior to outer = hole".
    `absarc(start, end, ccw=false)` produces a CCW arc; if your hole
    looks like a solid island instead of a cut-out, you've got the
    winding inverted.
  - For a rounded slot, build it as two arcs + two lines, NOT as a
    single rounded rectangle — `Shape.absellipse` + `absarc` are the
    reliable building blocks. See the Gerber ref's `addRoundedSlot`.
  - The hole's local frame matches the SHAPE's, not the world. After
    `geo.rotateX(-Math.PI / 2)` and `geo.translate(...)` the holes
    move with the rest of the geometry.

--------------------------------------------------------------------------
3.8 — SDF + MARCHING CUBES (continuous-sculpt topology)
--------------------------------------------------------------------------
For organic continuous-sculpt meshes (a humanoid body, a soft head
where head blends into neck blends into shoulders with no visible
panel break), build a signed-distance field in JS, then polygonise
it once with a tiny marching-cubes pass. The result is a SINGLE
watertight mesh whose vertex count you can dial by the grid
resolution; it never has the seams that stacking separate
RoundedBox primitives leaves.

  // 1) Define capsules with smin/smax
  function sdCapsule(px,py,pz, ax,ay,az, bx,by,bz, ra, rb) {
    const pax=px-ax, pay=py-ay, paz=pz-az;
    const bax=bx-ax, bay=by-ay, baz=bz-az;
    const baLen2 = bax*bax + bay*bay + baz*baz;
    let h = baLen2>0 ? (pax*bax + pay*bay + paz*baz)/baLen2 : 0;
    h = h<0?0:h>1?1:h;
    const dx = pax - bax*h, dy = pay - bay*h, dz = paz - baz*h;
    return Math.sqrt(dx*dx + dy*dy + dz*dz) - (ra + (rb-ra)*h);
  }
  // Polynomial smooth minimum — k = blend radius in world units
  function smin(a, b, k) {
    if (k <= 0) return Math.min(a, b);
    const h = Math.max(0, Math.min(1, 0.5 + 0.5*(b-a)/k));
    return b*(1-h) + a*h - k*h*(1-h);
  }

  // 2) Build the field as a sum of capsules
  function bodyField(x, y, z) {
    let d = sdCapsule(x,y,z, 0, 1.5, 0,  0, -1.5, 0,  0.4, 0.3);   // torso
    d = smin(d, sdCapsule(x,y,z, 0, 2.7, 0,  0.5, 2.5, 0.3, 0.18, 0.16), 0.3);
    return d;
  }

  // 3) Polygonise once with marching cubes (implement or import)
  const positions = marchCubes(bodyField, RESOLUTION, BOUNDS);

  // 4) Build a BufferGeometry
  const geo = new THREE.BufferGeometry();
  geo.setAttribute('position', new THREE.Float32BufferAttribute(positions, 3));
  geo.computeVertexNormals();
  geo.computeBoundingBox(); geo.computeBoundingSphere();

The humanoid ref is the canonical example — body, head, hands, feet,
ears, tail, all from one signed-distance field per body region. This
is the only path in this spec that can produce a "continuous-sculpt"
topology (the JSON/JS spec's `sdf_blob` field is the equivalent on
the blueprint path). PART 11.1's "loss of seams" rule means: if your
reference is one fused mass, this is the technique you need.

================================================================================
PART 4 — IMPORTS & EXTERNAL DEPENDENCIES
================================================================================

The renderer's TS loading pipeline (SYSTEM_UPDATE_PROMPT §3) resolves your
imports against the page's own `<script type="importmap">`, which already
pins the exact Three.js build the rest of the renderer runs on. You only
need to author the imports the way you'd write them for a normal
TypeScript + Three.js project — the renderer does not fetch a second copy
of Three.js from anywhere; it normalizes one import-path spelling (below)
so it resolves against the import map that's already on the page.

--------------------------------------------------------------------------
4.1 — ALLOWED IMPORT PATTERNS
--------------------------------------------------------------------------
  import * as THREE from 'three';                                            // REQUIRED
  import { XxxGeometry } from 'three/examples/jsm/geometries/XxxGeometry.js';
  import { XxxLoader } from 'three/examples/jsm/loaders/XxxLoader.js';
  import { XxxControls } from 'three/examples/jsm/controls/XxxControls.js';
  import { XxxPass } from 'three/examples/jsm/postprocessing/XxxPass.js';
  import { Xxx } from 'three/addons/...';                                    // also accepted, same source

The renderer rewrites ONLY the `three/examples/jsm/` prefix, swapping it
for this page's `three/addons/` import-map alias:
  from 'three/examples/jsm/X'   →   from 'three/addons/X'
`'three'` itself, and anything already spelled `'three/addons/...'`, pass
through completely untouched — they resolve natively via the page's
import map. This matters more than it sounds: fetching Three.js a second
time from a different URL would give you a second, distinct copy of the
`THREE` classes, and `group instanceof THREE.Object3D` (which the
renderer checks on your factory's return value) would then fail even for
an otherwise-correct file. Leaving `'three'` alone is what keeps your
output and the viewer on the same instance.

--------------------------------------------------------------------------
4.2 — FORBIDDEN IMPORTS
--------------------------------------------------------------------------
  - Anything not under `three` or `three/...`. No npm packages, no
    local helpers, no relative paths. The model file must be
    self-contained.
  - Default-import of three itself (`import THREE from 'three'`).
    Use namespace import — Three.js ships named/namespace exports with
    no default, and several addons expect the namespace shape.
  - Anything from `node:*`, `fs`, `path`, `crypto`. The renderer is
    browser-only.

--------------------------------------------------------------------------
4.3 — LIB INITIALIZATION
--------------------------------------------------------------------------
Some three/examples/jsm modules need a one-time init (RectAreaLightUniformsLib
for soft area lights, OrbitControls for camera rig, etc.). Call the
init inside the factory, not at module top level — that way the module
itself is side-effect-free and importable from a test without a DOM:

  export function createBMXEnduranceBikeModel(options) {
    RectAreaLightUniformsLib.init();    // safe to call repeatedly; it's idempotent
    const root = new THREE.Group();
    // …build…
    return root;
  }

================================================================================
PART 5 — VFX / ANIMATION: the `tick(dt, elapsed)` CONTRACT
================================================================================

If your model has per-frame animation (recoil, idle sway, smoke, particle
systems, blinking lights, a clock hand, etc.), expose it via
`root.userData.tick`. The renderer's main loop calls it every frame with
the same `dt` and `elapsed` it feeds the camera controls.

--------------------------------------------------------------------------
5.1 — SIGNATURE
--------------------------------------------------------------------------
  const tick = (dt: number, elapsed: number): void => {
    // dt = seconds since the previous frame (use this for ALL time math)
    // elapsed = seconds since the renderer started (use for periodic effects)
  };
  root.userData.tick = tick;

Do NOT use `performance.now()` or `Date.now()` for the time math — the
renderer is in control of time, your factory is a passive consumer.
Use `dt` for decay, easing, and integration; use `elapsed` for sin/cos
periodic motion where the phase needs to be stable across pauses.

--------------------------------------------------------------------------
5.2 — STATE MACHINES (the recommended pattern)
--------------------------------------------------------------------------
The shotgun example's auto-fire loop is a clean reference. Pattern:

  const state = {
    recoil: 0,             // 0..1 current kick
    flash: 0,              // seconds of flash remaining
    sinceFire: 0,          // seconds since the last shot
    shotIndex: 0,
  };
  const FIRE_INTERVAL = 2.4;        // seconds between shots
  const FLASH_DURATION = 0.07;      // flash envelope
  const RECOIL_DECAY = 3.2;         // recoil spring stiffness
  const GRAVITY = 6.5;

  function fire() {
    state.recoil = 1;
    state.flash = FLASH_DURATION;
    state.sinceFire = 0;
    state.shotIndex++;
    window.setTimeout(spawnShell, 70);   // shell ejects a touch after ignition
  }

  const tick = (dt: number, elapsed: number): void => {
    state.sinceFire += dt;
    if (FIRE_INTERVAL > 0 && state.sinceFire >= FIRE_INTERVAL) fire();

    state.recoil = Math.max(0, state.recoil - dt * RECOIL_DECAY);
    const r = state.recoil * state.recoil;     // ease
    // apply r to whichever nodes are affected (gun.position, recoilPivot.rotation, …)
    // …
  };

This keeps ALL the per-frame work inside one function, every piece of
mutable state in a single `state` object, every constant in a
named const. Diffable, debuggable, easy to extend.

--------------------------------------------------------------------------
5.3 — DISCRETE / SPAWNED ACTORS (shells, particles, decals)
--------------------------------------------------------------------------
The shotgun example's `shells[]` and `puffs[]` pools are the pattern.
Pre-allocate the maximum number of actors you'll ever need, park them
in a pool, and recycle slots:

  const shells: { group: THREE.Group; active: boolean; vel: THREE.Vector3; ang: THREE.Vector3; life: number }[] = [];
  for (let i = 0; i < 5; i++) {
    const g = buildShell();
    g.visible = false;
    root.add(g);
    shells.push({ group: g, active: false, vel: new THREE.Vector3(), ang: new THREE.Vector3(), life: 0 });
  }

  function spawnShell() {
    const slot = shells.find((s) => !s.active) ?? shells[state.shotIndex % shells.length];
    // …reset slot to new position/velocity/rotation, set active = true, visible = true
  }

  // in tick:
  for (const s of shells) {
    if (!s.active) continue;
    s.life -= dt;
    s.vel.y -= GRAVITY * dt;
    s.group.position.addScaledVector(s.vel, dt);
    s.group.rotation.x += s.ang.x * dt;
    // …bounce / fade / despawn…
  }

This is GC-friendly (no per-frame allocations) and keeps the file
diffable when you tune parameters.

--------------------------------------------------------------------------
5.4 — EASING
--------------------------------------------------------------------------
Cheap, good-looking easings in 2 lines each:
  - Linear:               const t = clamp01(elapsed / dur);
  - Ease-out (cubic):     const t = 1 - Math.pow(1 - clamp01(...), 3);
  - Ease-in-out (sine):   const t = -(Math.cos(Math.PI * clamp01(...)) - 1) / 2;
  - Spring (critically damped):  r = state.recoil; state.recoil = max(0, r - dt*k); r = r*r;
  - Pop:                  r = clamp01(t); r = r * (2 - r);     // ease-out, then accelerate to 0
  - Bounce:               (Google "easeOutBounce"; 6 lines of if/else)

For idle motion (sway, breathing, blink, head-bob), use elapsed directly
with a slow sin/cos so the phase survives any pause:

  root.rotation.y = Math.sin(elapsed * 0.3) * 0.28;          // ±0.28 rad sway
  root.position.y = 0.55 + Math.sin(elapsed * 0.9) * 0.01;    // tiny vertical breath

--------------------------------------------------------------------------
5.5 — WHEN NOT TO USE tick
--------------------------------------------------------------------------
Static props, materials studies, references shots, anything that doesn't
animate should NOT have a tick — leave root.userData.tick undefined and
the renderer won't call into your model per frame. Adding an empty tick
function is a wasted dispatch.

--------------------------------------------------------------------------
5.6 — AnimationMixer + THREE.AnimationClip (skeletal animation)
--------------------------------------------------------------------------
For models with skeleton-driven animation (a walking/running/jumping
character with bones, a machine whose arms articulate along authored
curves), use THREE.AnimationMixer + THREE.AnimationClip instead of (or
in addition to) procedural tick math. The renderer recognises this shape
under `root.userData.sculptRuntime.animations` and:

  (1) Auto-silences the factory's own mixer when the in-app animation
      player is active, so two mixers never fight over the same bones
      (a long-standing bug fixed in v1.3).
  (2) Surfaces the clips in the renderer's play / next-clip UI.
  (3) Auto-ticks the factory's mixer every frame (dt) at the renderer's
      render-loop cadence.

Three accepted shapes (the renderer tries them in this order):

  // (a) Modern shape — mixer + clips, both reach into the renderer's UI
  const mixer = new THREE.AnimationMixer(root);
  const clips = [
    new THREE.AnimationClip('idle',  2.0, [ /* …tracks… */ ]),
    new THREE.AnimationClip('walk',  1.4, [ /* …tracks… */ ]),
    new THREE.AnimationClip('attack', 0.8, [ /* …tracks… */ ]),
  ];
  const actions = clips.map(c => mixer.clipAction(c));
  root.userData.sculptRuntime.animations = { clips, mixer, actions };
  // Hand-off: the renderer silences the mixer on mount and ticks it
  // itself at dt. Your `root.userData.tick` no longer needs to call
  // `mixer.update(dt)` — duplicate the call and you'll see
  // double-application.

  // (b) Legacy hint-array — synthesised AnimationClips
  // Older factories publish a plain array; the renderer builds real
  // THREE.NumberKeyframeTrack + AnimationClip from each entry.
  root.userData.sculptRuntime.animations = [
    { name: 'drive', duration: 4.0, tracks: [
        { name: 'wheel.rotation[x]', times: [0, 1, 2, 3, 4], values: [0, 1.5, 3, 4.5, 6] },
        { name: 'body.position[y]',  times: [0, 1, 2, 3, 4], values: [0, 0.05, 0, 0.05, 0] },
    ]},
  ];

  // (c) Custom namespace — if you keep the mixer on your own runtime
  // object (e.g. root.userData.electricMouseMascotRuntime.mixer), the
  // renderer finds it via the lblFindAnimationMixer() DFS in PART 29
  // and ticks it. v1.3 added this so factories don't have to know
  // which exact path the renderer reads.

If you mix BOTH a procedural `userData.tick` AND an AnimationMixer, the
factory's tick must own the mixer.update() call (otherwise the renderer
silences it and your tick is the only thing keeping the pose alive). The
recommended pattern from the humanoid ref:

  const previousTick = root.userData.tick as ((dt: number, elapsed: number) => void) | undefined;
  root.userData.tick = (dt: number, elapsed: number) => {
    previousTick?.(dt, elapsed);   // any earlier tick (e.g. breath, sway)
    controller.update(dt);         // ticks the AnimationMixer
  };

This way the factory has ONE tick entry point and the renderer never
double-ticks.

--------------------------------------------------------------------------
5.6(a) — BAKING FROM A .glb/.gltf REFERENCE: PROPERTY-NAME TRANSLATION (CRITICAL)
--------------------------------------------------------------------------
When clips are built from keyframe data extracted out of a reference
.glb/.gltf file (not hand-authored), the raw glTF JSON uses glTF's own
channel target names:

    translation | rotation | scale

These are NOT the three.js Object3D property names. THREE.PropertyBinding
resolves KeyframeTrack names against the actual object properties, and
Object3D has no `.translation` property at all, and `.rotation` is an
Euler — a different value type/size than the Quaternion a glTF 'rotation'
channel is baked as. Using the glTF path name verbatim as the track name
does NOT throw, does NOT log a warning, and the AnimationClip / mixer /
action all construct and play "successfully" — the track simply never
finds anything to write to, so the model sits frozen while every symptom
you'd check (clips present, actions playing, mixer.update() being called
every frame) looks correct. This is the single most common way a baked
clip silently fails to play.

The required translation table when building track names from glTF data:

    glTF channel target      three.js KeyframeTrack target      Track type
    --------------------      -----------------------------      ----------
    translation           →   <node>.position                    VectorKeyframeTrack
    rotation               →   <node>.quaternion                  QuaternionKeyframeTrack
    scale                   →   <node>.scale                       VectorKeyframeTrack

    // NEVER build a track name as `${node}.${gltfPath}` directly.
    // ALWAYS pass gltfPath through an explicit lookup table first:
    const GLTF_PATH_TO_THREE_PROPERTY = {
      translation: 'position',
      rotation: 'quaternion',
      scale: 'scale',
    };
    const trackName = `${nodeName}.${GLTF_PATH_TO_THREE_PROPERTY[gltfPath]}`;

A `rotation` channel MUST be constructed with `QuaternionKeyframeTrack`
(4 floats/key, XYZW) targeting `.quaternion` — never `NumberKeyframeTrack`
per-Euler-component targeting `.rotation[x/y/z]` when the source data is
already baked as quaternions. (Per-axis Euler NumberKeyframeTracks
targeting `.rotation[x]` etc. remain valid ONLY for hand-authored
procedural tracks where you chose Euler angles yourself — never mix the
two conventions on data pulled from a .glb sampler.)

--------------------------------------------------------------------------
5.6(b) — MANDATORY: HEADLESS PLAYBACK VERIFICATION BEFORE DELIVERY
--------------------------------------------------------------------------
"The clip constructs without a compile/type error" is NOT evidence the
animation plays. TypeScript cannot catch a track name that resolves to
a nonexistent runtime property — this is a runtime binding failure, not
a type error, and `tsc --strict` will pass on the broken version just as
cleanly as the fixed one.

Before treating any baked-animation file as done, run an actual headless
playback check — not just a compile check:

  1. Stub `document.createElement` to return a no-op object (most factory
     files early-return out of their canvas-texture helpers when
     `getContext()` returns null, so this is usually enough to construct
     the model headless).
  2. Import the compiled factory, call it, grab a node that a track
     targets via `root.getObjectByName('<NodeName>')`.
  3. Record that node's `.position` / `.quaternion` BEFORE ticking.
  4. Call `root.userData.tick(dt, elapsed)` (or drive the mixer directly)
     for ~30-90 simulated frames.
  5. Record the same node's `.position` / `.quaternion` AFTER, and assert
     it actually changed.

If the AFTER values equal the BEFORE values, the clip is NOT playing —
even though the clip, action, and mixer all "exist" — and the file is
not done. Do this check for at least one rotation-path node and one
translation-path node per clip family before delivery. A passes/
passesReviewed note claiming a clip count or animation description is
documentation, not verification — it does not substitute for this check.

--------------------------------------------------------------------------
5.7 — Custom-runtime `update(elapsed)` (no tick, no mixer)
--------------------------------------------------------------------------
Some models (the pikachu ref is the canonical example) keep their
animation driver on a custom runtime namespace like
`userData.electricMouseMascotRuntime` and expose a `.update(elapsed)`
method on it — but DO NOT set `userData.tick` (because the entire
animation logic lives inside the namespace, including a private
elapsed clock). v1.3 added an auto-discovery path for this:

  // The renderer walks root.userData after mount, finds the first
  // object with both an `update(elapsed)` method AND a `_root`
  // back-reference to the model, and calls it every frame with the
  // renderer's elapsed time. No `root.userData.tick` needed.

If you go this route, set `_root` on the runtime so the DFS finds it:

  const runtime = {
    _root: root,
    update(elapsedSeconds: number) { /* … */ },
  };
  root.userData.electricMouseMascotRuntime = runtime;

The rule of thumb: prefer `root.userData.tick` (PART 5.1) when
practical — it's the simplest, no DFS, no `_root` back-reference, and
the renderer will tick it deterministically. Reach for the custom-runtime
pattern only when you need a private clock, multiple sub-states, or a
clock that survives tab switches (the pikachu ref's "10K celebration"
counter is one such case).

================================================================================
PART 6 — sculptRuntime CONTRACT (the runtime hooks the inspector reads)
================================================================================

The renderer's inspector reads `root.userData.sculptRuntime` and
presents it as a navigable tree: named nodes (groups / meshes), named
sockets (empty Object3Ds the host can reparent to), materials, vfx
actors, colliders, destruction groups. Populate it; don't skip it.

--------------------------------------------------------------------------
6.1 — REQUIRED SHAPE
--------------------------------------------------------------------------
  export type ProceduralModelRuntime = {
    nodes: Record<string, THREE.Object3D>;
    meshes: Record<string, THREE.Mesh>;
    sockets: Record<string, THREE.Object3D>;
    colliders: Record<string, unknown>;
    destructionGroups: Record<string, THREE.Object3D[]>;
  };

  // after the model is fully assembled:
  root.userData.sculptRuntime = {
    nodes:        { receiver, handguard, barrel: barrelGroup, redDot, grip: gripGroup, triggerGroup, bolt: boltGroup },
    meshes:       { /* same names but only Mesh children, not Groups */ },
    sockets:      { muzzle: muzzleSocket, ejectionPort: ejectAnchor },
    colliders:    { /* optional: collision proxies, raycast targets */ },
    destructionGroups: { /* named groups for breakable subassemblies */ },
  } satisfies ProceduralModelRuntime;

The renderer's TS path stores this verbatim — your type IS the contract.

--------------------------------------------------------------------------
6.1B — FULL OPTIONAL SHAPE (the v1.3 expansion)
--------------------------------------------------------------------------
v1.3 expanded the contract with several OPTIONAL fields that the
renderer actively uses. The complete shape the inspector + action-hooks
panel + fidelity gate reads is:

    inferred: string[],                   // e.g. ['rear hair', 'fine fingers']

  root.userData.sculptSpec = {

    reference: '<local path or URL>',
    style: '<from PART 48.1 vocabulary>',

  };
  root.userData.actionReadiness = {

Every optional field is safe to omit. The more you populate, the more
the renderer's Inspector + fidelity gate + action-hooks panel can do.
v1.2 files that only set nodes/meshes/sockets/colliders/
destructionGroups keep working — all the new fields are pure additions.



NOTE — if `animations.mixer` here is the SAME mixer instance a
`root.userData.tick` also calls `.update()` on (PART 5.6), that is a
double-drive bug (the clip plays at 2x speed, not "doesn't play" — a
different symptom from 5.6(a), but the same root cause: two update
paths touching one mixer). The factory's tick owns `mixer.update()`;
`sculptRuntime.animations.mixer` is for the renderer's UI/inspector to
read from, not a second place to drive it from.

--------------------------------------------------------------------------
6.2 — NAMING
--------------------------------------------------------------------------
Names should be:
  - camelCase (matches the JS/JSON spec's field convention)
  - descriptive ("frontTire", not "t1")
  - consistent across the file — once you call it "frontTire" in the
    geometry code, it MUST be "frontTire" in sculptRuntime, NOT
    "front_tire" or "FrontTire" or "tireFront"
  - unique within each Record (it's a Record, not an array — last
    write wins, so two `nodes.foo` is a bug)

The names surface in the inspector's tree, so spend the extra
10 seconds making them readable. The shotgun example uses
`receiver`, `handguard`, `barrel: barrelGroup`, `redDot`, `grip:
gripGroup` — note the `: alias` pattern when the variable in scope
is named for its function (`gripGroup`) but the runtime name is
the user-facing one (`grip`).

--------------------------------------------------------------------------
6.3 — SOCKETS (empty Object3Ds the host can reparent things to)
--------------------------------------------------------------------------
A "socket" is a THREE.Object3D with no visible content, just a
position+rotation+scale. The host can then attach anything to it
(muzzle flash VFX, a held item, a particle emitter, a debug
gizmo) by `socket.add(otherThing)`. Mark with `.name` and `.userData
.socketType = 'muzzle' | 'mount' | 'attach' | 'spawn'` so the
host can find them by type.

Example (from the shotgun file):
  const muzzleSocket = new THREE.Group();
  muzzleSocket.name = 'muzzleSocket';
  muzzleSocket.position.set(-1.78, 0.12, 0);
  muzzleSocket.userData.socketType = 'muzzle';
  add(muzzleSocket);   // becomes a child of the gun, not a free-floating node

When the host attaches a muzzle flash, a casing spawner, or a
particle system to `sockets.muzzle`, the flash rides the recoil
and ejecta fly out of the right spot.

--------------------------------------------------------------------------
6.4 — DESTRUCTION GROUPS
--------------------------------------------------------------------------
For breakable / explodable / collapsable models, group every part
of a logical subassembly into a destructionGroup:

  destructionGroups: {
    glass: [windscreen, sideWindowL, sideWindowR, rearWindow],
    panels: [hood, fenderL, fenderR, doorL, doorR, roof],
    wheels: [frontWheel, rearWheel, ...],
  }

The host rig can then iterate the group and apply a per-part
debris effect (hide, animate shatter, swap to a fractured mesh,
etc.) when the model "takes damage". The BMX example
demonstrates this with `destructionGroups.frame = [frameGroup]`.

--------------------------------------------------------------------------
6.5 — COLLIDERS
--------------------------------------------------------------------------
If the model needs physics-aware colliders (raycast targets, simple
bounding proxies), put them in `colliders`. These are typed as
`Record<string, unknown>` because the contract is host-defined —
the BMX example uses them as named Object3D proxies; a custom
host might use Rapier/Bullet shape descriptors. Whatever the host
can consume goes here.

--------------------------------------------------------------------------
6.6 — userData CONVENTIONS [RJS update 1, S3]
--------------------------------------------------------------------------
Convention: If the renderer offers LOD generation, the active scene's
root.userData.lods is set to
  { lod0: THREE.Object3D, lod1: THREE.Object3D, lod2: THREE.Object3D }
where lod0 is full quality and lod2 is the most decimated. TS factories
that want their own LOD structure may overwrite this with a type that
matches the same shape.

--------------------------------------------------------------------------
6.7 — PER-MESH METADATA (component role + action profile) [v1.3]
--------------------------------------------------------------------------
For complex models with many named parts, the renderer reads four
OPTIONAL per-mesh metadata fields. None of them are required, but
populating them turns the Inspector from a passive tree into a live
gizmo that knows what each part IS and what you can do to it.

  // 6.7.1 — sculptComponent: identity + role + parent + dependent sockets
  node.userData.sculptComponent = {
    id:       'cabin',                  // human-readable, surface in tools
    parentId: 'body',                   // 'parent' component this hangs off
    role:     'cabin' | 'shell' | 'garment' | 'head' | 'limb' |
              'wheel' | 'barrel' | 'receiver' | 'trigger' | 'magazine' |
              'scope' | 'stock' | 'joint' | 'bone' | 'ik-target' |
              'socket' | 'mount' | 'handle' | 'crown-emblem' |
              'character-root' | 'skeleton-root' | 'rig-root' |
              /* …anything the host recognizes… */,
    sockets:  ['cabin-socket'],         // socket names this part depends on
  };

  // 6.7.2 — actionProfile: which 1-click actions are valid for this part
  node.userData.actionProfile = {
    canSpin:    true,    // drives sculptRuntime.actions.spin
    canGlow:    true,    // drives sculptRuntime.actions.glow
    canFire:    true,    // drives sculptRuntime.actions.fire
    canRecoil:  true,    // drives sculptRuntime.actions.recoil
    canEject:   true,    // drives sculptRuntime.actions.eject
    canOpen:    true,    // drives sculptRuntime.actions.openLid
    canElectrify: true, // drives sculptRuntime.actions.triggerElectric
    canJump:    true,    // drives sculptRuntime.actions.jump
    canWiggle:  true,    // drives sculptRuntime.actions.wiggle
    canSway:    true,    // drives sculptRuntime.actions.sway
    canRecenter: true,  // drives sculptRuntime.actions.reset / recenter
  };
  // The Inspector reads this and shows only the relevant buttons. A
  // barrel node with canFire + canRecoil + canEject gets three
  // buttons; a foot node with canSway gets one.

  // 6.7.3 — animationRole: classify nodes for skeletal animation
  // The renderer's lblCollectAnimations path reads this when scanning
  // THREE.Bone hierarchies; helps it know which objects to look at
  // and which to skip.
  node.userData.animationRole = 'character-root' | 'skeleton-root' |
                                'rig-root' | 'bone' | 'ik-target' |
                                'socket' | 'aim-target' | 'attachment';

  // 6.7.4 — socketFor: trace parent ↔ child between a part and its
  // socket. The reciprocal of `sockets: { id: socketObject3D }` — set
  // this on a socket to point at the part it serves.
  socket.userData.socketFor = 'cabin';   // matches a sculptRuntime.nodes key

A few rules:
  - Set these AFTER positioning the node in the scene (so the parent
    id is the one actually being used as the parent).
  - Names must match the same casing convention as sculptRuntime
    (PART 6.2). 'frontTire' in the runtime MUST be 'frontTire' here.
  - These fields are read by the renderer's INSPECTOR, the gizmo,
    and the action-hooks panel. They do NOT change the rendered
    scene. A factory that omits them is still valid; the Inspector
    simply has less to show.

--------------------------------------------------------------------------
7.4 — PBR PRINCIPLES (PART 50.1 of the JSON/JS spec applies here too)
--------------------------------------------------------------------------
Every distinct material needs:
  - an albedo (color or map) — the visible base hue
  - a roughness value — controls how sharp the highlight is
  - a metalness value — 0 for dielectrics, ~1 for metals
  - a normal/bump source if the surface has micro-relief (knurl,
    grain, scratches, weld beads)

Never alias channels. A "dark gold" isn't `color: darken(gold, 0.5)` —
either it's a different color, or it's the same gold under
different lighting. The shortcut "color = baseColor * shadowFactor"
produces muddy results because it ignores how the light interacts
with the roughness/metalness channels.

--------------------------------------------------------------------------
7.5 — MATERIAL MAP (PART 50 of the JSON/JS spec)
--------------------------------------------------------------------------
The PART 50 rules apply unchanged. Specifically:
  - Sharp small highlight + dark reflections → metal / metallic preset
    (metalness > 0.5, roughness < 0.4). Don't paint the highlight as
    a separate region.
  - Soft wide highlight + no reflection → matte / fabric / skin
    (roughness > 0.7, metalness 0.0).
  - Visible highlight + transparency → glass / translucent
    (transmission > 0.5, ior 1.4-1.5).
  - Bright saturated against a darker surround, with a halo or glow →
    emissive+emissiveIntensity, not just a bright color.
  - Flat-shaded illustration style → MeshBasicMaterial (no lighting
    at all) or MeshToonMaterial with a 3-step gradient. Don't
    accidentally use a physically-lit preset on flat-shaded art.

================================================================================
PART 8 — PROCEDURAL CANVAS TEXTURES (no external art)
================================================================================

The TS path is fully self-contained — no .png, .jpg, or .hdr files
to load. Everything that needs a texture is generated at runtime
from a `<canvas>` element. This is a hard constraint of the format;
if you find yourself wanting an external image, redesign the
material to not need one (use procedural noise / baked patterns
instead).

--------------------------------------------------------------------------
8.1 — DETERMINISTIC PRNG (required for stable, diffable textures)
--------------------------------------------------------------------------
Mulberry32, 4 lines:
  function mulberry32(seed: number): () => number {
    let a = seed >>> 0;
    return () => {
      a |= 0;
      a = (a + 0x6d2b79f5) | 0;
      let t = Math.imul(a ^ (a >>> 15), 1 | a);
      t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
      return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
    };
  }

Use a DIFFERENT seed per texture so they don't all share the same
pattern. Convention: pick a seed hex that hints at the texture
purpose (`0xba7e11` for bakelite, `0x5ca7c3` for slate scratches).

--------------------------------------------------------------------------
8.2 — CANVAS TEXTURE FACTORY
--------------------------------------------------------------------------
  function makeCanvas(w: number, h: number): { canvas: HTMLCanvasElement; ctx: CanvasRenderingContext2D } {
    const canvas = document.createElement('canvas');
    canvas.width = w;
    canvas.height = h;
    return { canvas, ctx: canvas.getContext('2d')! };
  }

  function hex(c: number): string {
    return '#' + c.toString(16).padStart(6, '0');
  }

  function makeTexture<T extends keyof CanvasTextureOptions>(
    w: number, h: number, kind: T,
    draw: (ctx: CanvasRenderingContext2D, w: number, h: number, rand: () => number) => void,
  ): THREE.CanvasTexture {
    const { canvas, ctx } = makeCanvas(w, h);
    const rand = mulberry32(KIND_TO_SEED[kind]);
    draw(ctx, w, h, rand);
    const tex = new THREE.CanvasTexture(canvas);
    tex.wrapS = tex.wrapT = THREE.RepeatWrapping;
    tex.colorSpace = (kind === 'albedo' || kind === 'decal') ? THREE.SRGBColorSpace : THREE.NoColorSpace;
    tex.anisotropy = 8;
    tex.needsUpdate = true;
    return tex;
  }

Every procedural texture is one of: albedo (color), bump (greyscale
heightfield, used as bumpMap), decal (transparent PNG-equivalent
painted on a flat plane), or env (cube/equirect — but you almost
never need one in the TS path since the renderer's scene has
shared env lighting).

--------------------------------------------------------------------------
8.3 — COMMON TEXTURE RECIPES (copy from the example files)
--------------------------------------------------------------------------
  // weldBead  — fish-scale TIG weld bead bump map
  // gripKnurl — horizontal ring grooves for rubber grip
  // knurlBump — diamond cross-hatch for knurled knobs/pegs
  // leather   — soft mottled bump for saddle / padding
  // reflector — small diamond cells for amber pedal reflectors
  // scratch   — fine speckle + scratches for painted-metal receiver
  // marble    — amber bakelite swirls + grain streaks
  // flag      — monochrome US flag decal
  // markings  — text + hatched-triangle logo decal
  // tyre      — colour + bump for a TorusGeometry, sidewall lettering
  // flashSprite — radial gradient + 8 spikes for muzzle flash
  // smokeSprite — soft round puffs for smoke

See createIssacaShotgunModel.ts and createBMXEnduranceBikeModel.ts
for the full implementations — they are the canonical examples for
every texture pattern this format supports.

--------------------------------------------------------------------------
8.4 — TEXTURE SPACE & ORIENTATION
--------------------------------------------------------------------------
  - CanvasTexture's default UV layout is 0..1 in both directions;
    for a TorusGeometry, U runs around the major axis, V runs around
    the tube cross-section. So a tyre texture that wants different
    visuals on the sidewall (V near 0.13 and 0.87) and the crown
    (V 0.28-0.72) lays them out at those V bands, NOT at U positions.
  - To flip text so it reads correctly on both sides of a symmetric
    part, set `tex.repeat.set(-1, 1)` — this mirrors the texture in U.
    The tyre sidewall lettering in the BMX example does this.
  - For a wraparound decal on a cylinder, the decal's U direction
    runs around the cylinder; the host of the decal quad is
    responsible for rotating the quad so text reads the right way
    from the camera angle.
  - For painted text on a flat panel (a receiver, a side cover),
    the decal quad's U direction is whatever you point it at;
    set the rotation so "up" in the canvas matches "up" on the part.

--------------------------------------------------------------------------
8.5 — IMAGE TEXTURES (optional user-uploaded image as material map)
--------------------------------------------------------------------------
Unlike 8.1-8.4's procedural canvas textures (generated from math, no
external file), the renderer also supports applying a specific
user-uploaded image to one part as its material map — this is primarily
a flat-format JSON/JS blueprint feature (see PART 5.1 of the Prompt/Image
→ JS/JSON specs), but a TS-authored factory MAY opt into the same idea
WITHOUT breaking this format's self-contained/no-fetch rule (PART 4.2),
by embedding the image as a data URL literal in the source and loading
it locally — a data: URL is decoded by the browser with no network
request, so it does not violate "the model file must be self-contained":

  const DOOR_GRAIN = 'data:image/png;base64,iVBORw0KGgoAA...'; // baked in, no fetch

  function applyImageTexture(
    mat: THREE.Material, dataUrl: string,
    opts?: { role?: 'map'|'normalMap'|'roughnessMap'; repeat?: [number,number]; rotationDeg?: number },
  ): void {
    const tex = new THREE.TextureLoader().load(dataUrl);
    const role = opts?.role ?? 'map';
    tex.colorSpace = (role === 'map') ? THREE.SRGBColorSpace : THREE.NoColorSpace;
    tex.wrapS = tex.wrapT = THREE.RepeatWrapping;
    if (opts?.repeat) tex.repeat.set(opts.repeat[0], opts.repeat[1]);
    if (opts?.rotationDeg) { tex.center.set(0.5, 0.5); tex.rotation = THREE.MathUtils.degToRad(opts.rotationDeg); }
    (mat as any)[role] = tex;
    mat.needsUpdate = true;
  }

RULES:
  - The data URL must be a literal baked into the .ts source — never a
    `fetch()` call, never a relative path lookup. PART 4.2 forbids
    network calls and non-`three` imports; a `data:` URL loaded through
    `THREE.TextureLoader` stays inside that rule because nothing leaves
    the browser to resolve it.
  - Same colorSpace convention as 8.2: SRGBColorSpace for albedo/color
    maps, NoColorSpace for normal/roughness/metalness/any data texture.
  - If a part doesn't need a genuinely user-supplied photo or logo,
    prefer the procedural canvas recipes in 8.3 instead — they're far
    smaller, always available offline, and don't bloat the source with
    base64 data.
  - This mirrors the flat-format "textureImage" field family (PART 5.1
    of the JS/JSON specs) conceptually — same override intent (an image
    texture replaces, never blends with, a procedural one on the same
    part) — but here it's authored directly as code, since a TS model
    has no separate declarative per-object descriptor to attach a field
    to; the factory is the descriptor.

PART 9 — STANDARD HELPERS (copy these, don't reinvent)
================================================================================

--------------------------------------------------------------------------
9.1 — applyShadow(obj, options)
--------------------------------------------------------------------------
  function applyShadow(obj: THREE.Object3D, opts: { castShadow?: boolean; receiveShadow?: boolean; wireframe?: boolean }): void {
    obj.traverse((o) => {
      const m = o as THREE.Mesh;
      if (m.isMesh) {
        m.castShadow = opts.castShadow ?? true;
        m.receiveShadow = opts.receiveShadow ?? true;
        if (opts.wireframe) {
          const mat = m.material as THREE.MeshStandardMaterial;
          if (mat && 'wireframe' in mat) mat.wireframe = true;
        }
      }
    });
  }

Call this ONCE on the root group, after the model is fully assembled,
to recursively set castShadow/receiveShadow on every Mesh. Saves ~30
lines of "for every part: cast = true, receive = true".

--------------------------------------------------------------------------
9.2 — v(x,y,z) and UP
--------------------------------------------------------------------------
  const UP = new THREE.Vector3(0, 1, 0);
  const v = (x: number, y: number, z = 0): THREE.Vector3 => new THREE.Vector3(x, y, z);

Use these EVERYWHERE instead of `new THREE.Vector3(x, y, z)` — saves
typing and makes the file greppable for "every place I positioned a
vertex".

--------------------------------------------------------------------------
9.3 — xCyl(rTop, rBot, len, seg, mat)
--------------------------------------------------------------------------
  function xCyl(rTop: number, rBot: number, len: number, seg: number, mat: THREE.Material): THREE.Mesh {
    const g = new THREE.CylinderGeometry(rTop, rBot, len, seg);
    g.rotateZ(Math.PI / 2);   // axis -> X
    return new THREE.Mesh(g, mat);
  }

The shotgun example uses this for every cylinder whose long axis is
+X or -X (barrel, springs, trigger rod, etc.). CylinderGeometry's
default axis is Y, the rotateZ in-place puts it on X without an
extra group wrapper.

--------------------------------------------------------------------------
9.4 — tube(a, b, r1, r2, mat, radial)
--------------------------------------------------------------------------
  function tube(
    a: THREE.Vector3, b: THREE.Vector3,
    r1: number, r2: number, mat: THREE.Material, radial = 20,
  ): THREE.Mesh {
    const dir = new THREE.Vector3().subVectors(b, a);
    const len = dir.length();
    const geo = new THREE.CylinderGeometry(r2, r1, len, radial, 1, false);
    const mesh = new THREE.Mesh(geo, mat);
    mesh.quaternion.setFromUnitVectors(UP, dir.clone().normalize());
    mesh.position.copy(a).addScaledVector(dir, 0.5);
    return mesh;
  }

Connect two points with a tapered cylinder. The BMX example uses
this for every frame tube, fork leg, handlebar, seat post, etc.

--------------------------------------------------------------------------
9.5 — cable(pts, r, mat, seg)
--------------------------------------------------------------------------
  function cable(pts: THREE.Vector3[], r: number, mat: THREE.Material, seg = 40): THREE.Mesh {
    const curve = new THREE.CatmullRomCurve3(pts, false, 'catmullrom', 0.5);
    return new THREE.Mesh(new THREE.TubeGeometry(curve, seg, r, 8, false), mat);
  }

Smooth tube along a hand-authored control-point path. For cables,
hoses, swept-extrude pipes, anything that has to follow a non-straight
route. The 0.5 centripetal parameterization is the safest default.

--------------------------------------------------------------------------
9.6 — weldRing(at, dir, tubeR, mat)
--------------------------------------------------------------------------
  function weldRing(at: THREE.Vector3, dir: THREE.Vector3, tubeR: number, mat: THREE.Material): THREE.Mesh {
    const geo = new THREE.TorusGeometry(tubeR * 1.06, tubeR * 0.26, 10, 32);
    const mesh = new THREE.Mesh(geo, mat);
    mesh.quaternion.setFromUnitVectors(new THREE.Vector3(0, 0, 1), dir.clone().normalize());
    mesh.position.copy(at);
    return mesh;
  }

A torus band wrapping a tube of radius `tubeR`, oriented so its
hole-axis is along `dir`. Use for visible weld beads at frame joints
(the BMX example puts one at every tube joint to read "welded steel
frame", not "plastic model kit").

--------------------------------------------------------------------------
9.7 — decalQuad(tex, w, h, fallbackColor)
--------------------------------------------------------------------------
  function decalQuad(tex: THREE.CanvasTexture | null, w: number, h: number, fallbackColor = '#888888'): THREE.Mesh {
    const mat = new THREE.MeshPhysicalMaterial({
      map: tex ?? undefined,
      color: tex ? new THREE.Color('#ffffff') : new THREE.Color(fallbackColor),
      transparent: true, roughness: 0.25, clearcoat: 0.6,
      depthWrite: false, polygonOffset: true, polygonOffsetFactor: -2, envMapIntensity: 0.6,
    });
    return new THREE.Mesh(new THREE.PlaneGeometry(w, h), mat);
  }

A flat transparent panel that displays a canvas texture. Used for
all painted decals, stencils, logos, labels. The polygonOffset
prevents z-fighting when the decal sits flush on a curved surface.

================================================================================
PART 10 — COLOR & PALETTE DISCIPLINE
================================================================================

The JSON/JS spec's PART 26 (advanced model quality) and PART 50
(material mapping) translate to the TS path as direct discipline
on the palette constants. Follow the same rules as the JSON/JS path:

  - Define a `COL` (or named-color) constant block at the top of
    the file with every color in the model.
  - Sample the MIDTONE of each region, not highlights or shadows.
  - Match each region's finish to a PART 7 recipe by its actual
    visual behavior.
  - Don't add colorVariation / toneVariant by default — those are
    for cases where the reference CLEARLY shows a panel-shade
    variation, not as automatic decoration.
  - Stay under ~10-15 distinct colors per model. More than that
    reads as visual noise; fewer than 4 reads as flat / unfinished.

The shotgun example uses 14 named color constants; the BMX example
uses 13. Both read as visually rich but disciplined.

================================================================================
PART 11 — PROPORTIONS & MODELING DISCIPLINE
================================================================================

The JSON/JS spec's PART 20 (modeling guidance), PART 26 (advanced
model quality), and PARTs 36-45 (referential integrity, pose, held
props, garments) translate as MODELLING PRINCIPLES, not field names.
The intent is identical:

  - PART 20 — recognize the silhouette first, then secondary forms,
    then surface detail. Don't under-build ("low poly fox" is a
    complete brief, not permission to ship 5 cubes).
  - PART 26 — measure proportions from a real reference; default
    to realistic but PRESERVE deliberate stylization.
  - PART 36-45 — every part belongs to something (no floating
    props); limbs are continuous meshes from joint to joint;
    terminal attachments (hands, feet, cuffs) attach to the limb,
    not float on their own; default pose is RELAXED (not T-pose);
    held props attach to the hand; garments need straps and overlap,
    not just flat panels.
  - PART 26.6/26.10 — contact shadows where two surfaces meet;
    secondary detail (panel lines, rivets, stitching, decals) on
    every visible large flat surface.
  - PART 48-51 — universal style lock, measured proportions, material
    mapping, pre-output + post-render fidelity gate. These fire on
    every render and apply to TS output too.

The single most common modeling failure in TS output is FLOATING
PARTS — a hand that doesn't attach to a forearm, a barrel that
floats in front of a receiver, a tyre that hovers above a wheel
hub. The geometry primitives don't enforce connectivity; the AI
has to. Use the `tube(a, b, …)` and `cable(pts, …)` helpers from
PART 9 to physically connect parts that should be one continuous
form, and use the `attachTo` / `parent.add()` pattern from Three.js
to make parts move together when the host rig animates a parent.

--------------------------------------------------------------------------
11.1 — ORGANIC CONTINUOUS-MASS FORMS: NO NATIVE METABALL EQUIVALENT (v7.9)
--------------------------------------------------------------------------
The JSON/JS spec's PART 61 documents a decision framework for soft,
sculpted, continuous references (a person, an animal, a blob, anything
that reads as ONE unbroken mass rather than distinct hard-surface
parts): use "sdf_blob" with multiple small balls in a line per limb, so
marching cubes produces one seamless mesh instead of separate primitives
that only ever look glued together (PART 61.1's core problem — two
Mesh objects positioned to touch NEVER actually fuse, in this renderer
or in plain Three.js, regardless of format). That core problem applies
here too, but the fix does not translate directly, because this path
has NO metaball/marching-cubes builtin and NO CSG (PART 1's note: "no
CSG, no decals, no instance dedup, no fidelity gate — none of that
applies to hand-authored code", quoted again at PART 18). Three real
options, in order of
preference:
  1. Prefer authoring that ONE reference as JSON/JS instead of TS. If a
     soft continuous-mass figure is the actual deliverable, PART 61's
     sdf_blob technique is a first-class, already-verified feature on
     that path and gives you real marching-cubes output for free; there
     is no equivalent shortcut here.
  2. Hand-roll a marching-cubes-style BufferGeometry directly (PART 3.6,
     LAST RESORT there too) if the model must stay TS — e.g. by
     evaluating your own metaball field over a grid and building
     vertices/faces from it. This is real work with no helper in PART 9
     to lean on, and the result loses the inspector's part-list
     navigation, so only do this when a TS deliverable is a hard
     requirement.
  3. Fake a "single mass" READ without literal mesh fusion: use one
     continuous LatheGeometry/TubeGeometry/CatmullRomCurve3 threaded
     through the whole torso-to-limb path (PART 3.4/3.5) so at least
     that path is genuinely one mesh, then rely on tight "overlap"-style
     oversizing (PART 10's palette-discipline equivalent — size
     adjoining parts 0.04-0.08 units oversized, same rule of thumb as
     PART 26.5 on the JSON/JS side) plus matching materials/shading to
     minimize the visible seam where a genuinely separate part (e.g. a
     head sphere) meets it. This is a visual approximation, not an
     actual fix — don't present it as equivalent to option 1's real
     merge when the seam matters at close range.
For a hard-surface reference that needs to read as one mesh (not
organic/sculpted), there is still no CSG here either — approximate with
tightly-overlapping primitives and matching materials, same caveat as
above, or move that model to the JSON/JS path where PART 10's boolean
union is real.

CAVEAT — RIG-TEST / EXTERNAL-VIEWER EXPORT (see PART 30.7): whichever
option you pick above (thread a continuous Lathe/Tube through the whole
torso-to-limb path, or approximate with tightly-overlapping primitives),
never let it collapse the ENTIRE model into one mesh. Option 3's "one
continuous mesh" is meant for a SINGLE limb or panel run at most — the
head, the torso, and every other limb must still come out of your
factory as separate THREE.Mesh objects. A whole-model single mesh looks
fine in this renderer's own viewport but leaves the exported .glb with
exactly one exportable part, which fails external rig-test viewers
outright even though this renderer has no rig-test mode of its own to
catch it locally.

PART 12 — VALIDATION CHECKLIST (run through silently before output)
================================================================================

This is the TS-path equivalent of PART 21 of the JSON/JS spec. If the
model has joints/limbs/articulation, also run the addendum in PART
30.6 (rigging, animation & export).
Run through it silently and fix any check before emitting the file.

  SHAPE / CONTRACT
  [ ] File is a single ES module that imports THREE (PART 1.1)
  [ ] Exactly one (or one clearly-default) `export function createXxxModel(...)` (PART 1.2)
  [ ] Factory returns a THREE.Object3D with at least one descendant mesh
  [ ] Options interface declares `scale?`, `shadows?`, `wireframe?` at minimum
  [ ] root.userData.sculptRuntime is populated and typed (PART 6.1)
  [ ] (If animated) root.userData.tick is a `(dt, elapsed) => void` function (PART 5.1)
  [ ] (If skeletal) root.userData.sculptRuntime.animations has { clips, mixer } (PART 5.6)
  [ ] (If custom-runtime) root.userData.<ns>._root points at the model root (PART 5.7)
  [ ] No `import.meta`, `process.env`, `Buffer`, `require`, `eval` (PART 1.5)
  [ ] `tsc --strict --target ES2020 --module ESNext --moduleResolution bundler` passes

  GEOMETRY
  [ ] Every part is in a coordinate-frame that makes sense relative to its parent
  [ ] No part is FLOATING (not attached to anything) — use tube/cable/parent.add (PART 11)
  [ ] No part is INSIDE another part it shouldn't intersect (sphere embedded in a box, etc.)
  [ ] No obvious gaps (limb that doesn't reach the torso, tyre floating above the rim)
  [ ] Symmetric parts actually are symmetric (mirror across the model's symmetry plane, PART 27.7)
  [ ] The model is COMPLETE from every angle — the back is built, not just the front
  [ ] Continuous-sculpt topology uses SDF + marching cubes (PART 3.8) — never stacked
      touching primitives (PART 11.1)
  [ ] Cut-outs use Shape + ExtrudeGeometry with holes[] (PART 3.7), NOT three-bvh-csg
  [ ] Repetitive geometry (4+ identical parts) uses InstancedMesh (PART 28.5)

  MATERIALS
  [ ] Every distinct visible material has color, roughness, metalness
  [ ] PBR channels are not aliased (no "dark gold = baseColor * 0.5")
  [ ] Emissive things actually have emissive + emissiveIntensity > 1
  [ ] Glass / transmission materials have a non-zero envMapIntensity
  [ ] Flat-shaded style uses MeshBasicMaterial / MeshToonMaterial, not a physically-lit preset
  [ ] Physical material extensions (transmission, sheen, anisotropy, clearcoat) are
      USED only when the visual justifies the cost — don't ship a fully flat surface
      with clearcoat: 0.85
  [ ] Glow / bloom elements use SpriteMaterial + AdditiveBlending + depthWrite:false
      (PART 28.3), not emissive: 0xffffff + emissiveIntensity: 999
  [ ] onBeforeCompile shaders always set customProgramCacheKey() (PART 28.1)
  [ ] Converted-colour-into-GLSL uses .convertSRGBToLinear() on the source color

  SILHOUETTE / PROPORTIONS
  [ ] Silhouette is recognizable as the subject from at least the 3/4 front view
  [ ] Proportions are intentional (measured from a reference or deliberately stylized)
  [ ] No part is wildly out of scale with its neighbours (a giant head on a tiny body,
      a barrel twice the length of the receiver, etc.)
  [ ] Pose is RELAXED, not T-pose, unless the subject is specifically at attention

  SECONDARY DETAIL
  [ ] Every visible large flat surface has at least one piece of detail (panel line,
      decal, screw, vent, trim, colour break) — never a blank wall
  [ ] Decals read the right way up from the default camera angle
  [ ] No floating or duplicated detail (a screw that appears in two places, a decal
      that wraps the wrong way)
  [ ] Hinged elements live in a pivot Group (PART 27.1), not directly in the body
  [ ] Skinned / rigged parts have userData.animationRole set (PART 6.7.3)

  VFX (if applicable)
  [ ] tick uses `dt` for decay, `elapsed` for periodic motion
  [ ] All mutable per-frame state lives in a single `state` object
  [ ] Spawned actors use a pre-allocated pool, no per-frame `new`
  [ ] Per-frame allocations are zero (or strictly bounded)
  [ ] tick never throws — wrap external calls in try/catch
  [ ] Cloth / hair / antennae use spring-damper lag (PART 27.4), not direct snap
  [ ] Aim / look-at constraints slerp from previous quaternion (PART 27.5)
  [ ] Face decals on continuous-sculpt bodies use surface-follow with
      depthTest:false + renderOrder 3-4 + castShadow:false (PART 27.6)

  RUNTIME HOOKS
  [ ] sculptRuntime.nodes names match the variable names in the geometry code
  [ ] Sockets have name + userData.socketType ('muzzle' | 'mount' | 'spawn' | 'attach')
  [ ] Destruction groups are named for what they break into
  [ ] All Object3Ds in sculptRuntime are reachable from root (no orphans)
  [ ] Action hooks (sculptRuntime.actions / sculptRuntime.animation) are
      no-arg-callable functions that drive meaningful state changes
  [ ] Per-mesh metadata (sculptComponent, actionProfile) is consistent
      with the part's actual role in the model
  [ ] AnimationMixer is reachable from root.userData OR
      root.userData.sculptRuntime.animations (PART 5.6) — the renderer
      won't find a mixer living only on a deeply-nested child mesh

PART 13 — MINIMAL WORKED EXAMPLE
================================================================================

The smallest valid .ts factory, copy-paste-ready, that satisfies
the output contract. Loads as `createCubeModel`, returns a single
rounded box centred at origin with runtime hooks populated.

  import * as THREE from 'three';
  import { RoundedBoxGeometry } from 'three/examples/jsm/geometries/RoundedBoxGeometry.js';

  /**
   * Minimal worked example: a single rounded box.
   * Coordinate frame: standard — +y up, origin at the centre of the box.
   * Demonstrates: factory signature, options interface, sculptRuntime, applyShadow.
   */
  export interface CubeModelOptions {
    scale?: number;
    shadows?: boolean;
    wireframe?: boolean;
  }

  export type CubeModelRuntime = {
    nodes: Record<string, THREE.Object3D>;
  };

  export function createCubeModel(options: CubeModelOptions = {}): THREE.Group {
    const scale    = options.scale ?? 1;
    const shadows  = options.shadows ?? true;
    const wireframe = options.wireframe ?? false;

    const root = new THREE.Group();
    root.name = 'Minimal Cube';

    const mat = new THREE.MeshStandardMaterial({
      color: 0xc8763a, roughness: 0.45, metalness: 0.05,
    });
    const mesh = new THREE.Mesh(
      new RoundedBoxGeometry(1, 1, 1, 4, 0.05),
      mat,
    );
    if (wireframe && 'wireframe' in mat) (mat as THREE.MeshStandardMaterial).wireframe = true;
    if (shadows) { mesh.castShadow = true; mesh.receiveShadow = true; }
    root.add(mesh);

    root.userData.sculptRuntime = {
      nodes: { box: mesh },
    } satisfies CubeModelRuntime;

    root.scale.setScalar(scale);
    return root;
  }

That's the smallest thing that passes PART 12. A realistic model
extends this skeleton with: per-region materials (PART 7),
procedural textures (PART 8), helper functions (PART 9), tick
for animation (PART 5), and more populated sculptRuntime (PART 6).

PART 14 — A REAL WORKED EXAMPLE (the shotgun, abridged)
================================================================================

See the full file createIssacaShotgunModel.ts (the example shipped
with this spec) for the canonical pattern. Reading it end-to-end
is the fastest way to internalize everything in PARTs 1-12. Key
landmarks to study in order:

  1.  JSDoc header (PART 1.4) — the file's identity statement.
  2.  IssacaShotgunOptions interface (PART 1.2) — three standard
      options, one model-specific.
  3.  Color constants block (PART 10) — every color named.
  4.  mulberry32 + makeCanvas + hex (PART 8.1-8.2) — the standard
      texture helpers.
  5.  makeMarbleTexture, makeScratchBump, makeKnurlBump, … — the
      ten-or-so procedural texture recipes (PART 8.3). These are
      copy-paste-modify, not invented from scratch.
  6.  xCyl, v, UP — the geometry helpers (PART 9.2-9.3).
  7.  MATERIALS block — every material in the model, named,
      tuned. Notice how materials are grouped by region, not by
      Three.js class (the steel family has 3 variants for
      highlight / dark / standard).

PART 14B — A v1.3 WORKED EXAMPLE (action hooks + tick + sculptRuntime) [v1.3]
================================================================================

The smallest "do something interactive" factory — a button you can
click in the renderer's Action Hooks panel, with a tick for the
visible state change. Demonstrates PART 5 (tick), PART 6 (full
optional sculptRuntime), PART 6.7 (per-mesh metadata), PART 27.1
(pivot group), PART 28.3 (additive glow sprite). Copy-paste-ready.

  import * as THREE from 'three';
  import { RoundedBoxGeometry } from 'three/examples/jsm/geometries/RoundedBoxGeometry.js';

  /**
   * A power button: a rounded box with a glowing LED that toggles
   * on click. Coordinate frame: standard — +y up, origin at the
   * button's centre.
   * Demonstrates: action hooks, tick animation, additive sprite,
   * pivot group, per-mesh metadata, full optional sculptRuntime.
   */
  export interface PowerButtonOptions {
    scale?: number;
    shadows?: boolean;
  }

  const COL = {
    body: 0x2b2e33, bodyDark: 0x14161a,
    ledOn: 0x36d97c, ledOff: 0x2a1f24,
    glowOn: 0x7fffb0, glowOff: 0x181018,
  };

  function makeGlowSprite(color: number, size: number, opacity = 1): THREE.Sprite {
    const cv = document.createElement('canvas');
    cv.width = cv.height = 128;
    const ctx = cv.getContext('2d')!;
    const g = ctx.createRadialGradient(64, 64, 0, 64, 64, 64);
    g.addColorStop(0,    'rgba(255,255,255,1)');
    g.addColorStop(0.22, 'rgba(255,255,255,0.7)');
    g.addColorStop(0.55, 'rgba(255,255,255,0.16)');
    g.addColorStop(1,    'rgba(255,255,255,0)');
    ctx.fillStyle = g;
    ctx.fillRect(0, 0, 128, 128);
    const tex = new THREE.CanvasTexture(cv);
    return new THREE.Sprite(new THREE.SpriteMaterial({
      map: tex, color, opacity, transparent: true,
      blending: THREE.AdditiveBlending,
      depthWrite: false,
    }));
  }

  export function createPowerButtonModel(options: PowerButtonOptions = {}): THREE.Group {
    const scale   = options.scale   ?? 1;
    const shadows = options.shadows ?? true;

    const root = new THREE.Group();
    root.name = 'Power Button';

    // --- body
    const bodyMat = new THREE.MeshStandardMaterial({
      color: COL.body, roughness: 0.55, metalness: 0.4,
    });
    const body = new THREE.Mesh(
      new RoundedBoxGeometry(1.0, 0.32, 0.6, 4, 0.05),
      bodyMat,
    );
    body.castShadow = shadows;
    body.receiveShadow = shadows;
    body.userData.sculptComponent = {
      id: 'body', parentId: '', role: 'shell',
      sockets: [],
    };
    body.userData.actionProfile = { canGlow: true, canRecenter: true };
    root.add(body);

    // --- LED pivot (PART 27.1)
    const ledPivot = new THREE.Group();
    ledPivot.position.set(0, 0, 0.31);  // sits on the front face
    root.add(ledPivot);

    const ledMat = new THREE.MeshStandardMaterial({
      color: COL.ledOff, emissive: new THREE.Color(COL.ledOff),
      emissiveIntensity: 0.4, roughness: 0.3, metalness: 0,
    });
    const led = new THREE.Mesh(
      new THREE.SphereGeometry(0.05, 16, 12),
      ledMat,
    );
    led.userData.sculptComponent = {
      id: 'led', parentId: 'body', role: 'led', sockets: [],
    };
    ledPivot.add(led);

    const glow = makeGlowSprite(COL.glowOff, 0.3, 0);
    glow.position.copy(led.position).add(new THREE.Vector3(0, 0, 0.01));
    ledPivot.add(glow);

    // --- state + actions
    const state = { on: false, pulse: 0 };
    const setOn = (next: boolean) => {
      state.on = next;
      led.material.color.set(next ? COL.ledOn : COL.ledOff);
      led.material.emissive.set(next ? COL.ledOn : COL.ledOff);
      (glow.material as THREE.SpriteMaterial).color.set(
        next ? COL.glowOn : COL.glowOff,
      );
      state.pulse = 1;     // one-shot scale pulse on change
    };
    const toggle = () => setOn(!state.on);
    const reset   = () => setOn(false);

    // --- tick: pulse + breathe
    const tick = (dt: number, elapsed: number) => {
      state.pulse = Math.max(0, state.pulse - dt * 4);
      const breathe = 1 + Math.sin(elapsed * 1.6) * 0.05;
      const scale = (state.on ? 1.0 + state.pulse * 0.4 : 1.0) * breathe;
      led.scale.setScalar(scale);
      glow.scale.setScalar(0.3 * scale);
      (glow.material as THREE.SpriteMaterial).opacity =
        (state.on ? 0.6 : 0.05) * (0.85 + Math.sin(elapsed * 4) * 0.15);
    };

    // --- runtime
    root.userData.tick = tick;
    root.userData.sculptRuntime = {
      nodes: { body, led, ledPivot },
      meshes: { body, led },
      sockets: {},
      colliders: {},
      destructionGroups: {},
      materials: { bodyMat, ledMat },
      actions: { toggle, reset, setOn },       // PART 6.1B
      animation: { toggle, reset, setOn },     // alias
      vfx: { glow },
    };
    root.userData.provenance = {
      route: 'code-only procedural',
      exactnessTier: 'stylized-low-poly',
      inferred: [],
    };
    root.userData.sculptSpec = {
      source: 'inline', reference: 'inline', style: 'flat-low-poly', heightUnits: 0.32,
    };
    root.userData.actionReadiness = {
      note: 'sculptRuntime.actions.{toggle, reset, setOn} surface as buttons.',
    };

    root.scale.setScalar(scale);
    return root;
  }

  export function createPowerButtonLookDevLights(): THREE.Group {
    const g = new THREE.Group();
    const key = new THREE.DirectionalLight(0xffffff, 2.5);
    key.position.set(3, 5, 4);
    g.add(key);
    g.add(new THREE.HemisphereLight(0xffffff, 0x444444, 0.6));
    return g;
  }

Drop this into the page; the renderer's Action Hooks panel will show

PART 15 — COMMON MISTAKES (read these, don't make them)
================================================================================

  ✗ Forgetting to set root.name. The inspector falls back to
    "Object3D" and the user can't tell which model is which.
  ✗ Not populating sculptRuntime. The inspector tree is empty,
    the model looks "complete" but nothing is interactively
    reachable. PART 6 is required, not optional.
  ✗ Using `Mesh.material.opacity = …` without `material.transparent = true`
    (and without the `as` cast, PART 2.1).
  ✗ Returning `root` but having all geometry be children of an
    internal "assembly" group you forgot to add. The renderer
    computes the bounding box from `root`'s children; an empty
    root looks like an empty scene.
  ✗ Using a real `require('three')` instead of `import * as THREE
    from 'three'`. The renderer rewrites ES imports; CommonJS
    require() isn't recognised and the module fails to load.
  ✗ Using Date.now() / performance.now() / setInterval inside
    the factory for animation. Use the `tick(dt, elapsed)`
    contract; the renderer owns time.
  ✗ Trying to use `import.meta.url` to find the .ts file's
    directory. The renderer doesn't expose a base URL for the
    transpiled file; resolve any same-origin assets via
    `window.location.href` instead.
  ✗ Spawning per-frame actors with `new` instead of pooling them.
    After 30 seconds at 60fps, you've allocated 1800 objects and
    the renderer is GC-stuttering.
  ✗ Using a `THREE.Group` for a node that needs to be parented
    to a specific socket. Sockets are the host's responsibility;
    a `THREE.Object3D` (no children, no transform children) is
    the lightweight choice for a socket placeholder.
  ✗ Forgetting `tex.needsUpdate = true` on a CanvasTexture. The
    texture uploads to the GPU only on the first render; without
    needsUpdate, a texture created AFTER the first frame is blank.
  ✗ Setting `colorSpace = THREE.SRGBColorSpace` on a bumpMap
    (greyscale heightfield). SRGB encoding gamma-curves the
    heightfield and the bump looks wrong. Bump maps must be
    NoColorSpace (the default); albedo / decal maps must be
    SRGBColorSpace. The PART 8.2 helper sets this automatically.
  ✗ Re-creating materials on every frame inside `tick`. Build
    them once in the factory, look them up by name in tick.
  ✗ Setting root.userData.sculptRuntime AFTER the model is added
    to the scene. Some inspectors only walk the tree at attach
    time; set it before returning.
  ✗ Naming two different parts the same thing in sculptRuntime.nodes.
    Record semantics — last write wins, the inspector only sees
    the second one.
  ✗ Using a 0x-prefixed hex literal for emissive (`emissive: 0xff0000`).
    Use `emissive: new THREE.Color(0xff0000)`. Three.js's TypeScript
    types for the property accept a Color | string | number but
    the runtime conversion is finicky in older versions.
  ✗ [v7.9] Trying to fuse a soft, continuous-mass reference (a sculpted
    figure with no hard panel lines) out of separate touching Meshes and
    expecting them to read as one surface. They never do — see PART
    11.1: either move that model to the JSON/JS path (real sdf_blob
    support) or hand-roll a marching-cubes BufferGeometry; positioning
    tweaks alone won't fix it here any more than on the blueprint path.
  ✗ [v1.3] Using a custom-runtime `update(elapsed)` AND a `userData.tick`
    for the same model. Pick one — the renderer will skip the
    custom-runtime when tick exists. PART 5.7's `_root` back-reference
    is only consulted when there's no tick.
  ✗ [v1.3] Calling `mixer.update(dt)` in `userData.tick` AND publishing
    the mixer under `sculptRuntime.animations.mixer`. The renderer
    silences the factory's mixer on mount so the in-app player wins;
    if your tick also calls mixer.update() with stopped actions, you
    get a stuttering pose. Either omit the tick (let the renderer
    auto-tick the mixer) or stop the mixer's actions in your tick
    (the factory owns the clock).
  ✗ [v1.3] Forgetting `customProgramCacheKey()` on a material that
    uses onBeforeCompile. Two materials with different onBeforeCompile
    bodies that don't set a cache key share a compiled program and
    you get the wrong shader for at least one of them. PART 28.1.
  ✗ [v1.3] Stringifying an sRGB colour directly into GLSL (without
    `convertSRGBToLinear()`). The `mix` in the injected shader then
    blends in sRGB space and the result washes out. PART 28.1.
  ✗ [v1.3] Hinging a part without a pivot Group (PART 27.1). A bare
    `mesh.rotation.x = …` rotates around the mesh's local origin, not
    around a hinge. The lid pivots at the back-top edge; rotate the
    whole lid-from-hinge Group, not the lid itself.
  ✗ [v1.3] Trying to animate a part's position with `mesh.position = …`
    when it's parented to a moving part. The position is local to the
    parent — drive it via a captured rest pose + lerp (PART 27.3) or
    via a spring-damper (PART 27.4), not via direct writes.
  ✗ [v1.3] Mirror with `scale.x = -1` AND no winding-order check.
    A flipped-mesh with `side: DoubleSide` shows the inside; with
    `side: FrontSide` you get back-face culling that hides the
    flipped half. PART 27.7's full rules.
  ✗ [v1.3] Setting `emissive: 0xffffff` + `emissiveIntensity: 999`
    to fake a glow. The renderer will tonemap it back to white and
    you get a hot pixel, not a soft halo. Use a SpriteMaterial with
    AdditiveBlending (PART 28.3) or a toneMapped: false ShaderMaterial
    with a soft gradient.
  ✗ [v1.3] Spawning `new` THREE.Object3Ds in tick() to add particles.
    After 30 seconds at 60 fps you've allocated 1800 objects and
    the renderer is GC-stuttering. PART 5.3's pool pattern.

PART 18 — TS PIXEL-PERFECT FIDELITY PASS (per pixel_perfect_3d_techniques.txt,
          Final Master Edition, 2026-07-21)
================================================================================
A companion reference file, pixel_perfect_3d_techniques.txt, documents 17
techniques for the JSON/JS blueprint path in terms of DSL fields
("colorVariation", "cavityShading", "sculptStamp", etc.). None of those
fields exist in the TS path — a .ts factory is hand-authored Three.js code
that bypasses buildScene() entirely (PART 1 note: "no CSG, no decals, no
instance dedup, no fidelity gate — none of that applies to hand-authored
code"). This PART is the TS-native translation: the same visual techniques,
expressed as real Three.js code in this spec's own established style (PART
8's canvas-texture factory, PART 9's copy-paste helpers). Add these to your
PART 9 helper collection; nothing here changes the PART 1 output contract.

One honest exception, flagged up front rather than glossed over (matching
this spec's own practice of marking a technique ASPIRATIONAL when it
genuinely isn't achievable, rather than faking it): the JSON/JS path's
"eyeTrack": {"target":"camera"} works because the renderer's own module
scope has a direct reference to its `camera`. A .ts factory's `tick(dt,
elapsed)` (PART 5.1) receives exactly those two arguments — no camera,
no scene reference — because the factory is dynamic-imported as an
isolated module with no access to the host page's internal state. True
camera-tracking eyes are therefore NOT implementable in the TS path as
written today. 18.7 below gives the honest, achievable substitute.

--------------------------------------------------------------------------
18.1 — THE "PIXEL GRID" TECHNIQUE (new helper)
--------------------------------------------------------------------------
For ultra-detailed focal micro-features (an iris's fine detail, a small
emblem/logo, an instrument-panel grille) too fine for one primitive or one
canvas texture to sell, build a grid of tiny individual meshes rather than
reaching for a bigger flat panel:

  function pixelGrid(
    cols: number, rows: number, cellSize: number, gapRatio: number,
    baseColor: number, rand: () => number,
    toneStep: (col: number, row: number) => 'light' | 'mid' | 'dark',
  ): THREE.Group {
    const grid = new THREE.Group();
    const geo = new THREE.BoxGeometry(cellSize, cellSize, cellSize * 0.5);
    const pitch = cellSize * (1 + gapRatio);
    const base = new THREE.Color(baseColor);
    for (let r = 0; r < rows; r++) {
      for (let c = 0; c < cols; c++) {
        const tone = toneStep(c, r);
        const shade = tone === 'light' ? 1.12 : tone === 'dark' ? 0.85 : 1.0;
        // jitter (mulberry32, PART 8.1) mimics colorVariation's per-face
        // noise; +/-4% keeps it a "hand-painted" jitter, not visible noise
        const jitter = 0.96 + rand() * 0.08;
        const col = base.clone().multiplyScalar(shade * jitter);
        const mat = new THREE.MeshStandardMaterial({ color: col, roughness: 0.5, metalness: 0.05 });
        const cell = new THREE.Mesh(geo, mat);
        cell.position.set((c - (cols - 1) / 2) * pitch, (r - (rows - 1) / 2) * pitch, 0);
        grid.add(cell);
      }
    }
    return grid;
  }

  // usage — a small chest-emblem-scale grid, seeded so it's stable/diffable:
  const emblemRand = mulberry32(0x7a11e5);
  const emblem = pixelGrid(8, 8, 0.045, 0.12, 0xc8102e, emblemRand,
    (c, r) => ((c + r) % 3 === 0 ? 'light' : (c + r) % 3 === 1 ? 'mid' : 'dark'));
  emblem.position.set(0, 1.1, 0.31);
  chestGroup.add(emblem);   // local coords relative to its real parent Group — see 18.5

SCALE cellSize to the actual feature — an iris's fine detail inside an
eyeball that's itself only ~0.08-0.15 units across calls for ~0.006-0.01
cellSize, not the 0.045 shown above (sized for a chest-emblem/instrument-
panel-scale feature). Reserve this for genuinely focal detail on a hero
subject; PART 8's canvas textures remain the right, far cheaper tool for
anything larger than a few dozen resolvable cells or on a non-focal
surface.

--------------------------------------------------------------------------
18.2 — HERO-QUALITY CORE GEOMETRY (restates PART 3 item 2 as a hard rule)
--------------------------------------------------------------------------
PART 3.1 already says RoundedBoxGeometry's radius should go "thicker for
hero geometry" — promoted here to a hard rule for two specific object
categories: (1) a character's core body mass (torso/head), and (2) a hero
or focal prop (the one part the composition is built around). For both:
reach for RoundedBoxGeometry(w, h, d, segments, radius) — never a bare
BoxGeometry — with radius roughly 0.02-0.05 relative to the part's own
scale (PART 3.1's "thicker for hero geometry" made concrete) and enough
segments (3-4 minimum) that the round is actually visible per-facet
rather than reading as a single smoothed blob. This renderer's import map
doesn't ship a general Loop-subdivision utility, so extra resolvable
density beyond what the radius/segments give you is achieved the honest
way available in this path: more geometry (an added raised sub-panel, a
seam plate) rather than a subdivision pass this format doesn't have on
hand. Secondary/background parts don't need this — spend the extra
vertex/material budget on what the composition is actually about (PART
11's framing).

--------------------------------------------------------------------------
18.3 — colorVariation-EQUIVALENT: PER-VERTEX COLOR JITTER (new helper;
       reconciles with PART 10's "don't add by default" rule)
--------------------------------------------------------------------------
PART 10 is right that colorVariation/toneVariant shouldn't be automatic
decoration on every part — stay with that rule for ordinary parts. For a
HERO character's skin/core surface specifically, where the reference
technique is deliberately calling for a hand-painted, not flat-plastic,
read, apply real per-vertex color jitter directly to the BufferGeometry:

  function applyVertexColorJitter(geo: THREE.BufferGeometry, baseColor: THREE.Color, amount = 0.06, seed = 0x7a11e5): void {
    const rand = mulberry32(seed);
    const pos = geo.attributes.position;
    const colors = new Float32Array(pos.count * 3);
    const c = new THREE.Color();
    for (let i = 0; i < pos.count; i++) {
      const jitter = 1 + (rand() - 0.5) * 2 * amount;   // amount 0.04-0.08 — same sweet spot as the JSON/JS spec
      c.copy(baseColor).multiplyScalar(jitter);
      colors[i * 3] = c.r; colors[i * 3 + 1] = c.g; colors[i * 3 + 2] = c.b;
    }
    geo.setAttribute('color', new THREE.BufferAttribute(colors, 3));
  }
  // material must opt in: new THREE.MeshStandardMaterial({ vertexColors: true, ... })

Use amount 0.04-0.08 — the same range the JSON/JS spec settled on for the
same visual reason (noticeable hand-painted texture below ~0.04, dirty/
noisy above ~0.08). Reserve this for a hero subject's core surfaces, per
PART 10's own "not automatic decoration" framing — this is a deliberate
fidelity choice on the one subject the composition is about, not a
default applied everywhere.

--------------------------------------------------------------------------
18.4 — cavityShading-EQUIVALENT: CURVATURE-BASED FAKE AO (new helper)
--------------------------------------------------------------------------
  function applyCavityShading(geo: THREE.BufferGeometry, strength = 0.4): void {
    geo.computeVertexNormals();
    const pos = geo.attributes.position, norm = geo.attributes.normal;
    const idx = geo.index;
    if (!idx) return;
    const neighborSum = new Float32Array(pos.count * 3);
    const neighborCount = new Int32Array(pos.count);
    for (let t = 0; t < idx.count; t += 3) {
      const tri = [idx.getX(t), idx.getX(t + 1), idx.getX(t + 2)];
      tri.forEach((a) => tri.forEach((b) => {
        if (a === b) return;
        neighborSum[a * 3] += pos.getX(b); neighborSum[a * 3 + 1] += pos.getY(b); neighborSum[a * 3 + 2] += pos.getZ(b);
        neighborCount[a]++;
      }));
    }
    const existing = geo.getAttribute('color') as THREE.BufferAttribute | undefined;
    const colors = existing ? (existing.array as Float32Array) : new Float32Array(pos.count * 3).fill(1);
    for (let i = 0; i < pos.count; i++) {
      if (!neighborCount[i]) continue;
      const avgX = neighborSum[i * 3] / neighborCount[i], avgY = neighborSum[i * 3 + 1] / neighborCount[i], avgZ = neighborSum[i * 3 + 2] / neighborCount[i];
      const vx = pos.getX(i), vy = pos.getY(i), vz = pos.getZ(i);
      // vertex sitting BEHIND its neighborhood average, measured along its
      // own normal, is in a concave crease — darken it; a convex ridge
      // (in FRONT of the average) is left untouched, same asymmetry as
      // the JSON/JS spec's applyCavityShading.
      const dot = (vx - avgX) * norm.getX(i) + (vy - avgY) * norm.getY(i) + (vz - avgZ) * norm.getZ(i);
      const cavity = Math.max(0, -dot);
      const dark = 1 - Math.min(0.6, cavity * strength * 8);
      colors[i * 3] *= dark; colors[i * 3 + 1] *= dark; colors[i * 3 + 2] *= dark;
    }
    geo.setAttribute('color', new THREE.BufferAttribute(colors, 3));
  }
  // material must opt in: vertexColors: true — combine AFTER
  // applyVertexColorJitter (18.3) so cavity darkening multiplies on top of
  // the jitter rather than one silently overwriting the other's color attribute.

Use strength 0.3-0.5 for a visible crease/joint/panel-seam read — the same
range the JSON/JS spec recommends. Reserve for the same hero-surface cases
as 18.3, for the same PART 10 reason.

--------------------------------------------------------------------------
18.5 — ATTACHING DETAIL TO A ROTATED PARENT (no new mechanism — a
       structural advantage this path already has)
--------------------------------------------------------------------------
The JSON/JS spec needs "sideOf"/"sideToward" (its PART 37/57.4) because
its renderer adds every object to one FLAT list with no real parent-child
hierarchy, so a rotated parent's "top face" has to be recomputed by hand.
The TS path doesn't have this problem: `parentGroup.add(childMesh)` gives
the child a REAL place in the Three.js scene graph, so a child positioned
in the parent's LOCAL space (e.g. `child.position.set(0, halfHeight, 0)`
for "on top of the parent") automatically follows the parent's actual
rotation — Three.js's own matrix stack does the work sideOf/sideToward
exists to fake in the other path. The only way to reintroduce the JSON/JS
spec's drift bug here is to skip the hierarchy and position everything in
one shared WORLD-space coordinate system instead (computing an absolute
position by hand for a part that sits on a rotated parent) — don't do
that. Nest with real `.add()` calls and author child positions in that
parent's own local space, per PART 11's existing floating-parts guidance.

--------------------------------------------------------------------------
18.6 — NESTED FEATURE DEPTH FOR HERO EYES (new recommendation)
--------------------------------------------------------------------------
A single textured sphere (map/bump baked via PART 8's canvas-texture
factory) is a good, cheap default for any background character or
anything small-in-frame. For a HERO character specifically, build the eye
as genuinely separate nested Object3Ds instead — this path's Group
hierarchy makes this direct:

  const eyeSocket = new THREE.Mesh(socketGeo, socketMat);          // recessed base
  const eyeball = new THREE.Mesh(new THREE.SphereGeometry(0.045, 16, 12), eyeMat);
  eyeball.position.set(0, 0, 0.01);                                 // local to the socket
  eyeSocket.add(eyeball);
  const pupil = new THREE.Mesh(new THREE.CircleGeometry(0.014, 12), pupilMat);
  pupil.position.set(0, 0, 0.043);                                  // local to the eyeball
  eyeball.add(pupil);

This gives genuine parallax and a real cast shadow between the three
layers as the camera orbits — depth a single textured sphere cannot
produce, at the cost of 2-3 extra named nodes per eye (name and register
all three in sculptRuntime.nodes, PART 6.2). Flat single-sphere eyes
remain right for anything that isn't the focal subject.

--------------------------------------------------------------------------
18.7 — EYE "TRACKING": THE HONEST, ACHIEVABLE VERSION
--------------------------------------------------------------------------
As flagged in this PART's introduction, `tick(dt, elapsed)` (PART 5.1)
has no camera reference, so literally aiming an eye at the live camera
position is not implementable here. Two real, achievable substitutes,
both driven by `elapsed` the way PART 5.2's other periodic effects are:

  1. TRACK ANOTHER NAMED NODE IN THE SAME MODEL (fully achievable — this
     needs no camera, just a reference already in scope):
       const dir = new THREE.Vector3().subVectors(targetNode.position, eyeball.getWorldPosition(new THREE.Vector3()));
       eyeball.lookAt(eyeball.position.clone().add(dir));
     Good for eyes tracking a held prop, another character node, or any
     in-model point — a real, working "eyeTrack": target.

  2. IDLE GLANCE OSCILLATION (a substitute "reads as alive" effect, not a
     camera-tracking equivalent — say so if you use it):
       const glanceAngle = Math.sin(elapsed * 0.35) * THREE.MathUtils.degToRad(8);
       eyeball.rotation.y = restRotationY + glanceAngle;
     A small (roughly ±8°), slow periodic swivel around the eye's own
     rest orientation. This reads as "alive" in a still render or a
     fixed-camera view, but — unlike the JSON/JS path's real eyeTrack —
     it will NOT follow the viewer when the model is orbited. Document
     this limitation in the file's JSDoc header rather than silently
     shipping an eye that looks like it should track but doesn't.

--------------------------------------------------------------------------
18.8 — PARALLAX OCCLUSION MAPPING (directly portable — same Three.js API)
--------------------------------------------------------------------------
Unlike the blueprint-specific fields above, POM is standard Three.js
material API (`onBeforeCompile`), so the renderer's own implementation
ports directly into a factory with no translation needed:

  function applyParallaxOcclusion(mat: THREE.MeshStandardMaterial, heightMap: THREE.Texture, strength = 0.03): void {
    mat.onBeforeCompile = (shader) => {
      shader.uniforms.pomHeightMap = { value: heightMap };
      shader.uniforms.pomStrength = { value: THREE.MathUtils.clamp(strength, 0, 0.15) };
      shader.fragmentShader = shader.fragmentShader
        .replace('#include <common>', '#include <common>\nuniform sampler2D pomHeightMap;\nuniform float pomStrength;')
        .replace('#include <map_fragment>', `
          {
            vec3 pomT = normalize(dFdx(-vViewPosition) * dFdy(vUv).t - dFdy(-vViewPosition) * dFdx(vUv).t);
            vec3 pomB = normalize(-dFdx(-vViewPosition) * dFdy(vUv).s + dFdy(-vViewPosition) * dFdx(vUv).s);
            vec3 pomViewTS = normalize(vec3(dot(-vViewPosition, pomT), dot(-vViewPosition, pomB), dot(-vViewPosition, normalize(vNormal))));
            vec2 pomDeltaUV = (pomViewTS.xy / max(0.2, abs(pomViewTS.z))) * pomStrength / 10.0;
            vec2 pomUV = vUv; float pomLayer = 0.0; float pomH = 1.0 - texture2D(pomHeightMap, pomUV).r;
            for (int i = 0; i < 10; i++) {
              if (pomLayer >= pomH) break;
              pomUV -= pomDeltaUV;
              pomH = 1.0 - texture2D(pomHeightMap, pomUV).r; pomLayer += 0.1;
            }
            vUv = pomUV;
          }
          #include <map_fragment>`);
    };
    mat.customProgramCacheKey = () => 'pom_' + strength.toFixed(3);
    mat.needsUpdate = true;
  }
  // usage: applyParallaxOcclusion(panelMat, bumpTextureAsHeightSource, 0.03);

Keep strength in 0.02-0.04 for the same reason as the JSON/JS spec's
57.7 — this renderer's fixed 10-step search shows visible texel-swimming
at grazing angles above roughly 0.05. Reuse whatever bump/height canvas
texture (PART 8.2) the material already has rather than authoring a
second one, so the POM depth stays consistent with the material's actual
normal/bump detail.

--------------------------------------------------------------------------
18.9 — SUBTLE ASYMMETRY FOR HAND-CRAFTED FEEL (new — this fork only; the
       Image-input fork already covers this via its own PART 17.3)
--------------------------------------------------------------------------
This spec currently has no equivalent of the JSON/JS path's asymmetry
mechanism at all. For a prompt-only build (no reference image to measure
a real pose from), add a small deliberate asymmetry to a hero character
rather than leaving every joint a perfect mirror:

  headPivot.rotation.z += THREE.MathUtils.degToRad(2.5);   // 2-3°, same range as the JSON/JS spec
  leftShoulderPivot.position.y -= 0.03;                     // 0.02-0.05 world units, human-scale character

Apply this directly to the Group pivots the pose is already built from
(PART 11) — there's no separate DSL block to populate here, it's just a
small deliberate offset on top of the otherwise-symmetric rig. Keep it in
the 2-3°/0.02-0.05-unit range (scale proportionally for a much larger/
smaller subject): enough to read as "alive," not enough to read as an
injury. A perfectly symmetrical reference/description (a product shot, a
creature explicitly described as symmetrical) shouldn't get invented
asymmetry — this is for otherwise-generic hero characters only.

--------------------------------------------------------------------------
18.10 — VALIDATION, TS-STYLE (restates PART 12 — no new checklist)
--------------------------------------------------------------------------
The JSON/JS path's validation log (scanForBadRefs / validateBlueprintSchema)
doesn't run on this path at all — the TS pathway bypasses buildScene()
entirely, so there is no separate schema validator to consult. The real
equivalent, already established in PART 12, is: `tsc --strict` compiling
clean, PLUS actually pasting the file into low_poly_3d.html and watching
the browser console — a bad import, a factory that throws, or a
`create*Model` name that doesn't match the required pattern surfaces
there as a real thrown error with a line number (the compiler's
diagnostics are on specifically so this works), not as a silent fallback.
Restated here only because the pixel-perfect guide singles out
validation as its closing point: for this path, "read the validation
log" means "read the console," and it's exactly as mandatory a last step
as PART 12 already says.

================================================================================
PART 27 — CONSTRAINTS (declarative + procedural) [v1.3]
================================================================================

Constraints in the TS world are EMITTED by code, not by a data
schema. The supported patterns are 8, in order of how often you'll
reach for each:

--------------------------------------------------------------------------
27.1 — parent/child pivot groups
--------------------------------------------------------------------------
The most common constraint: a "hinged" element lives in a Group
whose local origin IS the hinge axis. Animation writes to the
Group's .rotation; geometry follows automatically. The lid on a
treasure chest is the textbook case:

  const lidHinge = new THREE.Group();
  lidHinge.position.set(0, 0.06, -0.42);     // hinge axis
  root.add(lidHinge);
  const lid = new THREE.Mesh(lidGeo, enamel);
  lid.position.set(0, 0.175, 0.42);          // offset from hinge
  lidHinge.add(lid);
  // later, in tick() or in an action:
  lidHinge.rotation.x = -t * (Math.PI * 0.42);   // open 75°

The same pattern: recoilPivot at the gun's grip, tailPivot at the
rump, springLeaf at the elbow, antennaMount at the housing. Pivot
groups are the right tool for ~70% of the constraints you'll write.

--------------------------------------------------------------------------
27.2 — attach() / preserve-world
--------------------------------------------------------------------------
THREE.Object3D.attach(child) reparents without losing the child's
WORLD transform. Use this when a part needs to swap parents mid-life
— a magazine that's inserted into a port, a barrel that's swapped for
a silencer, a held prop that changes grip.

  const heldItem = root.getObjectByName('heldItem');
  socket.attach(heldItem);   // reparent + preserve world position

The simple alternative is `socket.add(child)` but that RESETS the
child's local transform, which looks like a teleport.

--------------------------------------------------------------------------
27.3 — IK-like placement
--------------------------------------------------------------------------
Pre-compute a rest position and rotation on construction, then in
tick() lerp the local transform toward a target that depends on
another part. The Sony earbuds ref's placeBud() is the canonical
example:

  const seat = { pos: new THREE.Vector3(...), rot: new THREE.Euler(...) };
  function placeBud(bud, s, xSign, lift, spinTurn, bob) {
    const upY = topY + 1.05 + bob;
    const outX = s.pos.x + xSign * 0.28 * lift;
    bud.position.set(
      THREE.MathUtils.lerp(s.pos.x, outX, lift),
      THREE.MathUtils.lerp(s.pos.y, upY, lift),
      THREE.MathUtils.lerp(s.pos.z, 0.02, lift),
    );
    bud.rotation.y = spinTurn * lift;
    bud.rotation.x = THREE.MathUtils.lerp(s.rot.x, -0.15, lift);
  }

  // in tick():
  const lift = Math.max(riseO * (1 - fallO), 0);
  placeBud(budL, seat.L, -1, lift, spinTurn, bob);
  placeBud(budR, seat.R,  1, lift, spinTurn, bob);

The keys: capture the rest pose on construction, drive one or more
"lift / spin / bob" scalar values from elapsed time, and let the
function interpolate to the target. This is hand-rolled, but
predictable and cheap.

--------------------------------------------------------------------------
27.4 — spring-damper lag
--------------------------------------------------------------------------
For cloth, hair, antennae, anything that should follow but not snap.
State = current + velocity; per frame:

  velocity += (K * (target - state) - D * velocity) * dt;
  state    += velocity * dt;

K = stiffness (30-80 for cloth, 8-25 for hair); D = damping
(6-12 for cloth, 2-5 for hair). Tune per material until the motion
feels right. The humanoid ref's hairMassMesh uses this to make the
hair lag behind the head, with a UV-driven weight so the crown is
rigid and the lower edge moves most:

  // v is 1 at the hairline, 0 at the crown
  let w = uvAttr.getY(i) ** 3;            // cube it: top third rigid
  // apply spring-damper to w, displace each vertex by the result

For hair that has a private spring state, do the spring math
once per frame and apply the resulting position offset to every
vertex in the mesh's userData.

--------------------------------------------------------------------------
27.5 — aim constraint
--------------------------------------------------------------------------
Every frame, child.lookAt(target.getWorldPosition()), optionally
slerped from a previous quaternion. The Shotgun ref's recoilPivot
uses a slight aim toward the muzzle, the Bolt case is a "look at the
muzzle" effect.

  const tmpV = new THREE.Vector3();
  muzzleSocket.getWorldPosition(tmpV);
  flashLight.position.lerp(tmpV, 0.5);   // half follow

For a more accurate IK rig, use a 2-bone IK solver (THREE doesn't
ship one; the spec's recommended path is the cyclical-coordinate
descent on page 117 of Geometric Tools for Computer Graphics).
Reach for a real IK solver only when procedural aim breaks down.

--------------------------------------------------------------------------
27.6 — surface follow
--------------------------------------------------------------------------
Sample an analytic surface (an ellipsoid SDF, a torus, a parametric
equation) to project a 2D decal onto a 3D shape so it reads as
contact-mounted, not floating. The pikachu ref's frontSurfaceZ()
is the canonical example:

  // z = the front surface of a known ellipsoid at the given (x, y)
  function frontSurfaceZ(x, y): number {
    const nx = x / BODY_FACE_RX;
    const ny = (y - BODY_FACE_CENTER_Y) / BODY_FACE_RY;
    const remaining = Math.max(0.04, 1 - nx*nx - ny*ny);
    return BODY_FACE_RZ * Math.sqrt(remaining);
  }
  // then for every vertex of a face decal:
  vertex.setZ(frontSurfaceZ(vertex.x, vertex.y) + offset);

  // the renderer's depthTest=false + renderOrder=3 + castShadow=false
  // (PART 6.7.1's "sculptComponent.role = 'cheek'|'mouth'|'eye'") trick
  // prevents the near-side shoulder from clipping a contact decal in
  // 3/4 view.

Other surfaces: a cylinder for tube decals (any angle, any height),
a cone for conical surfaces, a plane for floor decals. A custom
analytic surface is usually cheaper than a real CSG.

--------------------------------------------------------------------------
27.7 — mirror
--------------------------------------------------------------------------
When a part is duplicated across a plane (L/R hand, L/R earbud,
mirrored decal), make the duplicate a child of a Group at the mirror
plane with scale.x = -1 (or scale.z = -1, depending on which axis
the mirror lives on). Triangle winding inverts automatically.

  function makeEarbud(sign) { /* … same as the source … */ }
  const budL = makeEarbud(-1);
  const budR = makeEarbud(1);
  budR.scale.x = -1;        // mirror across the YZ plane
  budR.scale.z =  1;        // (X-axis flip; Z stays)
  // The materials, shaders, and animation hooks are SHARED via the
  // makeEarbud() function — change one, both update.

Three caveats: (1) baked lighting in mirror'd vertices can look wrong
if the light isn't symmetric — the renderer usually gets this right.
(2) Animation that reads a local variable (`xSign = -1`) has to be
written the same way for both halves — easier to pass `sign` as an
arg than to track two parallel state objects. (3) If the model needs
asymmetric detail (a scar, a chip), override the mirror at the end
of the make function on the side that has it.

--------------------------------------------------------------------------
27.8 — attachment socket (the part-3 way)
--------------------------------------------------------------------------
The published `sockets` map is the "constraint" channel for things
that aren't permanent children. A muzzle socket for a flash, an
ejection port for shells, a lid hinge for an attached lid, a handle
mount for a D-ring. The renderer exposes them as drag-targets in
the Inspector; runtime code can reparent other meshes into a
socket with `attach()`.

The corresponding metadata (PART 6.7.4) makes the relationship
explicit: `socket.userData.socketFor = '<part id>'` plus
`node.userData.sculptComponent.sockets = ['<socket name>']`. A host
that wants to add a new flash effect to every gun that exposes a
`muzzle` socket just walks `nodes[*].sockets.muzzle` and attaches
its own sprite.

================================================================================
PART 28 — ADVANCED SHADER & VFX TECHNIQUES [v1.3]
================================================================================

Beyond the recipes in PART 7, four techniques separate "looks like
real material" from "looks like real effect". Use them when the
preset recipe isn't enough.

--------------------------------------------------------------------------
28.1 — onBeforeCompile + customProgramCacheKey (per-material shader)
--------------------------------------------------------------------------
THREE compiles every PBR material from a template shader. When you
need per-material shader effects (height-driven colour blend,
per-pixel emissive injection, two-tone faces), the supported path is
to register an onBeforeCompile hook that mutates the vertex and
fragment shader strings in place. ALWAYS set a customProgramCacheKey
return value — without it, identical materials with different
onBeforeCompile bodies share a compiled program and you get the
worst of both worlds.

  // Height-driven patina: the upper portion of a mesh turns teal
  // based on world-space Y, with a multi-octave sine-noise blotch
  // pattern. Used on the warhauler ref's rear armour hump.
  function makeWeatheredBrass(dirt, lo, hi) {
    const mat = new THREE.MeshStandardMaterial({ /* … */ });
    const patina = new THREE.Color(0x3f6f4c).convertSRGBToLinear();
    mat.onBeforeCompile = (shader) => {
      shader.uniforms.uLo = { value: lo };
      shader.uniforms.uHi = { value: hi };
      // vertex: pass world-space Y to the fragment
      shader.vertexShader = 'varying vec3 vWPosW;\n' +
        shader.vertexShader.replace(
          '#include <worldpos_vertex>',
          `#include <worldpos_vertex>
           vWPosW = (modelMatrix * vec4(transformed, 1.0)).xyz;`,
        );
      // fragment: blend in patina above uLo, blotchy
      shader.fragmentShader =
        `varying vec3 vWPosW;\nuniform float uLo;\nuniform float uHi;\n` +
        shader.fragmentShader.replace(
          '#include <color_fragment>',
          `#include <color_fragment>
           float _h = clamp((vWPosW.y - uLo) / (uHi - uLo), 0.0, 1.0);
           float _n = 0.5 + 0.5 * sin(vWPosW.x * 7.3 + 1.7) * sin(vWPosW.z * 5.1 - 0.9);
           _n += 0.35 * (0.5 + 0.5 * sin(vWPosW.x * 15.7 - 2.1) * sin(vWPosW.z * 12.3 + 0.4));
           _n = clamp(_n / 1.35, 0.0, 1.0);
           float _g = smoothstep(0.25, 0.9, _h) * smoothstep(0.25, 0.75, _n);
           diffuseColor.rgb = mix(diffuseColor.rgb,
             vec3(${patina.r.toFixed(4)}, ${patina.g.toFixed(4)}, ${patina.b.toFixed(4)}),
             _g * 0.92);`,
        );
    };
    mat.customProgramCacheKey = () => 'warhauler-patina-v2';
    return mat;
  }

Rules:
  - ALWAYS set customProgramCacheKey() to a unique-per-intent string.
  - ALWAYS use `new THREE.Color(0x…).convertSRGBToLinear()` before
    stringifying the colour into GLSL — otherwise the `mix` blends
    in sRGB space and the result washes out.
  - Inject varyings at the top of the shader with the matching
    declaration in BOTH vertex and fragment (`varying vec3 vX;`).
  - Inject math at the right chunk:
      * vertex displacement  → `#include <begin_vertex>`
      * per-vertex varying    → `#include <worldpos_vertex>` (or
                                  any other chunk that has access
                                  to modelMatrix)
      * per-fragment colour   → `#include <color_fragment>`
      * per-fragment emissive → `#include <emissivemap_fragment>`
      * per-fragment normal   → `#include <normal_fragment_maps>`
  - The pikachu ref uses onBeforeCompile to add a real-time breath
    mask to a single body shader (without duplicating the material
    per-region). The warhauler ref uses it to apply a height-driven
    patina to a rounded box without a per-vertex colour attribute.

--------------------------------------------------------------------------
28.2 — ShaderMaterial (when onBeforeCompile isn't enough)
--------------------------------------------------------------------------
For effects that go beyond PBR (a lightning bolt with a travelling
highlight, a custom hologram with a noise-driven hue shift, a sprite
with a procedural halo), use a full THREE.ShaderMaterial with your
own vertexShader + fragmentShader + uniforms:

  const lightningMat = new THREE.ShaderMaterial({
    uniforms: {
      uTime:        { value: 0 },
      uIntensity:   { value: 0 },
      uGlowColor:   { value: new THREE.Color(0xd98700) },
      uInnerGlow:   { value: new THREE.Color(0xffd45a) },
      uHighlight:   { value: new THREE.Color(0xffffd6) },
    },
    vertexShader: `
      varying vec2 vUv;
      void main() {
        vUv = uv;
        gl_Position = projectionMatrix * modelViewMatrix * vec4(position, 1.0);
      }
    `,
    fragmentShader: `
      varying vec2 vUv;
      uniform float uTime;
      uniform float uIntensity;
      uniform vec3 uGlowColor;
      uniform vec3 uInnerGlow;
      uniform vec3 uHighlight;
      void main() {
        float radial  = max(sin(vUv.y * 3.14159), 0.0);
        float core    = pow(radial, 5.5);
        float halo    = pow(radial, 1.05);
        float taper   = smoothstep(0.0, 0.10, vUv.x) *
                        (1.0 - smoothstep(0.90, 1.0, vUv.x));
        float sweep   = fract(uTime * 0.42);
        float sweepD  = abs(vUv.x - sweep);
        sweepD = min(sweepD, 1.0 - sweepD);    // seamless at 0/1
        float sweepL  = exp(-pow(sweepD / 0.085, 2.0));
        float sweepA  = pow(radial, 0.72);
        float movingH = (sweepL * sweepA) * taper;
        float alpha   = uIntensity * (0.88 * halo * taper + movingH * 0.34);
        vec3 col      = mix(uGlowColor, uInnerGlow, core);
        col           = mix(col, uHighlight, clamp(movingH * 0.92, 0.0, 1.0));
        gl_FragColor  = vec4(col, alpha);
      }
    `,
    transparent: true,
    depthTest:   false,
    depthWrite:  false,
    blending:    THREE.AdditiveBlending,
    side:        THREE.DoubleSide,
  });
  // Refs: pikachu's celebration lightning + electric attack.
  // Set `material.toneMapped = false` if the effect should bypass
  // ACES — neon, glow, anything that should stay bright through the
  // tonemapper.

ShaderMaterial replaces the PBR lighting model entirely. You give up
real PBR (IBL, shadows are manual) for full control. Use it for
non-PBR effects (VFX, holograms, decals with custom alpha), not for
"another way to make metal".

--------------------------------------------------------------------------
28.3 — SpriteMaterial + AdditiveBlending (glow / halo / spark)
--------------------------------------------------------------------------
For any bloom-able glow (headlight, muzzle flash, exhaust, LED, neon
halo), use a THREE.Sprite with a SpriteMaterial set to
AdditiveBlending + depthWrite: false + transparent: true:

  function makeGlowSprite(color: number, size: number, opacity = 1): THREE.Sprite {
    const s = new THREE.Sprite(new THREE.SpriteMaterial({
      map: glowTexture(),
      color, opacity, transparent: true,
      blending: THREE.AdditiveBlending,
      depthWrite: false,
    }));
    s.scale.setScalar(size);
    return s;
  }
  // glowTexture() — a CanvasTexture filled with a radial gradient
  //   white centre → colour-bleed edge → transparent. See PART 8.3
  //   for the canonical radial-gradient recipe.

The renderer composites additively blended sprites in the order they
appear in the scene graph; for "soft glow" effects this is
indistinguishable from a real bloom pass. Add `material.toneMapped
= false` if the glow should stay bright under ACES (you almost
always want this).

For moving glows (a muzzle flash that fades out over 70ms), animate
the opacity in tick():
  flashMat.opacity = state.flash / FLASH_DURATION;   // 1 → 0

--------------------------------------------------------------------------
28.4 — DataTexture (procedural normal / roughness / heightmap)
--------------------------------------------------------------------------
For data-only maps (normal, height, curvature, packed AO+roughness)
the canvas round-trip is wasteful — go direct to a DataTexture:

  function strandNormalTexture(): THREE.DataTexture {
    const w = 128, h = 16, LANES = 16;
    const data = new Uint8Array(w * h * 4);
    for (let x = 0; x < w; x++) {
      const phase = (x / w) * LANES * Math.PI * 2;
      const nx = -0.62 * Math.sin(phase);
      for (let y = 0; y < h; y++) {
        const ny = 0.13 * Math.sin((y / h) * Math.PI * 2 + phase * 0.2);
        const len = Math.hypot(nx, ny, 1);
        const o = (y * w + x) * 4;
        data[o]     = Math.round((nx / len * 0.5 + 0.5) * 255);
        data[o + 1] = Math.round((ny / len * 0.5 + 0.5) * 255);
        data[o + 2] = Math.round((1    / len * 0.5 + 0.5) * 255);
        data[o + 3] = 255;
      }
    }
    const tex = new THREE.DataTexture(data, w, h, THREE.RGBAFormat);
    tex.wrapS = tex.wrapT = THREE.RepeatWrapping;
    tex.minFilter = THREE.LinearMipmapLinearFilter;
    tex.magFilter = THREE.LinearFilter;
    tex.anisotropy = 8;
    tex.generateMipmaps = true;
    tex.needsUpdate = true;
    return tex;
  }
  // Ref: the humanoid ref's hair-strand normal + roughness maps.

DataTexture is the cheaper, more direct equivalent of CanvasTexture
for fully synthetic data — no canvas, no 2D context, no draw loop.
For 16×128 hair strands, it's ~6 KB of typed array vs ~30 KB of
canvas + draw overhead.

--------------------------------------------------------------------------
28.5 — InstancedMesh (repetitive geometry)
--------------------------------------------------------------------------
For any repeated part (8 wall blocks, 4 spokes, 9 jimping notches,
6 wheels, 12 lug bolts, 4 pegs, 36 perimeter blocks), use
THREE.InstancedMesh. One geometry, one material, N transforms:

  const BOLT_GEO = new THREE.SphereGeometry(0.025, 8, 6);
  function boltRow(count, from, to, mat) {
    const inst = new THREE.InstancedMesh(BOLT_GEO, mat, count);
    const m = new THREE.Matrix4();
    for (let i = 0; i < count; i++) {
      const t = count === 1 ? 0.5 : i / (count - 1);
      const p = from.clone().lerp(to, t);
      m.makeTranslation(p.x, p.y, p.z);
      inst.setMatrixAt(i, m);
    }
    inst.instanceMatrix.needsUpdate = true;
    return inst;
  }
  // Refs: warhauler's bolt rows, BMX's perimeter cinder-block wall,
  // shotgun's vent slots.

Three rules:
  - One InstancedMesh per (geometry, material) pair. Multiple
    InstancedMesh objects can share the same geometry/material.
  - `instanceMatrix.needsUpdate = true` AFTER setting all matrices.
  - InstancedMesh does NOT support per-instance colour in the
    standard pipeline; if you need per-instance variation, use a
    custom onBeforeCompile shader injection (PART 28.1) or instance
    attributes.

For 4-12 instances the savings are marginal; for 50+ it's the
difference between 5,000 vertices and 50,000. The BMX's perimeter
wall is 200+ blocks; without instancing it would be 200 BoxGeometry
meshes (~30,000 vertices) and the renderer would struggle to
inspect them.

================================================================================
PART 29 — ROOT-LEVEL userData ALIASES + ANIMATIONMIXER AUTO-TICK [v1.3]
================================================================================

v1.3 added automatic alias-flattening. A factory can hoist any of the
following to root.userData without writing into sculptRuntime; the
renderer hoists them on mount so the rest of the pipeline sees a
single uniform shape:

  root.userData.parts         → sculptRuntime.parts
  root.userData.nodes         → sculptRuntime.nodes
  root.userData.meshes        → sculptRuntime.meshes
  root.userData.colliders     → sculptRuntime.colliders
  root.userData.<anyNs>       → sculptRuntime.<anyNs>   (preserved)

For the AnimationMixer specifically, the renderer does a one-level
DFS through root.userData and looks for an object with an `update`
method whose `_root` back-reference points at the model root. If
found, it's invoked every frame with `(elapsedSeconds)`. This means
the pikachu ref's pattern of `root.userData.electricMouseMascotRuntime
= { _root, mixer, update }` works without any extra wiring.

  const runtime = {
    _root: root,                     // back-reference is what the DFS
                                      // matches on
    mixer: animationMixer,           // optional — the renderer also
                                      // finds this if it's set here
    update(elapsed: number) { /* … */ },
  };
  root.userData.electricMouseMascotRuntime = runtime;

The DFS is narrow on purpose — it walks ONE level deep into userData,
checks each value for `_root === root` AND a callable `update`. This
is safe to combine with anything else; it won't double-tick a
`userData.tick` (PART 5.1) because the rule is: tick wins, mixer
wins, custom-runtime-update is the fallback. Specifically:

  - If `root.userData.tick` exists → tick handles everything; the
    renderer does NOT also tick the mixer or the custom-runtime.
  - If `root.userData.tick` is missing AND the factory has a mixer
    (sculptRuntime.animations.mixer OR a discovered one) → the
    renderer auto-ticks the mixer.
  - If neither → the renderer auto-ticks a custom-runtime.update()
    if it finds one.

For the FULL optional sculptRuntime shape, see PART 6.1B.

================================================================================
PART 30 — RIGGING & ANIMATION AUTHORING STANDARD (articulated models) [v1.4]
================================================================================
This PART formalizes how to build an articulated model (anything with
joints that pose or animate — characters, creatures, walkers, mechs,
turrets, anything with more than a static tick sway) so it renders
correctly in THIS renderer. It does not replace PART 5 (tick/
AnimationMixer contract) or PART 6 (sculptRuntime contract) — it tells
you HOW to build the joint hierarchy and author clips that plug into
those two contracts cleanly.

--------------------------------------------------------------------------
30.0 — WHAT DOES / DOES NOT APPLY HERE
--------------------------------------------------------------------------
REMINDER (the single most common failure mode this PART risks causing):
everything below — the pivot hierarchy, the clip-building functions,
all of it — MUST be assembled and returned from inside your file's
`export function createXxxModel(options?): THREE.Group` (PART 1.2).
Rigging helper functions on their own (a standalone `buildSkeleton()`,
a standalone `buildWalkClip()`) are fine as internal helpers CALLED BY
that factory — but if the factory export itself is missing, renamed,
or doesn't match `/^create\w+Model$/`, the renderer's loader rejects
the file outright with "No create*Model() export found", regardless of
how correct the rigging inside it is. If you're translating rigging
code from an external, non-createXxxModel-shaped source (a standalone
skeleton-builder script, an export-pipeline file), the FIRST thing to
fix is wrapping the actual model construction in a real
`createXxxModel` factory — not a later step.

This renderer loads a native Three.js factory module directly in the
browser (PART 1) — that's the primary contract, and it does NOT need a
separate Blender/Unity/Unreal/Godot IMPORT step; those workflows are
for someone consuming an already-exported .glb in another engine and
must NOT appear in this file's output.

HOWEVER: the renderer DOES include a working GLB EXPORT feature
(`THREE.GLTFExporter`, wired up in the app) that can export your
factory's built model to a downloadable .glb. So export-safety is a
real constraint, not a hypothetical one — see PART 30.6.

If you are translating rigging notes from an external glTF-style rig
guide for a DIFFERENT specific asset, treat that asset's exact bone
coordinates and named clips as reference data only, not as this
model's content — re-express the STRUCTURE (pivot hierarchy, DOF
discipline, named-clip authoring) using the pattern below, built for
whatever subject you're actually generating.

--------------------------------------------------------------------------
30.1 — COORDINATE STANDARD
--------------------------------------------------------------------------
Standard Three.js right-handed, Y-up world space — the renderer applies
no coordinate remapping. Do not invent a different up-axis or handedness
for "compatibility with other engines"; there is only one engine here.

--------------------------------------------------------------------------
30.2 — PIVOT HIERARCHY (the "armature" for this renderer)
--------------------------------------------------------------------------
NESTED, not flat. A jointed model requires a nested parent-child chain
— that IS how a rotation at the hip propagates down through the knee
to the foot. There is no flat-hierarchy requirement anywhere in this
renderer (checked: it isn't enforced by the loader, the inspector, or
the export path), and a genuinely flat hierarchy is structurally
incompatible with articulation — a knee that isn't parented under a
thigh can't inherit the thigh's rotation. Reserve a flat, single-level
child list for the case it actually fits: a fully RIGID, non-jointed
prop or static-pose model with no moving parts, where there's nothing
to propagate. The moment a part needs to rotate relative to a parent
part at runtime, it needs to be an actual child Group of that parent.

There is no THREE.Skeleton/THREE.Bone requirement in YOUR code — a plain
nested THREE.Group hierarchy IS the armature you author. As of v8.3 the
renderer itself auto-promotes every NAMED transform-only Group into a
real THREE.Bone and auto-binds every mesh beneath it into a real,
single-bone-per-part skin at GLB-export time (see PART 30.7) — you never
write Skeleton/Bone/skin-weight code yourself, and the exported .glb
still ends up with a genuine `skins` section either way. The ONE thing
this promotion depends on: every pivot Group MUST have a non-empty,
unique `.name` (not just a JS variable name) — an unnamed Group is
invisible to the promotion pass and stays a plain, un-skinned Group in
the export. Each joint is a THREE.Group whose ORIGIN is the actual
rotation point (not the mesh's bounding-box center), with the child
mesh/sub-hierarchy offset inside it. Rotate the group; never rotate a
mesh directly if it has children that must follow.

  const hipL   = new THREE.Group(); hipL.name = 'hipL';
  hipL.position.set(-0.20, 0.55, 0);
  const thighL = new THREE.Group(); thighL.name = 'thighL';
  thighL.position.set(0, 0, 0);   // hinge at hip
  const kneeL  = new THREE.Group(); kneeL.name = 'kneeL';
  kneeL.position.set(0, -0.28, -0.03); // offset FROM thigh pivot
  const shinL  = buildLowPolyLeg(); shinL.position.set(0, 0, 0);    // hinge at knee

  hipL.add(thighL); thighL.add(kneeL); kneeL.add(shinL); root.add(hipL);

Before authoring the hierarchy, write a short comment table above the
factory function listing every pivot: id, parent, local offset (the
translation from PARENT pivot to THIS pivot, not world position),
one-line function, and which axis/axes it's allowed to rotate on. This
is documentation for future edits, not a runtime object — keep it
terse:

  // PIVOT TABLE (local offsets, parent → child)
  // hipL      root        (-0.20, 0.55, 0)   yaw+pitch+roll swing
  // thighL    hipL        (0, 0, 0)          pitch only (forward/back swing)
  // kneeL     thighL      (0, -0.28, -0.03)  pitch only (flexion, one direction)
  // shinL     kneeL       (0, 0, 0)          rigid (no further joint)

Keep each joint to the MINIMUM degrees of freedom it actually needs —
a knee that can only bend one way should only ever be driven on one
Euler axis. This avoids gimbal artifacts and keeps clip authoring
sane. Reserve full 3-DOF rotation for shoulder/hip-socket-style joints.

Register every pivot in `sculptRuntime.nodes` (PART 6.1) using the same
name you used in the pivot table, and set `node.userData.animationRole
= 'bone'` (PART 6.7.3) on each one so the renderer's animation tooling
recognizes the chain. Mark the top of the chain with `'skeleton-root'`
or `'rig-root'`.

--------------------------------------------------------------------------
30.3 — REST POSE
--------------------------------------------------------------------------
Assemble and position every pivot in a neutral REST POSE first (all
joint rotations at their zero/default value) and get the silhouette
right in rest pose before authoring any clip. Every AnimationClip
you build afterward is a set of OFFSETS from this rest pose — if the
rest pose is wrong, every clip inherits the error.

--------------------------------------------------------------------------
30.4 — NAMED ACTION CLIPS
--------------------------------------------------------------------------
For each distinct action (idle, walk, run, attack, jump, power-down,
whatever the subject calls for), author it as its own
THREE.AnimationClip per PART 5.6(a), using
THREE.QuaternionKeyframeTrack for joint rotation and
THREE.VectorKeyframeTrack for root/COM translation (bounce, crouch,
launch height). Document each clip with a short block comment
BEFORE the code that builds it — this is what actually keeps a
multi-clip character maintainable:

  // ACTION: walk — 1.2s seamless loop
  // Tracks: pelvis.position (bob + weight transfer), mainBody.quaternion
  //   (forward tilt + counter-yaw), thighL/R.quaternion (swing, 180°
  //   phase offset), kneeL/R.quaternion (flexion), ankleL/R.quaternion
  //   (ground-alignment compensation = -(thighAngle + kneeAngle))
  // Profile: pelvis Y oscillates between 0.55-0.59, thigh swing ±18°,
  //   knee flexes 0°→22° on forward swing, -7° on trailing push.
  function buildWalkClip(): THREE.AnimationClip { /* … */ }

Guidelines for the profile paragraph:
  - State the DURATION and whether it loops (seamless) or clamps
    (plays once and holds/stops) — this matters for how you author the
    first/last keyframe (loop clips need frame 0 === last frame).
  - Name which tracks move, not just "the legs move".
  - For legged locomotion, phase-offset left/right limbs by 180°
    (`workingElapsed` vs `workingElapsed + duration/2`) rather than
    authoring two near-duplicate keyframe sets by hand.
  - Ground-contact joints (ankles, feet) should compensate so the
    foot doesn't visibly slide or tilt through the floor — the
    simplest version is ankle angle ≈ -(sum of upstream joint
    angles), corrected by eye against the rest-pose foot orientation.
  - Secondary motion (an antenna, a cape, loose cable) should read as
    driven by the primary motion (inertia/drag), not moving on its
    own unrelated cycle.

Publish the finished set via `sculptRuntime.animations = { clips,
mixer, actions }` (PART 5.6a) so the renderer's play/next-clip UI
picks them up, AND add matching entries to `sculptRuntime.actions`
(PART 6.1B) for any clip that should also be one-click-triggerable
from the Action Hooks panel:

  const clipActions = new Map(clips.map(c => [c.name, mixer.clipAction(c)]));
  sculptRuntime.actions = {
    jump: () => { clipActions.get('jump')?.reset().play(); },
  };

--------------------------------------------------------------------------
30.5 — GLB EXPORT SAFETY (the renderer's export button is real — plan for it)
--------------------------------------------------------------------------
The renderer can export your built model via `THREE.GLTFExporter`. It
sanitizes some common mistakes for you (Euler rotation sub-tracks are
auto-converted to quaternion tracks; circular userData references —
including the `AnimationMixer` PART 5.6(a) tells you to publish under
`sculptRuntime.animations.mixer`, whose `_root` points back into the
model — are sanitized at EVERY node of the cloned export tree, not
just the root) — but don't rely on the safety net when authoring is
just as easy:

  - Author joint rotation with `node.quaternion` / QuaternionKeyframeTrack
    directly (PART 30.4 already tells you this) rather than animating
    `node.rotation.x/y/z` — quaternion tracks export cleanly with no
    conversion step, and dodge the wraparound issues Euler tracks can
    hit with the sanitizer.
  - Every pivot/mesh you want to survive export must be a real
    descendant of the returned root Group — don't build a detached
    THREE.Object3D purely for internal bookkeeping and expect it in
    the export.
  - Track target names are matched against actual node names in the
    scene graph — this is why PART 6.2's naming discipline (consistent
    names between the geometry code and `sculptRuntime`) matters for
    export, not just for the Inspector.
  - Helper-only objects (debug gizmos, outline meshes, wireframe
    overlays) should NOT be part of the exported result — if you add
    any such helper node, this renderer's convention is
    `node.userData.__helper = true` (or `__noExport`) to keep it out
    of the export, matching the pattern used elsewhere in the app.

30.7 — v1.6 UPDATE: REAL SKELETON EXPORT FOR EXTERNAL RIG-TEST VIEWERS
--------------------------------------------------------------------------
Source: field reports against an external GLB viewer's rig-test mode,
across two rounds. Round 1 showed "Using 1 mesh/group part(s) as
rig-test targets (low-poly mode)" for every exported model. Round 2,
after the model factories were confirmed to build genuinely separate
per-part meshes (this renderer's export path had a since-fixed bug that
was silently dropping userData in transit — nothing you do differently
here), showed the REAL cause in the same viewer's own log: "No
SkinnedMesh or bones found — this model has no true skeleton rig" /
"No skeleton found. Using 1 mesh/group part(s)... (low-poly mode)".
That fallback is gated purely on whether the .glb has a real glTF
`skins` section — NOT on mesh count and NOT on extras/userData. A
THREE.Bone with no skin binding has no special marker in glTF at all
(glTF has no distinct "bone" node type — a node is only ever identified
as a joint by appearing in some `skins[].joints` array), so it exports
as an utterly ordinary node, indistinguishable from a plain Group. An
earlier version of this renderer promoted named pivot Groups to
THREE.Bone but stopped there, on the reasoning that "the GLB has a real
node list with named bones an external tool can use even without a
skins section" — that reasoning was untested and wrong; the field data
above is what actually happens.

FIXED (v8.3, renderer-side, no authoring change needed beyond PART
30.2's `.name` requirement): the renderer now also auto-binds every
mesh under a promoted Bone into a real, single-bone-per-part skin —
each mesh rigidly bound 100% to its own one bone (the same technique
already used for years on this system's JSON/JS blueprint export path,
generalized here), never split across multiple bones per vertex. A
whole-mesh-to-one-bone rigid bind is mathematically identical to plain
scene-graph parenting at bind pose, so it changes nothing about how the
model looks or animates — it only gives the export a real `skins`
section. You do not write any of this yourself; it happens automatically
at export time as long as PART 30.2's pivot-naming rule is followed.

This is now the PRIMARY thing that satisfies an external rig-test
viewer's skeleton check. The rules below remain necessary in addition
to it — a real skin still needs genuinely separate per-part meshes to
skin, and isPickable/partName remain valuable for any viewer/tool that
reads extras instead of (or in addition to) skin data:

RULE — every distinct body part (head, each pivot-driven limb segment
per PART 30.2, each hand/foot, and any prop) must be its own separate
`THREE.Mesh` inside the returned root Group — never one fused
BufferGeometry standing in for the whole articulated model. This does
NOT conflict with PART 30.2's NESTED pivot hierarchy: a part mesh being
a descendant of a joint Group (`kneeL.add(shinL)`) is exactly right and
still counts as "its own separate Mesh" — nesting is about the transform
hierarchy, not about fusing geometry. The only thing this rule forbids
is literally merging multiple parts' vertex/index data into one shared
BufferGeometry (or one Lathe/Tube path standing in for the entire body).

Mark every part mesh for external pickability right after you construct
it — these two fields are inert to THIS renderer (nothing here currently
reads them) but are exactly what an external glTF-based rig-test tool
uses to enumerate and label separately-pickable parts:

  const headMesh = buildLowPolyHead();
  headMesh.userData.isPickable = true;
  headMesh.userData.partName = 'head';   // match the sculptRuntime.nodes
                                          // name (PART 6.1) when this
                                          // part also doubles as a pivot

Target for a character-scale model: roughly 10-15 separate mesh nodes in
the exported .glb (head, torso, upper-arm/forearm or whole-arm-chain ×2,
hand ×2, upper-leg/lower-leg or whole-leg-chain ×2, foot ×2, plus any
held props) — not 1. A simple, non-articulated prop can legitimately
have fewer; the requirement is "genuinely more than one part where the
subject actually has more than one part", not a forced minimum.

================================================================================
PART 19 — STAGED BUILD PASSES  (img2threejs alignment — added v1.2, 2026-07-31)
================================================================================
The single-shot "analyse then output the whole factory" flow above is
replaced by 8 progressive passes, mirroring the sister img2threejs
project. Each pass is reviewed before the next unlocks, so partial
self-correction is possible and the user can see WHERE a build went
wrong instead of only seeing a finished-but-wrong model. The renderer
reads root.userData.sculptRuntime.passes and verifies each of the 8
keys is present (or explicitly empty with a reason in pass.skipped).
A factory that silently skips a pass is flagged by the validator (see
SYSTEM_UPDATE_PROMPT §3a) — not refused, but surfaced as a warning.

--------------------------------------------------------------------------
19.1 — blockout
--------------------------------------------------------------------------
Output: outer silhouette only. The minimum primitive set that reads as
the subject from the camera angle. No surface detail, no decals, no
secondary forms.
  userData.sculptRuntime.passes.blockout = {
    meshes: <count of Mesh nodes added in this pass>,
    boundingBox: { min: [x,y,z], max: [x,y,z] },
    cameraFov: <number, from the reference>,
  }

--------------------------------------------------------------------------
19.2 — structural
--------------------------------------------------------------------------
Output: skeletal pivots, named sockets, parent/child hierarchy,
attachment points (held props, joints, mount points).
  userData.sculptRuntime.passes.structural = {
    pivots: [<pivotName>, ...],
    sockets: [{ name, worldPos: [x,y,z], parent: <pivotName> }, ...],
  }

--------------------------------------------------------------------------
19.3 — form
--------------------------------------------------------------------------
Output: secondary geometry — panel lines, bevels, hatches, cutouts,
internal sub-meshes, asymmetry per the reference.
  userData.sculptRuntime.passes.form = {
    additions: <count of Mesh nodes added in this pass>,
  }

--------------------------------------------------------------------------
19.4 — material
--------------------------------------------------------------------------
Output: MeshStandardMaterial / MeshPhysicalMaterial with per-region
roughness / metalness / clearcoat / emissive. Style is locked to
meta.style.
  userData.sculptRuntime.passes.material = {
    materialCount: <number>,
    pbrRegions: <number of meshes with metalness > 0.4 OR
                 clearcoat > 0.3>,
    emissiveRegions: <number of meshes with emissiveIntensity > 0>,
  }

--------------------------------------------------------------------------
19.5 — surface
--------------------------------------------------------------------------
Output: canvas textures, bump/normal maps, decals, painted detail.
Master texture from meta.textureImage is applied to every mesh with
useMasterTexture.
  userData.sculptRuntime.passes.surface = {
    textureCount: <number of CanvasTexture / DataTexture>,
    decalCount: <number of decal quads>,
  }

--------------------------------------------------------------------------
19.6 — lighting
--------------------------------------------------------------------------
Output: a createXxxModelLookDevLights(mode) export with one entry per
look-dev mode the model supports:
  'neutral'   — product-shot default
  'grazing'   — dramatic side-light for surface read
  'reference' — match the reference image's lighting setup
  userData.sculptRuntime.passes.lighting = {
    supportedModes: ['neutral', 'grazing', 'reference'],
  }

--------------------------------------------------------------------------
19.7 — interaction
--------------------------------------------------------------------------
Output: animation, held props, VFX, root.userData.tick. Held props
attach to hand sockets defined in 19.2. Animations are FK chains or
simple keyframe-driven values on userData.sculptRuntime.animations.
  userData.sculptRuntime.passes.interaction = {
    tickFn: <boolean, true if userData.tick is set>,
    animationCount: <number>,
    heldProps: [{ propName, socketName }, ...],
  }

--------------------------------------------------------------------------
19.8 — optimization
--------------------------------------------------------------------------
Output: castShadow / receiveShadow on every mesh, geometry merge where
the renderer supports it, draw-call reduction.
  userData.sculptRuntime.passes.optimization = {
    shadowedMeshes: <count>,
    drawCalls: <estimated count>,
  }

--------------------------------------------------------------------------
19.9 — All-pass envelope
--------------------------------------------------------------------------
  userData.sculptRuntime.passesComplete = <boolean>
  userData.sculptRuntime.passesReviewed = {
    blockout:    { score: <0..1>, notes: '...' },
    structural:  { score: <0..1>, notes: '...' },
    form:        { score: <0..1>, notes: '...' },
    material:    { score: <0..1>, notes: '...' },
    surface:     { score: <0..1>, notes: '...' },
    lighting:    { score: <0..1>, notes: '...' },
    interaction: { score: <0..1>, notes: '...' },
    optimization:{ score: <0..1>, notes: '...' },
  }
You MUST populate this with your own self-score per pass BEFORE
output. The renderer's Fidelity tab reads it and shows a per-pass bar
chart. A pass with score < 0.6 is flagged.

================================================================================
PART 20 — DETAIL INVENTORY GATE  (img2threejs alignment — added v1.2, 2026-07-31)
================================================================================
Before PART 19 starts, you MUST enumerate every identity-defining
feature of the subject as a flat list. This is img2threejs's
detailInventory — a structured list the build passes check against and
the review gate scores. Without it you are trusted to "remember"
identity features from prose alone, which is the main cause of
"almost right but missed a stripe" failures.

Mandatory shape:
  userData.sculptRuntime.detailInventory = [
    {
      id: 'face.leftEye',         // stable string id, dotted.path style
      region: 'face',             // body region or hard-surface area
      kind: 'feature',            // 'feature' | 'panel' | 'socket' |
                                  // 'decal' | 'prop' | 'landmark'
      description: 'amber iris, ~0.04 radius, slight inner-corner shadow',
      priority: 'high',           // 'high' | 'medium' | 'low'
      reviewThreshold: 0.85,      // 0..1, must clear in review
    },
    ...
  ]

Rules:
  - List MUST be non-empty. A factory with an empty detailInventory is
    rejected by the validator.
  - High-priority items are identity-defining (face features, weapon
    silhouettes, vehicle proportions). The Tier 1 gate checks that
    every high-priority item has at least one Mesh assigned in PART 19.
  - reviewThreshold is the per-item score your own post-render fidelity
    self-check (PART 23) must clear. Default 0.85 for high-priority,
    0.7 for medium, 0.5 for low.
  - Items are sorted by priority then by id for stable diffing across
    regenerations.
  - The validator's coverage check is:
      for each high-priority item with kind in {feature, panel, decal,
      landmark}:
        assert item has at least one matching Mesh in the userData
        tree (matched by .name startsWith item.id with '.' -> '/')
  - Image-fork gets this from PART 17 measurement; text-fork gets it
    from PART 20 semantic priors (this PART itself, on the text path).

================================================================================
PART 21 — SEMANTIC LANDMARK RATIOS  (img2threejs alignment — text-fork
          variant of image-fork PART 21 — added v1.2, 2026-07-31)
================================================================================
Same contract as the image-fork's landmark pixel measurement, but
since there is no reference image to measure, landmarks are expressed
as semantic RATIOS instead of pixel coordinates — derived from PART 20
priors (your own knowledge of the subject's proportions) rather than
from a measured image.

Shape:
  userData.sculptRuntime.landmarks = {
    // Ratios are relative to the subject's overall bounding box.
    // 0..1 on each axis, origin = subject's bottom-left-front.
    'face.leftEyeCenter':   [0.42, 0.72],   // 42% across, 72% up
    'face.rightEyeCenter':  [0.58, 0.72],
    'face.noseTip':         [0.50, 0.62],
    'face.chin':            [0.50, 0.38],
  }

Rules:
  - Every entry in detailInventory (PART 20) with kind='landmark' MUST
    have a matching key in userData.sculptRuntime.landmarks.
  - The renderer computes landmarkIou the same way as the image fork;
    only the units differ. The IoU here is between the rendered
    silhouette and a hull derived from the projected ratio coordinates
    mapped onto the model bounds.
================================================================================
PART 22 — SUBJECT ROUTING  (img2threejs alignment — added v1.2, 2026-07-31)
================================================================================
Before PART 17 (image fork) or PART 20 (text fork) runs, you MUST
classify the subject and write the routing decision to
userData.sculptRuntime.subject.

Shape:
  userData.sculptRuntime.subject = {
    kind: 'object' | 'character' | 'hybrid' | 'creature',
    // For creatures only:
    creaturePlan: 'quadruped' | 'avian' | 'winged-dragon' |
                  'serpentine' | null,
    // For characters and hybrid:
    landmarks: ['face.leftEyeCenter', 'face.rightEyeCenter', ...],
    // For objects and hard-surface hybrid:
    hardSurfaceFaces: ['front', 'side.left', 'side.right',
                       'back', 'top'],
  }

Routing rules:
  - 'object'    → skip landmark rules; PART 20 inventory uses
                  hard-surface faces as regions.
  - 'character' → landmarks REQUIRED; inventory uses body regions
                  (face, torso, limbs, etc.).
  - 'hybrid'    → both faces and body regions in inventory.
  - 'creature'  → landmarks REQUIRED; creaturePlan determines which
                  anatomy proportions apply (quadruped, avian,
                  winged-dragon, serpentine).

================================================================================
PART 23 — POST-RENDER FIDELITY SELF-SCORE  (img2threejs alignment — added v1.2, 2026-07-31)
================================================================================
A factory MUST populate a self-score alongside the model. This is your
own assessment of how well the build matches the reference (or, for
the text-only fork, the prompt). The renderer's Fidelity tab surfaces
it. PART 12 / PART 21 remain pre-output checklists (do this before
emitting); this PART is the post-output score.

Shape:
  userData.sculptRuntime.fidelity = {
    overall: 0.0,             // weighted average (recomputed by
                               // renderer, see below)
    perPass: {                // mirror of passesReviewed from 19.9
      blockout: 0.0, structural: 0.0, form: 0.0, material: 0.0,
      surface: 0.0, lighting: 0.0, interaction: 0.0,
      optimization: 0.0,
    },
    perItem: {                // mirror of detailInventory threshold
      'face.leftEye': 0.0, 'face.rightEye': 0.0, ...
    },
    landmarkIou: 0.0,         // computed by renderer, not you
    styleCoherent: true,      // matches meta.style
    notes: 'short string, max 240 chars',
  }

You populate overall, perPass, perItem, styleCoherent, and notes. The
renderer computes landmarkIou from PART 21 and the rendered silhouette.
overall is recomputed by the renderer as:
    0.45 * mean(perPass) +
    0.30 * mean(perItem) +
    0.25 * landmarkIou
If your reported overall differs from the recomputed overall by more
than 0.15, the renderer flags a "self-score inconsistent" warning.

PART 24 — RENDERER GUARANTEES THAT DO NOT APPLY ON THIS PATH (audit note —
           source: lbl_patch_1_quickwins.txt, cross-checked against
           low_poly_3d.html, 2026-07-29)
================================================================================
A patch describing 4 renderer quick-wins was audited against the actual
source. All 4 turned out to already be shipped — but as part of the
JSON/JS blueprint pipeline (buildScene()/buildMaterialRaw()), which this
TS path deliberately bypasses entirely (PART 1, PART 18.10). Two of the
four do NOT reach a TS-authored model, and that gap is worth stating
explicitly since it's easy to assume a blueprint-side guarantee carries
over here:

--------------------------------------------------------------------------
19.1 — NO AUTOMATIC PER-STYLE TONE MAPPING
--------------------------------------------------------------------------
The JSON/JS path picks a tone-mapping operator (NoToneMapping, ACES,
Linear, or Cineon) from blueprint.meta.style every time buildScene() runs.
Loading a .ts factory never calls that function — renderer.toneMapping is
left at whatever it was last set to (ACESFilmicToneMapping at
exposure 1.1 on a fresh page load, or a leftover style-driven value if a
JSON/JS blueprint was rendered earlier in the same session). Design PBR
materials (PART 7) assuming ACESFilmic roll-off applies — that's the safe
default a cold-loaded page will actually have — and don't rely on a flat/
unrolled look unless you know the session's tone mapping is already set
that way. There is no TS-side field that requests a specific operator.

--------------------------------------------------------------------------
19.2 — NO AUTOMATIC EMISSIVE-INTENSITY CLAMP
--------------------------------------------------------------------------
The JSON/JS path soft-warns above 2.5 and hard-clamps emissiveIntensity
at 5.0 before it reaches the material. That clamp lives in
buildMaterialRaw(), which this path never calls — a TS factory sets
`material.emissiveIntensity` directly, and whatever value you write is
what renders, uncapped, with no console warning either way. Self-impose
the same discipline from PART 7.5's material map: 1.0-1.5 soft glow,
2.0-3.0 strong neon, and treat ~5.0 as a practical ceiling even though
nothing enforces it here — under ACESFilmic roll-off (19.1), values much
past that clip to solid white exactly as they would on the JSON/JS path,
just without a warning telling you it happened.

PART 25 — PATCH 3 AUDIT NOTE: PRIMITIVE SUGGESTION APPLIES, THUMBNAILS AND

A patch describing 3 renderer big-features (primitive-count suggestion,

19's items, these three split unevenly across the JSON/JS vs. TS paths —
one applies here untouched, two do not reach a TS-authored model at all.
Same caveat as PART 24: this is easy to get wrong by assuming a blueprint-
side guarantee carries over, so it's stated explicitly below rather than
left implicit.

--------------------------------------------------------------------------
20.1 — PRIMITIVE-COUNT SUGGESTION: APPLIES HERE UNCHANGED
--------------------------------------------------------------------------
The Prompt Builder's reference-image primitive-count estimate (color-
region counting, 32×32 downsample, clamped 3-40) and its TripoSR link are
pure UI behavior that runs the moment a reference image is attached in
the panel — it has no dependency on which output format (JSON, JS, or TS)

parts/factory-composed sub-shapes the model might need, never a hard
target, and never AI shape reconstruction. Nothing TS-specific to author
here.

--------------------------------------------------------------------------
20.2 — REFERENCE LIBRARY THUMBNAILS: DO NOT APPLY TO TS BUILDS
--------------------------------------------------------------------------
saveBlueprintToReferenceLibrary() — the function the thumbnail capture
was added to — is called with CURRENT_BLUEPRINT after a build, and no-ops
immediately if that argument is missing meta.style/meta.category. Loading
a .ts factory never populates CURRENT_BLUEPRINT at all (it stays null;
the live model lives in CURRENT_TS_MODEL/CURRENT_TS_META instead, per
PART 1/18.10) — so a TS-authored build is never written to the reference
library, with or without a thumbnail, exactly as it was never saved to
that library before this patch either. This patch changes what gets
stored for JSON/JS saves; it changes nothing about TS builds' total
absence from that library.

--------------------------------------------------------------------------
20.3 — EMISSIVE MASK ("emissiveMask"): DO NOT APPLY TO TS BUILDS
--------------------------------------------------------------------------
Same shape as PART 24.2's emissiveIntensity clamp: the new "emissiveMask"
blueprint field is read and applied inside buildMaterial(), in the same
JSON/JS-only code path this spec's PART 1/18.10 already establishes a TS
factory bypasses entirely. There is no TS-side equivalent field, and
setting `material.emissive`/`material.emissiveIntensity` directly inside
a createXxxModel() factory affects the WHOLE material exactly as it
always has — there is no way to reserve a sub-region (e.g. just the eyes)
for emissive-only glow from a .ts factory. If a model needs a masked
emissive region (the paper's "purple emissive eyes reserved on a separate
map" case), either accept whole-material emissive on this path, or
author the same model as JSON/JS instead where "emissiveMask" is
available (see that pipeline's PART 60.3), or split the masked part out
as its own separate mesh/material within the factory with its own
tighter geometry so its emissive naturally stays confined to the intended
region without needing a texture mask at all.

31.1 — MANDATORY COMPONENT HIERARCHY (MACRO → MESO → MICRO)
--------------------------------------------------------------------------------
Every character factory MUST build at least these named Group nodes
under root (use these exact .name strings or clearly scoped
equivalents). Missing any macro/meso part is a quality failure.

MACRO (required — these are the 6 root-level body masses):
  root            — the returned THREE.Group (set root.name = '')
  pelvis          — child Group .name = 'pelvis'
  abdomen         — child Group .name = 'abdomen'
  chest           — child Group .name = 'chest'
  neck            — child Group .name = 'neck'
  head            — child Group .name = 'head'

MESO (required for full-body characters):
  hair            — child Group .name = 'hair' (may be omitted only if bald)
  clavicle-l / clavicle-r
  upper-arm-l / upper-arm-r
  forearm-l / forearm-r
  hand-l / hand-r
  thigh-l / thigh-r
  shin-l / shin-r
  foot-l / foot-r

MICRO (required for face readability):
  brow-l / brow-r
  ear-l / ear-r
  nose
  mouth
  eye-l / eye-r
  eye-cavity-l / eye-cavity-r   (recessed sockets — see 31.5, never flat decals)

Optional but recommended when visible:
  fingers (thumb/index/middle/ring/little × 2-3 phalanges per hand)
  tail, ears (animal character), horns, accessories, clothing layers,
  held props

RULE: Never collapse independently movable parts into one mesh. Each
limb segment is its own Group with its own named pivot, and the chain
generator from PART 3 / PART 30 is the preferred single-mesh
implementation when the limb needs per-segment continuity — the limb
STILL rides on its own named Group ("arm_l", not folded into "chest").

SKELETON PATTERN (real TypeScript — use this as the factory's spine):

  export function createCharacterModel(opts?: CharacterModelOptions): THREE.Group {
    const root = new THREE.Group();
    root.name = ''; // root intentionally unnamed; see PART 1.2

    // MACRO
    const pelvis  = pivot('pelvis',  [ 0.00, 0.95, 0.00]);
    const abdomen = pivot('abdomen', [ 0.00, 1.20, 0.00]);
    const chest   = pivot('chest',   [ 0.00, 1.45, 0.00]);
    const neck    = pivot('neck',    [ 0.00, 1.70, 0.00]);
    const head    = pivot('head',    [ 0.00, 1.85, 0.00]);

    root.add(pelvis);
    pelvis.add(abdomen);
    abdomen.add(chest);
    chest.add(neck);
    neck.add(head);

    // MESO (left arm — right arm mirrors the same pattern)
    const clavicleL = pivot('clavicle-l', [-0.22, 1.55, 0.00]);
    const armL      = buildArm('l');
    const handL     = buildHand('l');
    chest.add(clavicleL);
    clavicleL.add(armL);
    armL.add(handL); // chain generator already builds pivot geometry

    // MESO (legs)
    const thighL = pivot('thigh-l', [-0.12, 0.85, 0.00]);
    const shinL  = pivot('shin-l',  [-0.12, 0.50, 0.00]);
    const footL  = pivot('foot-l',  [-0.12, 0.05, 0.08]);
    pelvis.add(thighL); thighL.add(shinL); shinL.add(footL);
    // mirror for right side ...

    // MICRO face
    const eyeCavityL = buildEyeCavity('l');
    const eyeL       = buildEye('l');
    head.add(eyeCavityL); eyeCavityL.add(eyeL);
    // ear-l, ear-r, nose, mouth, brow-l, brow-r, hair ...

    // Expose named nodes so the host rig can drive them
    root.userData.sculptRuntime = {
      nodes: {
        root, pelvis, abdomen, chest, neck, head,
        arm_l: armL, hand_l: handL, /* ... */
      },
      sockets: {
        'chest-clavicle-l': clavicleL,
        'chest-clavicle-r': clavicleR,
        'pelvis-thigh-l':   thighL,
        'pelvis-thigh-r':   thighR,
        'head-eye-l':       eyeCavityL,
        'head-eye-r':       eyeCavityR
      },
      materials: { /* see 31.4 */ }
    };

    applyOptions(root, opts);
    return root;
  }

  // Local helper — a named pivot Group at a world position:
  function pivot(name: string, pos: [number, number, number]): THREE.Group {
    const g = new THREE.Group();
    g.name = name;
    g.position.set(pos[0], pos[1], pos[2]);
    return g;
  }

31.2 — ATTACHMENT CONTRACT (userData.attachment on every child mesh)
--------------------------------------------------------------------------------
Every child Mesh (or Group that contains a mesh) MUST carry a
`userData.attachment` object describing the seam to its parent. The
TS path's runtime already populates `userData` (PART 6) so this rides
along to the inspector / future rig layer without any renderer change.

PREFERRED SHAPE (TypeScript):

  interface Attachment {
    parentSocket: string;         // semantic socket name on parent
    localStart:   [number, number, number]; // attach point in parent local space
    localEnd:     [number, number, number]; // far end of this segment
    contactType:  'rigid-weld' | 'socket-joint' | 'hinge-joint';
    baseRadius:   number;         // thickness at root
    endRadius:    number;         // thickness at tip
    embedDepth:   number;         // 0.02-0.05
    gapTolerance: number;         // 0.01
  }

CONTACT TYPE GUIDANCE (semantic, not enforced by the renderer):
  rigid-weld    — torso segments, neck, hair, clothing panels
  socket-joint  — shoulder, hip
  hinge-joint   — elbow, knee, finger joints, jaw

Minimum overlap at seams: 0.02 world units (do not leave floating
parts). The existing parent-child Group structure (31.1) is what the
scene graph USES to position the child — the userData.attachment object
is the contract that the rest of the model needs to satisfy.

EXAMPLE — arm_l with a full attachment contract (real TypeScript):

  function buildArm(side: 'l' | 'r'): THREE.Group {
    const sign = side === 'l' ? 1 : -1;
    const arm = new THREE.Group();
    arm.name = `arm_${side}`;
    // chain generator (PART 3) — or compose two capsule segments per
    // PART 40. Pivot is implicit in the segment aim direction.
    const mesh = chainMesh({
      baseRadius: 0.07,
      segs: 6,
      segments: [
        { length: 0.32, tipRatio: 0.85, aim: [ 0.06 * sign, -1, 0.05] },
        { length: 0.30, tipRatio: 0.65, aim: [ 0.08 * sign, -1, 0.20] }
      ]
    }, M.skin);
    arm.add(mesh);
    arm.userData.attachment = {
      parentSocket: 'chest-clavicle-' + side,
      localStart:   [ 0.22 * sign, -0.05,  0.00],
      localEnd:     [ 0.26 * sign, -0.65,  0.05],
      contactType:  'socket-joint',
      baseRadius:   0.085,
      endRadius:    0.055,
      embedDepth:   0.04,
      gapTolerance: 0.01
    };
    return arm;
  }

  // Quick helper for a "weld" attachment (clothing panels, hair):
  function weldAttachment(
    localStart: [number, number, number],
    localEnd:   [number, number, number],
    baseR: number, endR: number
  ): Attachment {
    return {
      parentSocket: 'auto',
      localStart, localEnd,
      contactType: 'rigid-weld',
      baseRadius: baseR, endRadius: endR,
      embedDepth: 0.03, gapTolerance: 0.01
    };
  }

31.3 — ACTION PROFILE & PIVOTS (userData.actionProfile on every macro/meso)
--------------------------------------------------------------------------------
Every macro and meso Group/Mesh should carry a
`userData.actionProfile` object. This is the same shape PART 30's rig
code reads — keep it in sync so a host rig can drive the character
without re-deriving it.

PREFERRED SHAPE (TypeScript):

  type AnimationRole = 'root' | 'static' | 'limb' | 'digit' | 'face';
  interface ActionProfile {
    animationRole: AnimationRole;
    pivot: {
      mode: 'center' | 'root' | 'custom';
      localPosition: [number, number, number];
      axis:           [number, number, number];
    };
    transformChannels: {
      translate:     boolean;
      rotate:        boolean;
      scale:         boolean;
      bend:          boolean;
      twist:         boolean;
      detach:        boolean;
      visibility:    boolean;
      materialState: boolean;
    };
    collider: {
      type:   'box' | 'sphere' | 'capsule';
      offset: [number, number, number];
      scale:  [number, number, number];
    };
    destruction: {
      breakable:     boolean;
      fractureGroup: string;
    };

PIVOT PLACEMENT RULES (read these BEFORE setting pivot.localPosition):
  root        — at the model's logical center (usually 0,0,0)
  pelvis      — at the hip center
  abdomen     — at the lower torso center
  chest       — at the upper torso center
  neck        — at the base of the neck (jaw line)

  forearm     — at the elbow
  hand        — at the wrist
  thigh       — at the hip
  shin        — at the knee
  foot        — at the ankle
  eye         — at the eye center
  jaw/mouth   — at the lower-lip center

EXAMPLE — head with actionProfile (real TypeScript):

  function buildHead(): THREE.Group {

    head.name = 'head';
    head.position.set(0, 1.85, 0);

      new THREE.SphereGeometry(0.18, 18, 14),

      pivot: { mode: 'center', localPosition: [0, 0, 0], axis: [0, 1, 0] },
      transformChannels: {
        translate: true, rotate: true, scale: false,
        bend: false, twist: false, detach: false,
        visibility: true, materialState: false
      },
      collider: { type: 'sphere', offset: [0, 0, 0], scale: [1, 1, 1] },
      destruction: { breakable: false, fractureGroup: 'head' }
    };

  // Helper for the common "limb joint" case:
  function jointActionProfile(
    role: AnimationRole,
    axis: [number, number, number] = [0, 1, 0]

      animationRole: role,

31.4 — MATERIALS (character palette + frequency bands)
--------------------------------------------------------------------------------
Minimum material set for a clothed character:
  skin, hair, shirt (or torso cloth), pants, shoes, eye, lips

A creature/mascot may substitute "fur"/"feathers"/"scales" for skin +
hair, but keep the eye + a "mouth interior" material distinct.

The TS path's MeshStandardMaterial already supports color / roughness /
metalness / emissive / normalMap. The "surface frequency bands" from
the enrichment file are extra OPTIONAL fields the runtime ignores today
— they're documented here for future rig/timing layers:

  - albedo.dominant        — MeshStandardMaterial.color (already set)
  - albedo.secondary       — optional "secondary color" for hand-painted
                              trim panels (renderer-ignored; document intent)
  - roughness.base         — MeshStandardMaterial.roughness (already set)
  - roughness.variation    — optional 0.0-0.1 jitter amount
  - surfaceFrequencyBands: — object with three optional sub-fields
      macro  — broad color/height breakup (sampled region span)
      meso   — pores, fabric weave, fur clumps
      micro  — highlight breakup under grazing light

DO NOT use a single flat color for the whole character. DO NOT paint
lighting into albedo. If you want a lit-vs-shadow region, use one of:
  - A second MeshStandardMaterial with slightly darker color on the
    specific panel/sub-mesh that's genuinely recessed
  - A duplicated, slightly inset mesh under a "shadow" Group
  - A custom onBeforeCompile hook (PART 28) for vertex-driven shading

ROUGHNESS GUIDANCE (when you set it explicitly on
MeshStandardMaterial.roughness):
  skin   0.45 - 0.60
  cloth  0.70 - 0.90
  hair   0.55 - 0.75
  eye    0.15 - 0.25
  lips   0.30 - 0.50
  shoe   0.50 - 0.80

31.5 — FACE LANDMARKS & RECESSED EYES (critical)
--------------------------------------------------------------------------------
Eyes MUST read as recessed cavities, not flat stickers. PREFERRED
techniques, in order of preference:

  1. Smaller sphere for the cavity, then a slightly smaller eye sphere
     inset into it (most reliable across every renderer version).
  2. Inset sphere with a slight negative Z offset (chibi style).
  3. booleanSubtract a small sphere from the head, then place a smaller
     eye sphere inside the resulting hole. (Use the three-bvh-csg
     library for true boolean ops, or use ExtrudeGeometry with a
     pierced Shape from PART 3.7.)

LANDMARK PLACEMENT (relative to head height, where head height = 1.0):
  eye line          — at   0.55 of head height from the chin
  eye spacing       — 0.30-0.35 of head width apart (center to center)
  nose base         — at   0.40 of head height from the chin
  mouth line        — at   0.25 of head height from the chin
  brow line         — at   0.68 of head height (above the eye line)
  ear line          — at   0.55 of head height (≈ on the eye line)

EXAMPLE — recessed eye cluster (chibi, head height 0.42, real TS):

  function buildEyeCavity(side: 'l' | 'r'): THREE.Group {
    const sign = side === 'l' ? -1 : 1;
    const g = new THREE.Group();
    g.name = `eye-cavity-${side}`;
    g.position.set(0.06 * sign, 0.04, 0.18);
    const m = new THREE.Mesh(
      new THREE.SphereGeometry(0.045, 12, 10),
      M.skin_d
    );
    m.name = `eye-cavity-${side}-mesh`;
    g.add(m);
    g.userData.actionProfile = {

31.6 — BUILD PASSES (ordered, do not skip)
--------------------------------------------------------------------------------
When generating a character factory, mentally (or actually) follow this
order. Emit the full factory only after the last required pass.

  1. blockout
     - root + pelvis + abdomen + chest + neck + head + major limb capsules
     - Correct head-unit proportions and overall silhouette
     - Acceptance: humanoid proportions readable with zero materials

  2. proportion-lock
     - Lock head/torso/limb ratios to measured reference (or style table)
     - Fix pose angles (elbow/knee bend, weight shift)

  3. feature-placement
     - hair, brows, ears, nose, mouth, eyes + cavities
     - fingers if visible
     - All attachment contracts filled (31.2)

  4. material-pass
     - Assign skin/hair/cloth/shoe/eye/lips materials
     - Sample real mid-tone colors from reference if image is present
     - Add roughness variation and basic frequency bands (31.4)

  5. lighting-pass
     - Optional in the factory, required in the post-render review
     - Note key / fill / rim intent (which way does the main light come
       from on the reference?)

  6. interaction-pass
     - Confirm every limb has a named pivot in userData.actionProfile (31.3)
     - Confirm every held prop is parented to a hand Group, not floating
     - Populate root.userData.sculptRuntime with nodes + sockets (31.1)

  7. optimization-pass
     - Stay inside the performance budget (prefer < 80-120k tris for
       full characters)
     - Share material instances across sibling meshes (one M.skin,
       not 14 copies)

31.7 — QUALITY CONTRACT (anti-shallow rules — REJECT/REWRITE if any fire)
--------------------------------------------------------------------------------
REJECT the factory and rewrite if ANY of these are true:

  - Only a root + 1-2 child Groups for a full character (PART 31.1 lists
    the minimum set; a 3-Group character is NEVER acceptable)
  - Limbs are single CapsuleGeometry meshes with no elbow/knee break
    (use the chain generator from PART 3, or two stacked capsule
    segments per limb)
  - Eyes are flat PlaneGeometry / decal-style quads with no cavity (31.5)
  - Hands are undifferentiated BoxGeometry with no fingers (when
    fingers are visible at the reference's zoom level)
  - Materials are one generic MeshStandardMaterial with uniform
    roughness (31.4)
  - Child Groups float with no parent chain back to root (31.1)
  - Adjacent parts have seam gap > 0.02 (PART 30 rule)
  - Face landmarks ignore measured eye-line / mouth-line (31.5)
  - Pose is forced to perfect T-pose when the reference shows a
    different pose (PART 30 / PART 42)
  - root.userData.sculptRuntime.nodes does not name every macro +
    meso Group by its standard id (31.1 / 31.8)

DEFINITION OF DONE (character):
  Silhouette matches the reference, primary proportions are correct,
  component hierarchy depth ≥ 3 levels (macro + meso + micro from 31.1),
  most recognizable local features are present, materials respond to
  light (not flat plastic), root.userData.sculptRuntime exposes
  named nodes and sockets.

Append these to PART 12's validation checklist (character-only items):

  [ ] [v1.8] Character has all 6 MACRO Groups (root, pelvis, abdomen,

  [ ] [v1.8] Full-body character has all 14 MESO Groups (hair, 2× clavicle,

31.9 — QUICK CHARACTER SCAFFOLD (copy-paste starting point)

Use this mental skeleton, then fill real scales/positions from the
reference (or from PART 20's style table for a prompt-only build):

  root
  ├── pelvis
  │   ├── thigh-l → shin-l → foot-l
  │   └── thigh-r → shin-r → foot-r
  ├── abdomen
  │   └── chest
  │       ├── neck → head
  │       │         ├── hair
  │       │         ├── brow-l / brow-r
  │       │         ├── ear-l / ear-r
  │       │         ├── nose
  │       │         ├── mouth
  │       │         ├── eye-cavity-l → eye-l
  │       │         └── eye-cavity-r → eye-r
  │       ├── clavicle-l → upper-arm-l → forearm-l → hand-l (+ fingers)
  │       └── clavicle-r → upper-arm-r → forearm-r → hand-r (+ fingers)

For a chibi mascot, fold thighs and shins into one stubby cylinder per
leg, omit fingers, exaggerate the head, and keep all 6 MACRO Groups
(31.1 — never fold chest+abdomen+pelvis into one "body" even on a
chibi).

For a quadruped (dog, cat, horse, dragon), replace thigh-r/l + shin-r/l
with front-leg-r/l + back-leg-r/l, add a tail Group attached to
pelvis, and keep the same eye/brow/ear/nose/mouth micro face structure
(move ears forward to the eye line per 31.5).

For a creature with no arms (slime, octopus with a humanoid face), drop
clavicle/upper-arm/forearm/hand per side but keep the rest of the
hierarchy intact.

  // ---- Inspect metrics (closes error [9] + feeds the inspector) ------
  export function inspectModelTriangles(
    rootGroup: THREE.Object3D
  ): MeshTriangleMetrics {
    let triangles = 0, meshes = 0;
    const materials = new Set<THREE.Material>();
    rootGroup.traverse(obj => {
      const m = obj as THREE.Mesh;
      if (!m.isMesh) return;
      meshes++;
      const idx = m.geometry?.getIndex();
      const pos = m.geometry?.getAttribute('position');
      if (idx) triangles += idx.count / 3;
      else if (pos) triangles += pos.count / 3;
      const mat = m.material as
        THREE.Material | THREE.Material[] | undefined;
      if (Array.isArray(mat)) mat.forEach(x => materials.add(x));
      else if (mat) materials.add(mat);
    });
    const bones  = new Set<THREE.Bone>();
    const clips  = new Set<THREE.AnimationClip>();
    rootGroup.traverse(obj => {
      if ((obj as THREE.Bone).isBone) bones.add(obj as THREE.Bone);
    });
    const root = rootGroup as THREE.Group;
    (root.animations || []).forEach(c => clips.add(c));
    return {
      triangles: Math.round(triangles),
      meshes,
      materials: materials.size,
      bones:     bones.size,
      clips:     clips.size,
    };
  }

32.3 — STRUCTURAL REFERENCE CHECKLIST (run through silently before output)

Before you emit a .ts factory, mentally walk this list. Any unchecked
item is a build failure on the renderer's TS loader.

  [ ] 1. ZERO relative local imports (`./...` or `../...`).
  [ ] 2. All imports strictly from 'three' or 'three/examples/jsm/...'
        (or the 'three/addons/...' alias the import map accepts).
  [ ] 3. Every animated Bone has an explicit, matching .name string.
  [ ] 4. All QuaternionKeyframeTracks are normalized and use

  [ ] 5. Child bones are parented to their respective parent bones

  [ ] 6. Every animated node is attached to the root group BEFORE

  [ ] 7. All quaternion keyframe arrays are strictly monotonic in

  [ ] 8. All materials use MeshStandardMaterial (or MeshPhysicalMaterial

  [ ] 9. Every CanvasTexture has both `needsUpdate = true` and

[1] PROCEDURAL VERTEX AMBIENT OCCLUSION (AO) & CAVITY SHADING
    PROBLEM: flat-shaded or basic low-poly models can look washed out
    in uniform lighting without ambient occlusion textures.
    SOLUTION: calculate per-vertex AO mathematically during mesh
    generation by analyzing vertex proximity to adjacent geometry and
    ground planes; store the result in BufferGeometry's `color`
    attribute; enable on the material with `vertexColors: true`.
    CANONICAL HELPER (drop into every factory that needs cavity depth):

      export function applyProceduralVertexAO(
        geometry: THREE.BufferGeometry,
        cavityFactor = 0.85
      ): void {
        const pos = geometry.attributes.position;
        const colors = new Float32Array(pos.count * 3);
        for (let i = 0; i < pos.count; i++) {
          // Simple height-based cavity; replace with proximity/raycast
          // for true crevice depth on concave meshes.
          const y = pos.getY(i);
          const occlusion = Math.max(
            0.65,
            Math.min(1.0, 0.75 + (y * 0.25) * cavityFactor)
          );
          colors[i * 3]     = occlusion;
          colors[i * 3 + 1] = occlusion;
          colors[i * 3 + 2] = occlusion;
        }
        geometry.setAttribute('color', new THREE.BufferAttribute(colors, 3));
      }

    USAGE: call once per BufferGeometry after construction, then set
    `material.vertexColors = true`. For multi-mesh models, expose a
    top-level option `{ ao?: { enabled: boolean; cavityFactor?: number } }`
    on the factory's options interface. Default: enabled with
    cavityFactor = 0.85. Reinforces PART 7 (PBR recipes) and PART 18
    (fidelity pass).

[2] ANALYTICAL 2-BONE INVERSE KINEMATICS (IK) & GROUND ADAPTATION
    PROBLEM: forward-kinematics (FK) animations cause foot sliding on
    uneven terrain or when positioning legs interactively.
    SOLUTION: closed-form Law of Cosines 2-Bone IK solver in pure TS
    for digitigrade and anthropomorphic limbs. Given upper limb length
    L1, lower limb length L2, and target distance D:
        cos(AngleKnee) = (L1^2 + L2^2 - D^2) / (2 * L1 * L2)
    CANONICAL HELPER (drop in for any model with 2-segment limbs):

      export function solveTwoBoneIK(
        upperLength: number,
        lowerLength: number,
        target: THREE.Vector3,
        pole: THREE.Vector3 = new THREE.Vector3(0, 1, 0)
      ): { upper: THREE.Quaternion; lower: THREE.Quaternion } {
        const D = target.length();
        const D2 = D * D;
        const L1 = upperLength, L2 = lowerLength;
        // Law of cosines for the knee angle
        const cosKnee = (L1 * L1 + L2 * L2 - D2) / (2 * L1 * L2);
        const kneeAngle = Math.acos(Math.max(-1, Math.min(1, cosKnee)));
        // Knee bend axis: perpendicular to the upper-limb-to-target plane
        const upperDir = target.clone().normalize();
        const kneeOffset = upperDir
          .clone()
          .multiplyScalar(L1 * Math.cos(Math.PI - kneeAngle))
          .add(pole.clone().normalize()
            .multiplyScalar(L1 * Math.sin(Math.PI - kneeAngle)));
        const lowerDir = target.clone().sub(kneeOffset).normalize();
        const upperQ = new THREE.Quaternion()
          .setFromUnitVectors(new THREE.Vector3(0, -1, 0), kneeOffset.normalize());
        const lowerQ = new THREE.Quaternion()
          .setFromUnitVectors(new THREE.Vector3(0, -1, 0), lowerDir);
        return { upper: upperQ, lower: lowerQ };
      }

    USAGE: call once per frame from root.userData.tick when the model
    has interactive limb posing or terrain following. Expose the
    solver as a method on `root.userData.ikSolver` so the inspector
    or an external controller can drive it. Cross-references PART 5
    (tick contract) and PART 30 (rigging). Reinforces PART 32.4
    (normalized quaternions) — the solver already returns
    unit-length quaternions.

[5] AUDIO-REACTIVE & EVENT-DRIVEN ANIMATION BLENDING STATE MACHINE
    PROBLEM: animations are static playback loops without responsiveness.
    SOLUTION: a lightweight, zero-dependency Finite State Machine (FSM)
    with:

        → Alert).

        pulses, and exhaust glow to modulate dynamically with music or

    CANONICAL PATTERN (drop in for any model that ships with
    AnimationClips — pairs with PART 30.4):

      export interface FsmState {
        name: string;
        clip: THREE.AnimationClip;
        /** seconds to crossfade in */
        fadeIn?: number;
      }
      export class AnimationFsm {
        private mixer: THREE.AnimationMixer;
        private states: Map<string, FsmState>;
        private current: { action: THREE.AnimationAction; state: FsmState } | null = null;
        constructor(mixer: THREE.AnimationMixer, states: FsmState[]) {
          this.mixer = mixer;
          this.states = new Map(states.map(s => [s.name, s]));
        }
        transition(name: string, fadeIn = 0.25): void {
          const next = this.states.get(name);
          if (!next || this.current?.state.name === name) return;
          const nextAction = this.mixer.clipAction(next.clip);
          nextAction.reset().play();
          if (this.current) {
            this.current.action.crossFadeTo(nextAction, fadeIn, false);
          }
          this.current = { action: nextAction, state: next };
        }
        update(dt: number): void {
          if (this.current) this.mixer.update(dt);
        }
        /** Web Audio integration — drive emissive intensity from
            an AnalyserNode's frequency bin */
        attachAudio(analyser: AnalyserNode, target: THREE.MeshStandardMaterial): void {
          const data = new Uint8Array(analyser.frequencyBinCount);
          const loop = () => {
            analyser.getByteFrequencyData(data);
            const avg = data.reduce((a, b) => a + b, 0) / data.length;
            target.emissiveIntensity = 0.5 + (avg / 255) * 1.5;
            requestAnimationFrame(loop);
          };
          loop();
        }
      }

    USAGE: instantiate inside the factory; expose the FSM on
    `root.userData.animationFsm` so the inspector can list its states
    and trigger transitions. The Web Audio integration is OPT-IN —
    only attach `attachAudio()` when the model is loaded with a
    user-controlled audio source. Cross-references PART 5 (tick) and
    PART 30.4 (named AnimationClips).

[6] ZERO-TEXTURE PROCEDURAL PARTICLE & VFX EMITTERS
    PROBLEM: exhaust flames, dust puffs, and sparks usually require
    particle images.
    SOLUTION: procedural geometric particle systems using
    `THREE.InstancedMesh` or `THREE.Points` with mathematical shapes:
      - Conical hydraulic steam bursts.
      - Geometric polygonal foot-stomp dust clouds (faceted
        dodecahedrons).
      - Thruster plasma flame with animated vertex noise.
    CANONICAL PATTERN (InstancedMesh particle emitter — drop in for
    any model with continuous VFX):

      export function makeInstancedParticleEmitter(opts: {
        count: number;
        geometry: THREE.BufferGeometry;
        material: THREE.Material;
        /** units per second along local +Y by default */
        speed: number;
        /** world-seconds per particle lifetime */
        lifetime: number;
        /** local-space upward bias */
        bias?: THREE.Vector3;
      }): THREE.InstancedMesh {
        const mesh = new THREE.InstancedMesh(
          opts.geometry, opts.material, opts.count
        );
        mesh.frustumCulled = false;   // particles span a wide volume
        mesh.userData.particles = {
          velocities: new Array(opts.count).fill(0).map(() =>
            new THREE.Vector3(
              (Math.random() - 0.5),
              1,
              (Math.random() - 0.5)
            ).multiplyScalar(opts.speed)
          ),
          ages: new Float32Array(opts.count),
          lifetime: opts.lifetime,
          bias: opts.bias ?? new THREE.Vector3(0, 0, 0),
        };
        return mesh;
      }

      /** Per-frame updater — call from root.userData.tick */
      export function updateInstancedParticles(
        mesh: THREE.InstancedMesh, dt: number
      ): void {
        const m = new THREE.Matrix4();
        const p = mesh.userData.particles;
        for (let i = 0; i < mesh.count; i++) {
          p.ages[i] += dt;
          if (p.ages[i] > p.lifetime) p.ages[i] = 0;
          const v = p.velocities[i];
          m.makeTranslation(
            v.x * p.ages[i] + p.bias.x,
            v.y * p.ages[i] + p.bias.y,
            v.z * p.ages[i] + p.bias.z
          );
          mesh.setMatrixAt(i, m);
        }
        mesh.instanceMatrix.needsUpdate = true;
      }

    USAGE: create one or more emitters inside the factory, expose them
    on `root.userData.particles`, and call `updateInstancedParticles()`
    from `root.userData.tick`. Reinforces PART 5 (tick) and PART 28
    (VFX). No external textures — the AI picks the geometry primitive
    that fits the visual intent (cone for steam, dodecahedron for dust,
    custom small-mesh for sparks).

[8] SECONDARY SPRING DYNAMICS (PASSIVE JIGGLE / HYDRAULIC RECOIL)
    PROBLEM: rigid bones lack secondary physics momentum.
    SOLUTION: a lightweight Hooke's Law spring-damper calculation in
    the render loop:
        acceleration = -stiffness * displacement - damping * velocity
    Applied to:
      - Whip antenna flex during rapid turns.
      - Torso shock absorber recoil on landing.
      - Wire harness bounce during walking.
    CANONICAL PATTERN (drop in for any bone with a "jiggle" feel):

      export interface SpringState {
        displacement: number;  // current offset from rest
        velocity:     number;  // current rate of change
        stiffness:    number;  // pull-back strength (e.g. 80)
        damping:      number;  // energy loss (e.g. 8)
        rest:         number;  // 0 for centered springs
      }
      export function updateSpring(s: SpringState, dt: number,
                                   externalForce = 0): number {
        const a = -s.stiffness * (s.displacement - s.rest)
                  - s.damping * s.velocity
                  + externalForce;
        s.velocity     += a * dt;
        s.displacement += s.velocity * dt;
        return s.displacement;
      }

    USAGE: each jiggle bone has one or more `SpringState` values
    stored on `bone.userData.spring`; call `updateSpring()` from
    `root.userData.tick` and apply the returned displacement to a
    `bone.rotation` or `bone.position` axis. Reinforces PART 5 (tick)
    and PART 30 (bone-driven animation).

34.1 — THE ESCAPE HATCH (the one and only)
--------------------------------------------------------------------------
PART 4.1 / 4.2 say: every .ts factory is a single self-contained file.
The only allowed imports are 'three' and 'three/examples/jsm/...' (or
the 'three/addons/...' alias). Zero relative imports, zero npm packages,
zero local helpers, no fetch — the entire build must live in one file.

v1.11 sanctions a single, narrow exception:

    import {
      buildSkeleton,                 // compile a RigGraph → THREE.Skeleton
      buildSemanticWeights,          // smooth vertex-skin weights (4 influences)
      buildRigidSemanticWeights,     // compact uint8 vertex-skin weights (≤ 255 bones)
      validateRigGraph,              // check a RigGraph before compiling
      validateWeights,               // check a geometry's skinIndex/skinWeight
    } from 'three-rig-helpers';

The bare specifier 'three-rig-helpers' resolves through the renderer's
import map (the only entry added in v1.11, the fifth line in the
`imports` object — see PART 4.1's import-map convention) to a
pre-bundled, minified ES module at ./public/rig/three-rig-helpers.js
(3.9 KB, single file, ES2020 target, ZERO deps beyond the page's own
'three' build — the bundle's `import * as THREE from 'three'` is left
as a bare specifier so the page's import map resolves it).

That is the entire exception. Everything else in PART 4 still applies:
no other relative imports, no other local helpers, no other npm
packages, no fetch, no dynamic specifier hacks, no private registry,
no bundling your own three, no `import.meta`. The 'three-rig-helpers'
import is the single permitted local helper — period.

Why this exception exists: the v8.3 / v1.10-era auto Bone-promotion +
single-bone-per-part rigid skin at GLB export time (PART 30.7) is
sufficient for the 99% case where each mesh deforms as a rigid unit
bound to a single bone. The remaining 1% — smooth-skinned characters,
faces with proper blendshape-style vertex weighting, rig graphs with
> 255 bones that need a real multi-bone-per-vertex bind — needs the AI
to author a real THREE.SkinnedMesh with `skinIndex` + `skinWeight`
attributes, which is more code than belongs inline. The pre-bundled
helpers exist to make that 1% tractable while preserving every other
PART 4 guarantee.

--------------------------------------------------------------------------
34.2 — THE 5 PUBLIC FUNCTIONS
--------------------------------------------------------------------------
All 5 are pure / deterministic / have no DOM dependencies. All 5 throw
explicit Error messages (or push to a string[] for the validators) so
failures are diagnosable from the console, not silent.

  // 1. Compile a RigGraph into a THREE.Skeleton + bone map.
  //    Validates exactly one root joint, parent-before-child ordering,
  //    and updates matrixWorld BEFORE calculateInverses() (otherwise
  //    every inverse is identity and vertices stretch from the origin
  //    when SkinnedMesh applies the bind pose — see upstream comment).
  function buildSkeleton(graph: RigGraph): SkeletonBuildResult;

  // 2. Build smooth skin weights (4-influence per vertex, nearest joints
  //    by squared-distance falloff). Returns a Uint16BufferAttribute for
  //    skinIndex and a Float32BufferAttribute for skinWeight, plus
  //    maxWeightError (the worst |1 - sum| across the geometry — the
  //    AI should surface this in its pre-emission checklist).
  function buildSemanticWeights(
    geometry: THREE.BufferGeometry,
    skeleton: SkeletonBuildResult,
    joints: RigJoint[],
    maxInfluences?: number,        // default 4
  ): WeightBuildResult;

  // 3. Build COMPACT skin weights (uint8 indices + uint8 normalized
  //    weights, 1 influence per vertex, weight = 255). For
  //    reconstructed multipart surfaces where smoothing across an
  //    unknown source seam would be less truthful than a rigid semantic
  //    region. Throws if the skeleton has > 255 bones (uint8 index cap).
  function buildRigidSemanticWeights(
    geometry: THREE.BufferGeometry,
    skeleton: SkeletonBuildResult,
    resolveJoint: (x: number, y: number, z: number, vertex: number) => string,
  ): CompactWeightBuildResult;

  // 4. Validate a RigGraph BEFORE compiling it. Returns string[] of
  //    human-readable errors (empty array = clean). Checks for:
  //    duplicate joint ids, self-parenting, NaN / Infinity rest
  //    positions, missing parent joints, and root count != 1.
  function validateRigGraph(graph: RigGraph): string[];

  // 5. Validate a geometry's skinIndex + skinWeight attributes. Returns
  //    string[] of human-readable errors. Checks for: skinWeight vec4
  //    presence, skinIndex vec4 presence, and per-vertex |sum - 1|
  //    within the supplied tolerance (default 0.001). An empty return
  //    value is the 6th item in the pre-emission checklist below.
  function validateWeights(geometry: THREE.BufferGeometry, tolerance?: number): string[];

  // Bonus, not part of the "5 public" but documented for completeness
  // (also exported by the bundle, free, no extra cost):
  //   resetSkeleton(result):       re-pose a built skeleton to bind
  //   jointWorldPosition(result, id): query a joint's world position
  //   asVector([x,y,z]):           convert a Vec3 literal to THREE.Vector3

--------------------------------------------------------------------------
34.3 — THE 3 DATA SHAPES (re-declared for spec self-containment)
--------------------------------------------------------------------------
The bundle ships the source-of-truth types INLINE — no external type
imports. The spec must be self-contained, so the canonical shapes are
re-declared here verbatim. If the upstream character-ir.ts source is
attached in a future round, the types in this section are what to expect.

  // [number, number, number] — XYZ literal. THREE.Vector3-compatible.
  type Vec3 = [number, number, number];

  // [x, y, z, w] — quaternion in XYZW order. The bundle's
  // bone.quaternion.set(...restRotation) consumes this order directly.
  type Quat4 = [number, number, number, number];

  // One joint in the rig graph. parentId is OMITTED for the root.
  // restPosition is WORLD-space (the build pass subtracts the parent's
  // rest position to derive a local offset — see buildSkeleton above).
  // restRotation is WORLD-space quaternion in XYZW order. Bone NAMES
  // are the same .name strings, so they must follow PART 32 error [2]'s
  // alphanumeric-with-underscores rule and (for any humanoid / biped /
  // mech) reuse STANDARD_BONES from PART 33.1[10].
  interface RigJoint {
    id: string;                    // unique, alphanumeric + underscore
    parentId?: string;             // OMITTED on the single root
    restPosition: Vec3;            // [x, y, z] world-space
    restRotation: Quat4;           // [x, y, z, w] world-space, unit length
  }

  // The full rig graph. joints[] does NOT need to be topologically
  // sorted — buildSkeleton re-orders via a pending-queue walk that
  // defers a joint until its parent has been added. But sorting it
  // parent-before-child is fine and helps the AI's own debugging.
  interface RigGraph {
    joints: RigJoint[];
  }

The bundle ALSO exports two return-type shapes (free, not part of the
"3 data shapes" but useful for editor / .d.ts consumers):

  interface SkeletonBuildResult {
    root: THREE.Bone;
    bones: Map<string, THREE.Bone>;
    skeleton: THREE.Skeleton;
    restWorldPositions: Map<string, THREE.Vector3>;
  }
  interface WeightBuildResult {
    indices: THREE.Uint16BufferAttribute;
    weights: THREE.Float32BufferAttribute;
    maxWeightError: number;
  }
  interface CompactWeightBuildResult {
    indices: THREE.Uint8BufferAttribute;
    weights: THREE.Uint8BufferAttribute;
  }

--------------------------------------------------------------------------
34.5 — WORKED EXAMPLE: SMOOTH-SKINNED ROBOT (validate → build skeleton
        → build mesh → validate weights → expose userData.rigGraph)
--------------------------------------------------------------------------
The end-to-end pattern for a model that genuinely needs vertex skin
weights. Adapted from the maintainer's own robot-rigging build session
to fit this renderer's single-file factory contract. Drop this skeleton
into a real createXxxModel() factory — DO NOT paste it as a standalone
file with no factory wrapper (PART 30.0's load-time rejection applies).

  import * as THREE from 'three';
  import {
    buildSkeleton,
    buildSemanticWeights,
    validateRigGraph,
    validateWeights,
  } from 'three-rig-helpers';

  export function createSmoothSkinnedRobotModel(options?: { color?: number }): THREE.Group {
    const root = new THREE.Group();
    root.name = 'RobotRoot';

    // 1. Declare the rig graph (world-space rest positions, parent links).
    //    Note: parentId omitted on the single root; restRotation is a unit
    //    quaternion (0,0,0,1) for a default-pose robot.
    const rig: RigGraph = {
      joints: [
        { id: 'Bone_Pelvis', restPosition: [0, 1.0, 0], restRotation: [0, 0, 0, 1] },
        { id: 'Bone_Spine',  parentId: 'Bone_Pelvis', restPosition: [0, 1.25, 0], restRotation: [0, 0, 0, 1] },
        { id: 'Bone_Chest',  parentId: 'Bone_Spine',  restPosition: [0, 1.55, 0], restRotation: [0, 0, 0, 1] },
        { id: 'Bone_Head',   parentId: 'Bone_Chest',  restPosition: [0, 1.85, 0], restRotation: [0, 0, 0, 1] },
        { id: 'Bone_Shoulder_L', parentId: 'Bone_Chest', restPosition: [ 0.25, 1.65, 0], restRotation: [0, 0, 0, 1] },
        { id: 'Bone_Arm_L',      parentId: 'Bone_Shoulder_L', restPosition: [ 0.50, 1.55, 0], restRotation: [0, 0, 0, 1] },
        { id: 'Bone_Shoulder_R', parentId: 'Bone_Chest', restPosition: [-0.25, 1.65, 0], restRotation: [0, 0, 0, 1] },
        { id: 'Bone_Arm_R',      parentId: 'Bone_Shoulder_R', restPosition: [-0.50, 1.55, 0], restRotation: [0, 0, 0, 1] },
      ],
    };

    // 2. Validate BEFORE building — fail fast, surface every error.
    const rigErrors = validateRigGraph(rig);
    if (rigErrors.length > 0) {
      throw new Error('rig graph validation failed:\n  - ' + rigErrors.join('\n  - '));
    }

    // 3. Compile the rig → THREE.Skeleton + bone map.
    const built = buildSkeleton(rig);

    // 4. Build the geometry (procedural torso + head, no PART 30 auto-
    //    promotion needed because we're authoring the SkinnedMesh
    //    ourselves; the auto-promotion path is a no-op for true
    //    SkinnedMeshes).
    const torsoGeo = new THREE.CylinderGeometry(0.20, 0.22, 0.55, 8, 4, true);
    torsoGeo.translate(0, 0.275, 0);   // base at y=0 (parent local)

    // 5. Build smooth skin weights (4-influence, distance falloff).
    const w = buildSemanticWeights(torsoGeo, built, rig.joints);
    if (w.maxWeightError > 0.01) {
      console.warn('[rig] torso weights max error =', w.maxWeightError,
                  '(> 0.01 — geometry may show seams at joint boundaries)');
    }

    // 6. Validate the weights BEFORE assembling the SkinnedMesh.
    const weightErrors = validateWeights(torsoGeo);
    if (weightErrors.length > 0) {
      throw new Error('skin weight validation failed:\n  - ' + weightErrors.join('\n  - '));
    }

    // 7. Assemble the SkinnedMesh and wire it to the root bone.
    const torsoMat = new THREE.MeshStandardMaterial({
      color: options?.color ?? 0x8aa0b8,
      roughness: 0.55, metalness: 0.35,
    });
    const torsoMesh = new THREE.SkinnedMesh(torsoGeo, torsoMat);
    built.root.add(torsoMesh);
    // CRITICAL: bind the SkinnedMesh to the compiled skeleton explicitly.
    // (Auto-bind via mesh.skeleton = built.skeleton is the conventional
    //  shape; the renderer's GLB-export path picks it up either way.)
    torsoMesh.bind(built.skeleton, built.root.matrixWorld);

    // 8. Expose the runtime contract on userData so the renderer can
    //    surface a "Rig" button + the joint hierarchy panel.
    root.userData.rigGraph = rig;                                    // PART 34 contract
    root.userData.skeletonSource = 'three-rig-helpers';              // PART 34 marker
    root.userData.skeleton = built.skeleton;                         // optional: live THREE.Skeleton
    root.userData.bones = built.bones;                               // optional: id → THREE.Bone map
    root.userData.restWorldPositions = built.restWorldPositions;     // optional: id → world pos

    return root;
  }

That is the whole pattern: validate → build skeleton → build geometry →
build weights → validate weights → assemble SkinnedMesh → expose
userData.rigGraph. Every other line in the file is normal PART 1-33
factory body code (materials, head sphere, optional PART 33.1[5]
animationFsm, etc.).

34.7 — RUNTIME CONTRACT (what the renderer does when it sees
        userData.rigGraph)
--------------------------------------------------------------------------
The renderer's `window.lblSpec.refreshOnLoad()` (in index.html, the

contract, and inert for every other model:

  (a) VALIDATOR E11 (rig helpers marker check)
      If `root.userData.rigGraph` is present but
      `root.userData.skeletonSource !== 'three-rig-helpers'`, the
      renderer surfaces a non-blocking warning via the spec chip —
      "Rig graph declared but skeletonSource is missing or not
      'three-rig-helpers'". This is a STRICT check: the only
      sanctioned source is the pre-bundled helpers. A model with a
      custom-built SkinnedMesh is allowed (PART 30.7's auto-promotion
      + per-part skin handles it) but should NOT also declare
      userData.rigGraph — pick one path or the other.

  (b) RIG BUTTON (topbar, next to the Sockets button)
      If `root.userData.rigGraph` is present AND
      `root.userData.skeletonSource === 'three-rig-helpers'`, the
      renderer enables a new Rig button in the topbar (right after
      the Sockets button, before Recipes). Clicking it opens a panel
      listing every joint: id, parent id, and the rest position
      (read from the rigGraph on every open). The panel re-validates
      the graph with `validateRigGraph()` on every open and surfaces
      any errors as a red banner above the joint list. The validator
      runs CLIENT-SIDE — it does not require the bundle to be
      imported dynamically; the bundle is loaded once at page load via
      the import map and the helpers are available globally.

  (c) GLB EXPORT OPTIMIZATION (optional, buildSkinnedHierarchyForExport)
      The existing `buildSkinnedHierarchyForExport` (index.html line
      ~14069, see PART 30.7) is the renderer's auto Bone-promotion +
      per-part skin pass. If the loaded model ALREADY has a real
      SkinnedMesh with skinIndex + skinWeight from PART 34, the
      export pass detects that and is a no-op for those meshes (no
      need to re-bind what the factory already bound correctly). The
      optimization is internal — the export button is unchanged, no
      new button, no new workflow.

34.8 — CROSS-REFERENCES
--------------------------------------------------------------------------
PART 34 layers on top of, never replaces:

  - PART 4.1 / 4.2 — the single-file / no-relative-import rule. PART 34
    is the one explicit exception; the rest of PART 4 still applies.
  - PART 30 (rigging & animation authoring standard) — the default
    pivot-hierarchy approach is still the right answer for ~99% of
    cases. Reach for 34 only when 30's auto-promotion + single-bone-
    per-part rigid skin is insufficient.
  - PART 30.2 — bone naming rule. Every joint id must be alphanumeric
    + underscore and (for humanoids / bipeds / mechs) reuse
    STANDARD_BONES from PART 33.1[10].
  - PART 30.7 — the auto-promotion + per-part skin pass is the
    renderer's existing skeleton export path. PART 34 is a strictly
    more powerful alternative for the 1% of cases that need it.
  - PART 32 error [2] — track binding. Every animated bone still needs
    an explicit, alphanumeric .name. The Rig panel's joint list reads
    the same .name strings.
  - PART 32.4 (16-item structural reference checklist) — the 6 items
    in 34.6 are an APPEND to that list, not a replacement.
  - PART 33.1[10] / 33.5 — the universal rigging standard + the
    STANDARD_BONES catalog. Reuse the canonical names; don't invent
    alternates.
  - PART 33.4 (10-item architectural checklist) — orthogonal. None of
    33.4's items change. A model that imports 'three-rig-helpers'
    still benefits from any of 33.1[1-9] that apply to the subject.

PART 34 does NOT introduce:
  - Any new field that PART 30 / 33 doesn't already accept
  - Any new renderer behavior beyond (a) the E11 validator, (b) the Rig
    button, and (c) the export-path no-op described in 34.7
  - Any new dependency in the model file beyond the single
    'three-rig-helpers' import
  - Any change to the GLB export's user-visible behavior
